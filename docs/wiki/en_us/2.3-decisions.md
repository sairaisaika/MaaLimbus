## D1 · Maa owns the device, Python owns the judgement

`PROJECT.md:1338-1339` writes this out as a development contract: Maa owns screenshots/input and bounded Pipeline scheduling, pure Python ranks the choices, and the Agent returns recognition boxes and state updates. The direct consequence is that **no module under `src/maalimbus/` imports `maa` at module level**, except `windows_controller.native_methods()` (`src/maalimbus/windows_controller.py:17`) and a few `*_native.py` modules (e.g. `src/maalimbus/battle_counter_native.py:1`, `src/maalimbus/shop_native.py:1`) that reach for the native enums inside a function body. That is what lets the great majority of the judgement be replayed offline over archived frames in the 126 test files under `tests/`.

## D2 · The loop is a library, and page and input are the two injected seams

`docs/runner.md:5-14` records the motivation: the loop used to live inside `tools/window_step.py`, a command-line tool that built its own ADB controller, took its own screenshots and sent its own clicks. Nothing else could drive it, and nothing could test it without a device.

The two seams are defined in `src/maalimbus/runner.py`:

```python
class Device(Protocol):          # runner.py:250
    def screencap(self) -> np.ndarray: ...   # BGR, already in the 1920x1080 space
    def click(self, x: int, y: int) -> None: ...
    def swipe(self, x1: int, y1: int, x2: int, y2: int, duration_ms: int) -> None: ...
    def key(self, code: int) -> None: ...    # optional; may raise NotImplementedError
```

Three implementations:

- `MaaDevice(controller, *, wait=None, target_long_side=1920, deadline=None)` (`:272`) — wraps `context.tasker.controller`. Every call posts its job and waits it out before returning, so `click()` returning means the touch landed. Its constructor applies `set_screenshot_target_long_side(target_long_side)`, which is what pins the frame to the recognition space.
- `LocalDevice(...)` (`:321`) — the same mapping for the controller `window_step.py` builds, plus `foreground()` for the summary the CLI prints.
- `FakeDevice(frames=(), foreground=None)` (`:385`) — replays frames and remembers what was sent.

The `Observer` Protocol is at `:549`: one `directory: Path` and `observe(*, deadline=None) -> dict`. `MaaObserver(context, directory=None, *, pipeline='WindowMapObserve', battle_pipeline='WindowBattleObserve')` (`:596`) runs the agent's own recognition node and reads back the page it recorded; `FrameObserver(directory, frames=(), *, index=0, settings=None)` (`:565`) replays archived `frame-*.json` records.

`MirrorRunner` (`:1253`) has the signature:

```python
MirrorRunner(device, *, settings, locale='en', registry=None, store=None,
             directory=None, journal=None, flow=None, log=None,
             observer=None, roots=None, run_id=None, result=None)
```

`step()` (`:1421`) returns `{'page','reason','target','input_sent','event','stopped','done','observation', ...}`, where `stopped` names the condition that ended the window and `observation` is the record the CLI writes into `build/window-debug/<label>/frame-*.json`. `run(*, steps=300, interval=6.0, round_limit=5, deadline=None)` (`:2687`) is the outer loop.

The same loop now has two frontends: the CLI (`tools/window_step.py`) and the app (`MirrorLoopAction`, `agent/recognition.py:1473-1522`). Both build a `MirrorRunner` with an identical set of names — `docs/agent-loop.md:40-48` lists every CLI name that `custom_action_param` accepts.

## D3 · At most one input per page; refuse without evidence

`src/maalimbus/window.py:15-19` writes four rules into the module docstring:

1. a page never sends more than one input per plan;
2. a page with no proven control refuses instead of guessing a coordinate;
3. a click is only accepted when the successor page is one of the expected pages, otherwise the step is recorded as `unexpected_successor` and the window stops;
4. battle turns are submitted only when the game itself shows `START`.

Refusal is `_refuse(page, reason)` (`window.py:106`), which returns a plan with `action='record'` — not an exception, and not a default coordinate. `plan_step()` (`window.py:110`) is the only entry point; `_plan_step()` (`:139`) is the big table.

`window.py` also carries two helpers: `successor_ok(plan, page)` (`:956`) and `step_result(plan, *, sent, before, after, page, frame_changed=False)` (`:976`). And `ANY = '*'` (`:33`) is the expectation sentinel for a dismissal: the successor is proven by **the covered page being gone**, not by which page it uncovered — the overlay's cards walk through many different pages, so no positive list can name them all, but "still the overlay" is a decidable failure.

## D4 · A blacklist of controls that must never be clicked

`FORBIDDEN_CONTROLS` (`src/maalimbus/window.py:50-63`) lists 14 controls. Clicking any of them throws away an in-progress run or an already-earned reward, but their labels are also how the page is identified — so they **stay registered as anchors and are refused as targets**:

```
'resume.halt_button', 'reward_card.cancel_button', 'gift_pick.refuse_button',
'gift_warning.confirm_button', 'entry_confirm.cancel_button', 'level_warning.cancel_button',
'star_confirm.cancel_button', 'initial_gifts.refuse_button', 'gift_search_forgo.cancel_button',
'event_check.skip_button',           # means nobody attempts the roll: forfeits the check outright
'run_reward.give_up_button',         # throws the five-floor run away
'run_reward_confirm.cancel_button',  # dismisses the claim question without claiming
'window_reset.confirm_button',       # the weekly-reset Confirm leaves the dungeon
'expired_session.cancel_button'      # dismissing the expired session leaves its rewards unclaimed
```

The enforcement point is `window.py:128-135`: if a plan's target falls in the blacklist, it is rewritten to a `control_is_forbidden` refusal. There are exactly two explicit exemptions:

- `page == 'STAR_CONFIRM'` with target `star_confirm.cancel_button` and reason `incomplete_graces_return_to_selection`;
- `page == 'GIFT_PICK'` with target `gift_pick.refuse_button` and reason `refuse_proven_owned_single_free_gift`.

## D5 · Persist the intent before input

Every `*_transaction.py` has the same shape: **persist before input, and an unproven postcondition never permits another input**. `shop_transaction.py:1` puts it most plainly: "Reserve before attempting input. A reservation means the action may have happened."

`storage.write_json` (`src/maalimbus/storage.py:24`) uses a unique temporary name (`mkstemp`) plus `flush`, `os.fsync` and `os.replace`, so the previous complete state is always complete. `read_json` (`:40`) carries a 2 MiB default limit; `INTERFACE_LIMIT = 16 * 1024 * 1024` (`:21`) exists because the ProjectInterface carries the option table for every identity (3.4 MiB of `interface.json`).

Correspondingly, `run_wiring.settle()` (`src/maalimbus/run_wiring.py:81`) does not raise when the ledger refuses an event (`ValueError`) — it reports it through `on_refusal` and then **ends the loop**, because the ledger is the authority and the loop may not walk around it. It also stops when `store.record()` returns `fresh == False` (the identical observation is already on the ledger), since asking again would only repeat it.

## D6 · The ledger accepts only what a page can actually prove

`run_wiring.ledger_event()` (`src/maalimbus/run_wiring.py:41`) is a pure function: it takes a page name plus the current ledger state and returns what the page settles, or `None`. Three derivations are implemented:

- A map page that reads floor *n* proves floor *n-1* was cleared (`run_wiring.py:51-55`). Floor 1 proves nothing.
- The run summary (`RUN_CLAIM`, "Exploration Complete" at 100%) is the final victory, but only once all five floors are on the ledger (`:56-67`), because the summary itself is drawn from the whole run. The comment keeps the reason this matters: `build/window-run-continue-2.json` reached RUN_CLAIM (steps 52-55) and recorded nothing, so the rotation never moved.
- A completed run spending one weekly bonus can only be authorised by "this claim is this run's own payout" (`earned_its_payout()`, `:208`). The comment keeps the counter-example too: a ledger written before receipts carried `settled_at` cannot say which settled last, so it returns `False` — not knowing is not a reason to spend a weekly resource (there are only three, they reset weekly and do not carry over; Steam discussion 597403944640085425).

Two further entry points handle "the game threw the run away":

- `expire()` (`:129`) — when the weekly reset expires the session ("The previous session has expired. / Please claim your rewards.", live `evidence/runtime/window-20261007-170653/frame-0009.json`), confirming that page is the input that claims the leftover rewards, so the run is filed as abandoned; the rotation stays on the same team for the next attempt, and the abandoned entry keeps the floors it reached plus the frame that proved it.
- `reconcile()` (`:156`) — the loadout picker is drawn only for a *new* dungeon; a run still in progress answers with the Dungeon Progress dialog (`Resume` / `Halt Exploration`, live `evidence/runtime/window-20261006-025617/frame-0002.json`). So reaching the picker while the ledger still calls a run active means the game no longer has it. There is one hard constraint here: `phase == 'entry_pending'` raises `ValueError('Entry confirmation pending; do not discard or retry')` (`:179`). There is also one special case: if the run is already `victory` + `reward` and only the walk back is missing, recording an `entry_returned` receipt at the picker is worth more than throwing the run away (`:183-197`).

## D7 · An input is not a receipt

`run_wiring.ledger_event()` returns `None` for three pages (`:68-77`): the reward confirm page (`RUN_REWARD_CONFIRM`), the weekly-bonus question (`RUN_REWARD_BONUS`), and the team page before a `reward` exists (`DUNGEON_TEAM`). The reason is in the comments: only a separate, verified receipt/balance transaction may credit payout.

This corroborates `docs/design.md:358-371` ("Claim and weekly-bonus Confirm are inputs, not reward_received events") and is enforced by `src/maalimbus/reward_receipt_audit.py:1` ("read-only final payout proof; inputs and task success never imply receipt"). The same principle appears in `src/maalimbus/paid_reward_action.py:1` ("one freshly identified, durable reward control; never credits payout on input") and `src/maalimbus/run_summary.py:1` ("an independent completed Hard run summary, never a payment receipt").

## D8 · Private state is decoupled from cwd and PyInstaller extraction

`src/maalimbus/runtime_paths.py:8` gives `application_root(*, executable=None, frozen=None, source_file=None, override=None)` three routes:

- an explicit `override` wins;
- when frozen, the **grandparent** directory of the executable (`Path(executable or sys.executable).resolve().parents[1]`, `:15`) — the comment notes that both Agent and Runner live in an immediate subdirectory of the app;
- otherwise the grandparent directory of the source file (`:16`).

The module-level `ROOT` (`:19`) ignores `MAALIMBUS_ROOT` when frozen and only reads it when not frozen.

`data_directory(root=ROOT)` (`:23`) redirects private state when `config/user-data-root.json` exists, with three guards on the redirected directory:

| Check | Error raised on failure |
| --- | --- |
| must be an absolute path that is an existing directory | `Private-state directory is unavailable` |
| the target and every ancestor must not be a symlink or junction | `Linked private-state directory` |
| the target must not itself contain `user-data-root.json` | `Chained private-state binding` |

And the marker file is validated before use: its key set must be exactly `{'version', 'directory'}` with `version == 1`, else `Invalid private-state binding` (`:30-31`).

`ledger_path(value, root=ROOT)` (`:43`) is the single interpreter for ledger paths: an absolute path is used as is; a relative path starting with `config` goes through `data_directory()` and raises `Unsafe private ledger path` if `..` appears; anything else resolves against the application root.

## D9 · One controller, one cross-process OS lock

`src/maalimbus/controller_lease.py:1` is "One OS lock shared by native CLI and packaged Agent entry points". `PROJECT.md:1344` lists "One controller, bounded session, finite node hits" as part of the development contract. A measured consequence: `PROJECT.md:71-74` records that two failing tests were exactly the case of a real running app holding `%LOCALAPPDATA%/MaaLimbus/controller.lock` (`lease_path` redirects every `controller.lock` there), and they clear when no app is running.

## D10 · Why observation nodes must go through `Context.run_task`

`docs/agent-loop.md:93-103` records the incident and the fix: `MaaObserver` runs its node by calling `tasker.post_task(name)`, and inside a custom action that cannot be `context.tasker` — the framework's task runner is a single worker, so a node posted there queues behind **the very task that is waiting for it**. The wait then hits its deadline, and the framework's error path stops the running task, which is this run.

So the action hands `MaaObserver` an `AgentTasker` proxy (`agent/recognition.py:1421`), which is both the context (`.tasker` is itself) and the tasker (`post_task` → `Context.run_task`), running the sub-task synchronously on the calling thread.

`docs/agent-loop.md:22-27` records one more easily-missed semantic: `MirrorLoop` is `{"recognition": "DirectHit", "action": "Custom", ...}`, so its `400000` timeout only bounds the instant `DirectHit` step into `MirrorLoopDone`; what actually stops the whole run is the run's own `budget`. `on_error` is empty because a run that fails reports through its own journal instead of the pipeline.

## D11 · The PI Win32 profile is the only controller truth

`src/maalimbus/windows_controller.py:9`'s `controller_profile(interface_path, name)` finds the unique `type == 'Win32'` controller in `assets/interface.json` matching `name`, and raises `Unknown Windows controller: {name}` when the match count is not 1. `native_methods(profile)` (`:17`) maps the three strings `screencap`/`mouse`/`keyboard` onto `MaaWin32ScreencapMethodEnum` / `MaaWin32InputMethodEnum`. `DEFAULT_CONTROLLER = 'windows-window'` (`:6`).

The three Win32 profiles plus one Adb profile in the PI (`assets/interface.json:16/31/46/61`):

| Name | Line | screencap | mouse | keyboard |
| --- | --- | --- | --- | --- |
| `windows-window` | `interface.json:16` | `Background` | `SendMessageWithCursorPos` | `PostMessage` |
| `windows-background` | `interface.json:31` | `Background` | `SendMessageWithWindowPos` | `PostMessage` |
| `windows` | `interface.json:46` | `ScreenDC` | `Seize` | `Seize` |
| `mumu-adb` | `interface.json:61` | (`"adb": {}`, auto-detected by the toolkit) | — | — |

All four profiles write `display_long_side: 1920`, and all three `windows*` profiles write `permission_required: true` (`interface.json:20/35/50`). `docs/maaframework-conformance.md:97-102` checks that table rule by rule against `3.3-ProjectInterfaceV2协议.md`, and notes that it matches the official Win32 example method for method (`:102`).

The ADB side is stricter than the framework requires: `src/maalimbus/adb_device.py:1` says discovery goes through `Toolkit.find_adb_devices(adb_path)`, and that input is only ever sent when discovery offered EmulatorExtras (MuMu 12 serves the touch through the host, which is what once moved the user's mouse); read-only passes build the same controller with `MaaAdbInputMethodEnum.Null`. That policy is this project's own choice.

## D12 · What may not be an anchor

`PROJECT.md:1341` writes this as a contract: dungeon artwork, season number, currency amount and full-screen background are not anchors.

`docs/design.md:219-222` gives the concrete reading for the map page: the map page is identified **by text only** — the localized `Exploring` / `Before Entry` floor header inside the upper-left band, plus the theme-pack line directly beneath it; the pack line must sit in its own band and must not repeat the floor pattern; a page carrying similar wording elsewhere is never promoted; node artwork, cover art, season icons and currency amounts are not anchors.

`src/maalimbus/vision.py:1` abstracts it into one line: "Text + normalized position; artwork and currency are never scene anchors." The default recognition threshold is `.65` (`vision.py:19`), while narrow native reads use `.9`/`.95` (`docs/design.md:69-70`, `:376`).

`docs/design.md:199-213` also leaves an **unproven inference**, which belongs in "open questions" rather than in the architecture facts: the pinned LALC 431b432 keeps two trained classifiers (`mirror_legend`, eight node classes; `mirror_path`, nine `00..22` cells), masks and graffiti-fills those regions before inference, and `tools/compare_lalc_map_regions.py` sampling the retained floor-1 page finds LALC's six slots in the dark upper-left quadrant while the drawn nodes occupy a wider area — so LALC's coordinates are not this page's node coordinates, node identity stays unproven, and route stays a refusal. `docs/design.md:225-230` states the condition under which routing is actually allowed: the page is an identified map, **and** a single current-position marker is proven, **and** exactly one unvisited candidate remains; otherwise no click target is produced and only the reason is recorded.

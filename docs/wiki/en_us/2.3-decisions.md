## D1 · Maa owns the device, Python owns the judgement

`PROJECT.md:1338-1339` writes this out as a development contract: Maa owns screenshots/input and bounded Pipeline scheduling, pure Python ranks the choices, and the Agent returns recognition boxes and state updates. The direct consequence is that `maa` appears only in a few boundary modules, and mostly deferred to the call site: measured, the files that import `maa` **at module top level** number five — `src/maalimbus/adb_device.py:15-17` (`AdbController` / `MaaAdbInputMethodEnum` / `Toolkit`), `src/maalimbus/battle_counter_native.py:3`, `src/maalimbus/deployment_availability_native.py:7`, `src/maalimbus/floor_trial_vision.py:3`, `src/maalimbus/shop_native.py:3` — while six more import it inside a function body: `windows_controller.native_methods()` (`src/maalimbus/windows_controller.py:18`), `src/maalimbus/neural_shadow.py:132`, `src/maalimbus/reward_cost.py:39`, `src/maalimbus/overlay_dismissal.py:28`, `src/maalimbus/owned_inventory.py:113` and `:128`, and `src/maalimbus/deployment_numbers_native.py:7`. That is what lets the great majority of the judgement be replayed offline over archived frames in the 128 `tests/*.py` files.

## D2 · The loop is a library, and page and input are the two injected seams

`docs/runner.md:5-14` records the motivation: the loop used to live inside `tools/window_step.py`, a command-line tool that built its own ADB controller, took its own screenshots and sent its own clicks. Nothing else could drive it, and nothing could test it without a device.

The two seams are defined in `src/maalimbus/runner.py`:

```python
class Device(Protocol):          # runner.py:251
    def screencap(self) -> np.ndarray: ...   # BGR, already in the 1920x1080 space
    def click(self, x: int, y: int) -> None: ...
    def swipe(self, x1: int, y1: int, x2: int, y2: int, duration_ms: int) -> None: ...
    def key(self, code: int) -> None: ...    # optional; may raise NotImplementedError
```

Three implementations:

- `MaaDevice(controller, *, wait=None, target_long_side=1920, deadline=None)` (`:273`) — wraps `context.tasker.controller`. Every call posts its job and waits it out before returning, so `click()` returning means the touch landed. Its constructor applies `set_screenshot_target_long_side(target_long_side)`, which is what pins the frame to the recognition space.
- `LocalDevice(...)` (`:323`) — the same mapping for the controller `window_step.py` builds, plus `foreground()` for the summary the CLI prints.
- `FakeDevice(frames=(), foreground=None)` (`:387`) — replays frames and remembers what was sent.

The `Observer` Protocol is at `:551`: one `directory: Path` and `observe(*, deadline=None) -> dict`. `MaaObserver(context, directory=None, *, pipeline='WindowMapObserve', battle_pipeline='WindowBattleObserve')` (`:598`) runs the agent's own recognition node and reads back the page it recorded; `FrameObserver(directory, frames=(), *, index=0, settings=None)` (`:567`) replays archived `frame-*.json` records.

`MirrorRunner` (`:1277`) has the signature:

```python
MirrorRunner(device, *, settings, locale='en', registry=None, store=None,
             directory=None, journal=None, flow=None, log=None,
             observer=None, roots=None, run_id=None, result=None)
```

`step()` (`:1436`) returns `{'page','reason','target','input_sent','event','stopped','done','observation', ...}`, where `stopped` names the condition that ended the window and `observation` is the record the CLI writes into `build/window-debug/<label>/frame-*.json`. `run(*, steps=300, interval=6.0, round_limit=5, deadline=None)` (`:2756`) is the outer loop.

The same loop now has two frontends: the CLI (`tools/window_step.py`) and the app (`MirrorLoopAction`, `agent/recognition.py:1526-1575`). Both build a `MirrorRunner` with an identical set of names — `docs/agent-loop.md:40-48` lists every CLI name that `custom_action_param` accepts.

## D3 · At most one input per page; refuse without evidence

`src/maalimbus/window.py:15-19` writes four rules into the module docstring:

1. a page never sends more than one input per plan;
2. a page with no proven control refuses instead of guessing a coordinate;
3. a click is only accepted when the successor page is one of the expected pages, otherwise the step is recorded as `unexpected_successor` and the window stops;
4. battle turns are submitted only when the game itself shows `START`.

Refusal is `_refuse(page, reason)` (`window.py:106`), which returns a plan with `action='record'` — not an exception, and not a default coordinate. `plan_step()` (`window.py:110`) is the only entry point; `_plan_step()` (`:139`) is the big table.

`window.py` also carries two helpers: `successor_ok(plan, page)` (`:1032`) and `step_result(plan, *, sent, before, after, page, frame_changed=False)` (`:1052`). And `ANY = '*'` (`:33`) is the expectation sentinel for a dismissal: the successor is proven by **the covered page being gone**, not by which page it uncovered — the overlay's cards walk through many different pages, so no positive list can name them all, but "still the overlay" is a decidable failure.

## D4 · A blacklist of controls that must never be clicked

`FORBIDDEN_CONTROLS` (`src/maalimbus/window.py:50-63`) lists 14 controls. Clicking any of them throws away an in-progress run or an already-earned reward, but their labels are also how the page is identified — so they **stay registered as anchors and are refused as targets**:

```
'resume.halt_button', 'reward_card.cancel_button', 'gift_pick.refuse_button',
'gift_warning.confirm_button', 'entry_confirm.cancel_button', 'level_warning.cancel_button',
'star_confirm.cancel_button', 'initial_gifts.refuse_button', 'gift_search_forgo.cancel_button',
'event_check.skip_button',           # means nobody attempts the roll: forfeits the check outright
'run_reward.give_up_button',         # throws the five-floor run away
'run_reward_confirm.cancel_button',  # dismisses the claim question without claiming
'window_reset.confirm_button',       # the weekly-reset Confirm leaves the dungeon
'expired_session.cancel_button'      # dismissing the expired session leaves its rewards unclaimed
```

The enforcement point is `window.py:128-135`: if a plan's target falls in the blacklist, it is rewritten to a `control_is_forbidden` refusal. There are exactly two explicit exemptions:

- `page == 'STAR_CONFIRM'` with target `star_confirm.cancel_button` and reason `incomplete_graces_return_to_selection`;
- `page == 'GIFT_PICK'` with target `gift_pick.refuse_button` and reason `refuse_proven_owned_single_free_gift`.

## D5 · Persist the intent before input

Every `*_transaction.py` has the same shape: **persist before input, and an unproven postcondition never permits another input**. `shop_transaction.py:1` puts it most plainly: "Reserve before attempting input. A reservation means the action may have happened."

`storage.write_json` (`src/maalimbus/storage.py:24`) uses a unique temporary name (`mkstemp`) plus `flush`, `os.fsync` and `os.replace`, so the previous complete state is always complete. `read_json` (`:40`) carries a 2 MiB default limit; `INTERFACE_LIMIT = 16 * 1024 * 1024` (`:21`) exists because the ProjectInterface carries the option table for every identity (3.4 MiB of `interface.json`).

Correspondingly, `run_wiring.settle()` (`src/maalimbus/run_wiring.py:81`) does not raise when the ledger refuses an event (`ValueError`) — it reports it through `on_refusal` and then **ends the loop**, because the ledger is the authority and the loop may not walk around it. It also stops when `store.record()` returns `fresh == False` (the identical observation is already on the ledger), since asking again would only repeat it.

## D6 · The ledger accepts only what a page can actually prove

`run_wiring.ledger_event()` (`src/maalimbus/run_wiring.py:41`) is a pure function: it takes a page name plus the current ledger state and returns what the page settles, or `None`. Three derivations are implemented:

- A map page that reads floor *n* proves floor *n-1* was cleared (`run_wiring.py:51-55`). Floor 1 proves nothing.
- The run summary (`RUN_CLAIM`, "Exploration Complete" at 100%) is the final victory, but only once all five floors are on the ledger (`:56-67`), because the summary itself is drawn from the whole run. The comment keeps the reason this matters: `build/window-run-continue-2.json` reached RUN_CLAIM (steps 52-55) and recorded nothing, so the rotation never moved.
- A completed run spending one weekly bonus can only be authorised by "this claim is this run's own payout" (`earned_its_payout()`, `:208`). The comment keeps the counter-example too: a ledger written before receipts carried `settled_at` cannot say which settled last, so it returns `False` — not knowing is not a reason to spend a weekly resource (there are only three, they reset weekly and do not carry over; Steam discussion 597403944640085425).

Two further entry points handle "the game threw the run away":

- `expire()` (`:129`) — when the weekly reset expires the session ("The previous session has expired. / Please claim your rewards.", live `evidence/runtime/window-20261007-170653/frame-0009.json`), confirming that page is the input that claims the leftover rewards, so the run is filed as abandoned; the rotation stays on the same team for the next attempt, and the abandoned entry keeps the floors it reached plus the frame that proved it.
- `reconcile()` (`:156`) — the loadout picker is drawn only for a *new* dungeon; a run still in progress answers with the Dungeon Progress dialog (`Resume` / `Halt Exploration`, live `evidence/runtime/window-20261006-025617/frame-0002.json`). So reaching the picker while the ledger still calls a run active means the game no longer has it. There is one hard constraint here: `phase == 'entry_pending'` raises `ValueError('Entry confirmation pending; do not discard or retry')` (`:179`). There is also one special case: if the run is already `victory` + `reward` and only the walk back is missing, recording an `entry_returned` receipt at the picker is worth more than throwing the run away (`:183-197`).

## D7 · An input is not a receipt

`run_wiring.ledger_event()` returns `None` for three pages (`:68-77`): the reward confirm page (`RUN_REWARD_CONFIRM`), the weekly-bonus question (`RUN_REWARD_BONUS`), and the team page before a `reward` exists (`DUNGEON_TEAM`). The reason is in the comments: only a separate, verified receipt/balance transaction may credit payout.

This corroborates `docs/design.md:358-371` ("Claim and weekly-bonus Confirm are inputs, not reward_received events") and is enforced by `src/maalimbus/reward_receipt_audit.py:1` ("read-only final payout proof; inputs and task success never imply receipt"). The same principle appears in `src/maalimbus/paid_reward_action.py:1` ("one freshly identified, durable reward control; never credits payout on input") and `src/maalimbus/run_summary.py:1` ("an independent completed Hard run summary, never a payment receipt").

## D8 · Private state is decoupled from cwd and PyInstaller extraction

`src/maalimbus/runtime_paths.py:8` gives `application_root(*, executable=None, frozen=None, source_file=None, override=None)` three routes:

- an explicit `override` wins;
- when frozen, the **grandparent** directory of the executable (`Path(executable or sys.executable).resolve().parents[1]`, `:15`) — the comment notes that both Agent and Runner live in an immediate subdirectory of the app;
- otherwise the grandparent directory of the source file (`:16`).

The module-level `ROOT` (`:19`) ignores `MAALIMBUS_ROOT` when frozen and only reads it when not frozen.

`data_directory(root=ROOT)` (`:23`) redirects private state when `config/user-data-root.json` exists, with three guards on the redirected directory:

| Check | Error raised on failure |
| --- | --- |
| must be an absolute path that is an existing directory | `Private-state directory is unavailable` |
| the target and every ancestor must not be a symlink or junction | `Linked private-state directory` |
| the target must not itself contain `user-data-root.json` | `Chained private-state binding` |

And the marker file is validated before use: its key set must be exactly `{'version', 'directory'}` with `version == 1`, else `Invalid private-state binding` (`:30-31`).

`ledger_path(value, root=ROOT)` (`:43`) is the single interpreter for ledger paths: an absolute path is used as is; a relative path starting with `config` goes through `data_directory()` and raises `Unsafe private ledger path` if `..` appears; anything else resolves against the application root.

## D9 · One controller, one cross-process OS lock

`src/maalimbus/controller_lease.py:1` is "One OS lock shared by native CLI and packaged Agent entry points". `PROJECT.md:1344` lists "One controller, bounded session, finite node hits" as part of the development contract. A measured consequence: `PROJECT.md:71-74` records that two failing tests were exactly the case of a real running app holding `%LOCALAPPDATA%/MaaLimbus/controller.lock` (`lease_path` redirects every `controller.lock` there), and they clear when no app is running.

## D10 · Why observation nodes must go through `Context.run_task`

`docs/agent-loop.md:93-103` records the incident and the fix: `MaaObserver` runs its node by calling `tasker.post_task(name)`, and inside a custom action that cannot be `context.tasker` — the framework's task runner is a single worker, so a node posted there queues behind **the very task that is waiting for it**. The wait then hits its deadline, and the framework's error path stops the running task, which is this run.

So the action hands `MaaObserver` an `AgentTasker` proxy (`agent/recognition.py:1410`), which is both the context (`.tasker` is itself) and the tasker (`post_task` → `Context.run_task`), running the sub-task synchronously on the calling thread.

`docs/agent-loop.md:22-27` records one more easily-missed semantic: `MirrorLoop` is `{"recognition": "DirectHit", "action": "Custom", ...}`, so its `400000` timeout only bounds the instant `DirectHit` step into `MirrorLoopDone`; what actually stops the whole run is the run's own `budget`. `on_error` is empty because a run that fails reports through its own journal instead of the pipeline.

## D11 · The PI Win32 profile is the only controller truth

`src/maalimbus/windows_controller.py:9`'s `controller_profile(interface_path, name)` finds the unique `type == 'Win32'` controller in `assets/interface.json` matching `name`, and raises `Unknown Windows controller: {name}` when the match count is not 1. `native_methods(profile)` (`:17`) maps the three strings `screencap`/`mouse`/`keyboard` onto `MaaWin32ScreencapMethodEnum` / `MaaWin32InputMethodEnum`. `DEFAULT_CONTROLLER = 'windows-window'` (`:6`).

The three Win32 profiles plus one Adb profile in the PI (`assets/interface.json:16/31/46/61`):

| Name | Line | screencap | mouse | keyboard |
| --- | --- | --- | --- | --- |
| `windows-window` | `interface.json:16` | `Background` | `SendMessageWithCursorPos` | `PostMessage` |
| `windows-background` | `interface.json:31` | `Background` | `SendMessageWithWindowPos` | `PostMessage` |
| `windows` | `interface.json:46` | `ScreenDC` | `Seize` | `Seize` |
| `mumu-adb` | `interface.json:61` | (`"adb": {}`, auto-detected by the toolkit) | — | — |

All four profiles write `display_long_side: 1920`, and all three `windows*` profiles write `permission_required: true` (`interface.json:20/35/50`). `docs/maaframework-conformance.md:97-102` checks that table rule by rule against `3.3-ProjectInterfaceV2协议.md`, and notes that it matches the official Win32 example method for method (`:102`).

The ADB side is stricter than the framework requires: `src/maalimbus/adb_device.py:1` says discovery goes through `Toolkit.find_adb_devices(adb_path)`, and that input is only ever sent when discovery offered EmulatorExtras (MuMu 12 serves the touch through the host, which is what once moved the user's mouse); read-only passes build the same controller with `MaaAdbInputMethodEnum.Null`. That policy is this project's own choice.

## D12 · What may not be an anchor

`PROJECT.md:1341` writes this as a contract: dungeon artwork, season number, currency amount and full-screen background are not anchors.

`docs/design.md:219-222` gives the concrete reading for the map page: the map page is identified **by text only** — the localized `Exploring` / `Before Entry` floor header inside the upper-left band, plus the theme-pack line directly beneath it; the pack line must sit in its own band and must not repeat the floor pattern; a page carrying similar wording elsewhere is never promoted; node artwork, cover art, season icons and currency amounts are not anchors.

`src/maalimbus/vision.py:1` abstracts it into one line: "Text + normalized position; artwork and currency are never scene anchors." The default recognition threshold is `.65` (`vision.py:19`), while narrow native reads use `.9`/`.95` (`docs/design.md:69-70`, `:376`).

`docs/design.md:199-213` also leaves an **unproven inference**, which belongs in "open questions" rather than in the architecture facts: the pinned LALC 431b432 keeps two trained classifiers (`mirror_legend`, eight node classes; `mirror_path`, nine `00..22` cells), masks and graffiti-fills those regions before inference, and `tools/compare_lalc_map_regions.py` sampling the retained floor-1 page finds LALC's six slots in the dark upper-left quadrant while the drawn nodes occupy a wider area — so LALC's coordinates are not this page's node coordinates, node identity stays unproven, and route stays a refusal. `docs/design.md:225-230` states the condition under which routing is actually allowed: the page is an identified map, **and** a single current-position marker is proven, **and** exactly one unvisited candidate remains; otherwise no click target is produced and only the reason is recorded.

## D13 · A dialog's answer is the state word it changes to, not the explanatory row inside it

The shop's `Heal Sinners` dialog draws each of the three ways to spend 100 as a numbered row with its own price. The rows were clicked one by one on the live game: the third row's title `[1246,246,570,41]`, its `100` badge and the inner `Revive Selected Sinner` all change nothing (the counter stays at 3093, the frame is static), and clicking the already-picked portrait again *undoes* the pick (yellow outline 227px → 0, `window-20261012-214600`). What actually works is the modal's bottom-right button, whose **word changes with the state**: `Return` while the three options are shown, `Select` once a Sinner is picked, `Leave` once the revive is done (the three boxes are `[1610,941,172,55]`, `[1614,937,166,61]` and `[1622,943,150,53]`).

So `modal_bottom_control(records, patterns)` at `src/maalimbus/shop_revive.py:220` does exactly one thing: inside the fixed band `CONFIRM_X=(1560,1860)` × `CONFIRM_Y=(900,1010)` (`:216-217`) it looks for **exactly one** token scoring at least `.9` that matches the word list the caller passed; two hits or none return `None`, and the plan at `src/maalimbus/window.py:589-593` then `_refuse`s. The word list comes from the localisation dictionary (`assets/resource/en/locale.json:71` for `leave`, `:74` for `select`), never from a hardcoded string.

The general part: **the explanatory rows in a dialog are display, not controls.** An implementation that clicks by row text shows up as "clicked but nothing happened", while this window shows up as a refusal — the log difference is `the_modals_own_button_answers_the_pick_the_bar_made` versus a `_refuse` reason string.

## D14 · Title matching for the same card tolerates OCR confusables; the receipt tolerates nothing

On the live shop `window-20261012-221212` the shelf read `Today's Expression` as `Today's Expresslon` (`i`→`l`): the shop's own counter had already moved 2993 → 2804 (a difference of 189, exactly that card's price), but exact title matching left "which card was bought" empty, so `reconcile_purchase` raised `Independent complete successor shelf not proven` at `src/maalimbus/shop_transaction.py:431` and stopped the window. That stop is not a false alarm: it refuses to treat a card it could not read as some other card.

The fix adds a confusable fold to the comparison instead of loosening it into a fuzzy match: `_CONFUSABLE` (`shop_transaction.py:44`, `i/l/1/!/|→1`, `o→0`, the several apostrophes→`'`) with `_fold` / `_same_title` (`:48`, `:52`), applied at the four comparisons (`still`, `bought`, `prior`, and the successor shelf's `remaining`). It is explicitly **not** a fuzzy match — a card whose title really differs is still refused (the `Orach` case in `tests/test_shop_transaction.py`), and the receipt still requires the card's own `Purchased` badge plus the exact coin delta (`:458`). Evidence: that file at 45 passed, and the live `window-20261012-221631` booking the purchase as `Today's Expression` 189.

**Continued (2026-10-16): the page-identity side counts differing positions instead of listing them.** Item 8 below used to be the honest expectation — a confusable nobody had seen would stop the window in exactly the same way — and the next live run collected on it. `pi-20261016-011659` resumed the reservation `pi-20261015-214921` had left behind, its successor shelf read that page's own `Voodoo Doll` as `Vaodoo Doll` (same slot, same 149, same visit), and the check at `src/maalimbus/shop_transaction.py:553` — which refuses a successor showing a card the shelf never held — called it a different page and stopped the run at zero inputs. `a` and `o` are one bowl apart in that typeface.

The page-identity side now asks `_one_glyph_apart` (`src/maalimbus/shop_transaction.py:73`) through `held_offer` (`:541`): equal length, folded keys differing in exactly one position, and the same price. Enumerating pairs has to be repeated for every new pair; counting positions does not. What the tolerance cannot do is unchanged: it never names a purchase (the bought card is still matched by `_same_title`, and the receipt still needs the badge plus the exact delta), a title cannot shorten, and a different price is not the same row. Evidence: `tests/test_shop_transaction.py::test_a_neighbouring_slot_read_with_one_glyph_of_noise_is_still_the_same_page`, `::test_one_glyph_of_noise_is_not_a_licence_to_shorten_or_repricing`, and the live replay `::test_the_live_resumed_purchase_across_runs_is_receipted`.

## D15 · The map's "this step is walkable" mark is read by its colour, not by a badge bitmap stored from one floor

Live run `pi-20261021-185251` (started 2026-10-21 18:52): on floor 1, `Dregs of the Manor`, `candidates_of` (`src/maalimbus/runner.py:857`) handed the runner four candidates only — the player's own icon, a path chevron, and two lattice guesses inside the empty black panel to the right of the map. All four were clicks on nothing; after `window_map_retry` walked `remaining` down to 0 the run stopped with `no_candidate_node_observed`, with all 48 inputs spent.

What that page really marks as walkable are five gold rings (`frame-0119.png`, at (863,404), (1055,403), (1247,403), (1247,564) and (1055,723)), each 24 px across in BGR (21,140,223), sitting on the top edge of the node they belong to — while `node_badge_template()`'s stored bitmap matched none of them on that floor, so the whole badge channel was empty.

`gold_marks` (`src/maalimbus/map_vision.py:880`) now reads the rings by hue, saturation and brightness, `gold_badge_drop` (`:916`) lifts each onto its node (+44 px, measured: the ring at (863,404), the hexagon centred at (863,448)), and the candidate kind is `gold_badge_node` (`:1097-1100`). It ranks behind the walked path, the lit ring and the lit icon, and ahead of the neutral outline, the badge lift and the lattice; it used to be gated on `node_markers` reading nothing at all -- **that gate has been refuted by a live run, see the second continuation below**: it made one whole run spend nine click retries on the right-hand button column and stop on `unexpected_successor`.

## D22 A label has to be written where the input is actually sent (2026-10-22)

A scoring rule is only as good as the labels it can produce. The first version recorded "which
candidate this click was aimed at" on the **retry branch that runs after a click failed**, so a run
whose clicks all worked recorded zero `map_click_result` events out of 202 — not because nothing was
clicked, but because the success path never reached the recorder.

`src/maalimbus/runner.py` now records `state['map_pending']` immediately before the real
`self.device.click(*point)`, next to `window_intent`. Every map click in every run is therefore
judged `accepted` / `rejected` / `party_moved` on the next observation, per run, and a whole run can
be held out.

This is not "a log added for training"; it is the precondition of the comparison. Without a held-out
run's own click outcomes, any claim that the model is more accurate than the rule is proved either on
its own training frames or against labels the rule itself produced.

## D24 Observing without moving is a second kind of wedge (2026-10-22)

### D27 Three submits from one turn mean the board is refusing, so stop resending

The old "the click was swallowed" test required `plan.advance` and a successor page from the plan's `expect`. Battle submits default to `advance=False` (`_plan` in `src/maalimbus/window.py:91`), and their `expect` already holds `BATTLE_HUD`, `BATTLE_PLANNING` and `UNKNOWN`. Together that means a board that ignored the click and a board that accepted it are indistinguishable at the page level, so the swallowed verdict could never fire and the loop counted an ignored submit as success.

The one fact that separates them is the HUD's own `turn`, read every frame. The rule is now: a second submit from the same `turn` after more than 25 s (a real turn was measured at 43 s) records `battle_submit_not_accepted`; three submits from one `turn` record `battle_submit_ignored_repeatedly` and clear `turn_wait_until`, which hands the page back to the progress watchdog so the run enters recovery with a recorded cause instead of re-clicking an unfed board forever.

The judgement is `submit_was_ignored()`, pinned by six assertions: same turn past the window is true, a moved turn is false, inside the window is false, nothing submitted yet is false, an unread turn is false, and whitespace alone still counts as the same turn.

### D28 A dot where the space should be is page identity, not typography: `Exploring·Floor` is still the map

### D29 Whether a node can be walked to lives in the edge's brightness, not in the node's look

Live testing killed three hypotheses in order: the small gold badge sits on every node and does not mean walkable (four badged nodes on floor 3, every adb tap inert); tapping "adjacent" nodes is equally inert; and the real boundary is the **edge's brightness** -- bright cyan edges can be walked, grey ones cannot, plainly visible in `build/t94-now.png`.

The repository already had this rule: `path_end(image, player)` walks the bright cyan edge from the party to its far end, `advance_candidates(markers, player)` takes the neighbouring nodes, and `map_clicks` even has a `cyan_node` kind. All of them depend on `node_markers`, which template-matches the crescent badge under a node and returns **0** on this palette, so the whole cyan path route was dead and only the two kinds that cannot work -- badges and bright spots -- were offered.

On the same floor, feeding `path_end` the now-located party (`player_by_ring` yields `(972,428)`) still returns `None`, so the defect is not only at the entry point: the cyan-edge reading itself does not hold on this palette either.

Conclusion: the correct source of map candidates is "the nodes connected to the party by a lit edge", which needs a node set and an edge reading that do not depend on a template. Until that exists, reordering, retuning a radius or moving the click point are all patches applied downstream of the defect.

Addendum (measured on the same floor): the walkable cyan edge is not bright but **high-saturation and dark** -- HSV `H~95-98, S~220-250, V~13-55`, so a `V>=120` mask finds not one pixel, which is one direct reason `path_end` returns `None` on that frame. Sampling a +-5 px window along the straight line from the party to each node does not separate walkable from not (all five nodes score 0.81-1.0) because the background lattice lines are cyan as well; the discrimination has to be local to **that edge** -- a narrow perpendicular sample -- compared against the grey edges of the same floor.

### D30 A floor is wider than the viewport: panning is part of reading, not a recovery extra

## D36 (2026-10-23) A run has exactly one ending, and it must be readable

**Why.** Several live runs shared one shape: `stop_reason: null`, a killed process, or the loop turning silently for minutes. The journal showed only "nothing new happened", never who stopped the run or why.

**Decision.** Endings are one table, each with fields a reader can search:

| Ending | Written by | Fields |
|---|---|---|
| the loop judges a page failure | `runner._end_session` | `mirror_loop_stopped.reason` |
| 40 waiting steps, no new page | `wait_decision` | `loop_waited` + `the_loop_waited_without_a_new_page` |
| past the caller's budget | between-steps check | `loop_deadline_exceeded` |
| watchdog expiry | `stall_watchdog` | `window_no_progress` (clamped to the budget) |
| controller lost under a click | `jobs.InputLost` | `the_controller_was_lost_before_the_next_input` |
| killed from outside at its budget | the harness | `the_budget_ended_the_run` (plus `note`) |

**Two constraints that may not be traded away.** A slow click and a lost controller are different states: the first is soft while the screen still answers (a long transition legitimately outlives the job deadline), the second stops the run instead of clicking into an empty handle. And a watchdog may not outlive the budget it protects, nor buy a grace window once clamped — otherwise the budget is not a budget.

**Limit.** The table does not cover "the screen still answers, yet the framework rejects the click with an empty `controller_id`": live evidence aligns it with the `RESUME_DIALOG` click, and the cause is still open. Such a state is bounded only by the budget, not by itself.

## D37 (2026-10-23) A read may not outlive its bound, and a watchdog writes the ending

**Why.** Five consecutive runs on 2026-10-23 (15:33, 15:47, 16:07, 16:17, 16:32 — `packaged-mirror-20261023-153338` … `163257`) ended identically: `loop_heartbeat step=4 page=DRIVE`, `map_observed RESUME_DIALOG`, `window_intent RESUME_DIALOG`, then **380 s of complete journal silence**, then a single `window_no_progress` and nothing else. `tools/audit_runs.py` over `evidence/runtime` said it for the whole archive: **142 runs, 81 stopped, 51 died without a stop**, and `window_no_progress` was the last event of 16 of those 51.

Two defects shared that shape, and both were already named in D36's table without being enforced:

1. **The budget was advisory for native calls.** It was checked *between* steps. The click was followed by the inline settle read, which passed no deadline and so inherited the run-wide one; a single wedged node read could spend the whole remaining budget and the loop could not interrupt a call already in flight. Commit `7b91b6e` had bounded the module-level `_settle()` the same day and left this second site inside `MirrorRunner.step` alone — the same defect, through the door next to the one that was closed.
2. **The progress watchdog wrote no ending.** The frame watch (`_record_stall`) wrote the canonical `mirror_loop_stopped` before `os._exit(4)`; the progress watch (`_record_no_progress`) wrote only its diagnostic. So the ending that D36's table assigns to `stall_watchdog` did not exist for the watch that actually fired.

**Decision.**
- `MirrorRunner._observe` clamps every read to `ONE_READ_SECONDS = 30.0` (`min` with the run's remaining budget) and stamps `artifacts['reading']` with the phase it entered. A read that overruns now **fails as a read inside the step**, and the loop ends through the ordinary named path (`the_task_raised_before_the_next_input` with `no page for this frame`), not through a watchdog.
- `_reading_report()` turns that stamp into the ending record: `in_flight_phase`, `in_flight_seconds`, and `in_flight: true` while the call is still running (`lasted_seconds` once it returned).
- `_write_ending(stop_path, record)` is the single writer for both watches: `mirror_loop_stopped` with `reason`, `stop_path`, `step`, `page`, `last_event` and the in-flight fields. `'stall_watchdog'` and `'no_progress_watchdog'` are the two `stop_path` values.

**Counter-examples that must keep passing.** A read that *finished* is reported with `lasted_seconds` and `in_flight: false` (a slow read is not a wedge). A loop that keeps producing frames leaves the frame watch alone. A watch is never longer than the run it protects (`jobs.bounded_limit`: 450 s budget clamps a 900 s window to what is left; returns the limit when either side is `None`).

**Limit.** `runner.py` still has one in-step native wait handed only the run deadline — the pipeline-node action at the old line 3412 (`run_node(self.tasker, plan['node'], self.deadline)`), left alone deliberately because a pipeline node may declare its own internal wait. The diagnostic CLI paths (`one_shot_click`, `one_shot_swipe`, `observed_page`, `lux_task`, `reward_task`) also pass their caller's deadline; they are not part of the loop. The rule this decision adds is: **the runner's own read door is bounded**; a second door needs its own reason, not a shared one.

**Evidence** — `tests/test_settle_deadline.py` (9): a runner read is bounded without a caller deadline; a tighter run deadline still wins; a wedged node read returns instead of spending the run; a wedged read ends its run in under 10 s with the failure's name in `mirror_session_ended`. `tests/test_stall_watch.py` (10): the progress watch writes `window_no_progress` then `mirror_loop_stopped(stop_path=no_progress_watchdog)` with `in_flight_phase='settle'`, `page='RESUME_DIALOG'`, `step=4`, `in_flight_seconds > 300`; a finished read is not a wedge; the frame watch names the finished read too; a watch is never longer than its run.

## D38 (2026-10-23) A watch retires with the run it watches

**Why.** `stall_watchdog` is a daemon thread that ends the *process* (`os._exit(4)`) once its heartbeat is stale. Nothing in it knew whether the run it was started for still existed. Measured 2026-10-23: `pytest tests/test_agent_loop.py` passed 18 tests in 5.7 s and returned 0, and the process was then killed **5.7 s later** by a progress watch left over from a run that had already finished — twice, with exit 4 and no summary. The same shape explains part of the 51-of-142 "died without a stop" bucket: `os._exit` writes nothing, and a watch that fires after its run ended has no journal to write into.

A watch is cheap to leave running and impossible to scope: `exit(4)` cannot say "this process died because run X wedged". So the watch has to ask.

**Decision.**
- `stall_watchdog(..., alive=None)` checks `alive()` both before and after each wait; a retired watch returns without writing and without exiting.
- `MirrorRunner._start_stall_watch` keeps the token in `self._watch_live` (a `threading.Event`, set before either thread starts) and passes `alive=live.is_set` to both watches; a second `run()` on the same runner re-arms it.
- `MirrorRunner.run` is now a thin wrapper: `try: return self._walk(...) finally: self._retire_watches()`. The walk moved to `_walk` so the retirement cannot be skipped by any exit path — including an exception the loop does not catch.

**Counter-example that must keep passing.** A watch whose run *is* still live and whose page is frozen still ends the process (`test_the_third_wait_still_ends_the_process`, `test_the_watch_ends_a_loop_that_stopped_producing_frames`). Retirement is about the run being over, never about the stall being inconvenient.

**Limit.** Retirement is checked at the top of each wait cycle, so a watch that is *inside* `on_stall` when the run ends may still finish that record. That is deliberate: the record is evidence, and the exit that follows is now unreachable because `alive()` is re-checked before acting next round — but a wedged `on_stall` would still take the process down. `on_stall` writes files without taking a lock, so the risk is a partial record, not a hang.

## D40 (2026-10-23) An observation that never happened is not a success

**Why.** `tools/recovery_outcome.py` scores a recovery by the page it saw afterwards. `pairs()` yields `(event, None)` when no `window_intent`/`map_click_result` ever followed — the comment there says "no evidence" — and `summarise()` then did:

```python
    entry['changed'] += 1
```

`None != 'MAP'` is true, so **every recovery that asked for no input at all was counted as a change**. ## D43 (2026-10-23) A bound belongs to the door, not to the caller who remembered

**Why.** The same defect came back twice, and both times the fix had landed on one of
two sites. `7b91b6e` bounded the settle *helper* and left the inline settle read in
`MirrorRunner.step` unbounded (five runs on 2026-10-23 15:33-16:32 sat 380 s inside it).
`dea7028` then bounded `MirrorRunner._observe` — the *runner's* door — while
`MaaObserver.observe`, the door `tools/lux_task.py`, `tools/reward_task.py` and the

address: `ONE_READ_SECONDS` was defined 2 900 lines *after* the loop that used it, next
to the diagnostic helper that happened to need it too.

**Decision.** One formula, one place:

```python
def bounded_read(deadline, *, limit=None, clock=time.monotonic):
    limit = ONE_READ_SECONDS if limit is None else float(limit)
    own = clock() + limit
    return own if deadline is None else min(float(deadline), own)
```

- `ONE_READ_SECONDS = 30.0` moves up beside `DEEP_STEP_SECONDS`, where the loop's other
  measured limits live.
- `MaaObserver.observe` clamps **per attempt**, so a retry costs at most one more window
  instead of doubling the call's window, and the call as a whole is bounded by
  `read_tries × ONE_READ_SECONDS`.
- the module-level `observe()` clamps the value it hands *any* `Observer`, so a replay
  observer and a future implementation see the same contract.
- `MirrorRunner._observe` reuses the same helper and now **reports** the read (phase,
  age, `in_flight`) rather than being the read's only bound; `_settle` uses the helper
  instead of spelling the arithmetic a second time.

**Counter-examples.** A caller that asks for less still gets less (the clamp is a
ceiling, never an extension). A `FrameObserver` replay still returns its frame. And the
runner's breadcrumb is not the bound: `test_a_read_is_bounded_with_no_runner_and_no_deadline`
reads through the door with no `MirrorRunner` in existence at all.

**Limit.** Two places deliberately read *outside* the door and are listed rather than
forgotten: `tools/battle_auto_assign.py`, `tools/battle_step.py`, `tools/map_advance.py`

## D46. A bound belongs to every door, and an action is not a read

**Why.** D37 and D43 put a ceiling on every *read*: `bounded_read` sits on
`MaaObserver.observe` and on the module-level `observe`, so no page read can outlive its
own window.  The loop has a second kind of native call, and it kept the whole run's
budget: `MirrorRunner.step` sent a node action with
`run_node(self.tasker, plan['node'], self.deadline)`.  That is the same shape as the
read that motivated D37 -- one call, the entire remaining budget, no way for the
between-step check in `_walk` to interrupt it -- so the class was only half fixed.  It
was also invisible: only `_observe` stamped `artifacts['reading']`, so a run wedged
inside `run_node` reported `in_flight: false` and read exactly like a run with nothing
in flight.  The 51 runs in `evidence/runtime` that died without a stop are what that
looks like from the outside.

**Decision.** One formula, two named doors.  `_ceiling(deadline, limit, clock)` is the
arithmetic (the caller's tighter window wins, never an extension); `bounded_read` and
`bounded_action` are the two rules it serves, each with its own constant, so a reader
can see which rule they are looking at and a test can pin each one.  `MirrorRunner._act`
is the action door: it stamps `artifacts['acting']` with phase/node/page/limit before the
call, bounded by `bounded_action(self.deadline)`, and raises `ActionNeverReturned`
(`reason = 'the_action_node_did_not_finish_inside_its_window'`) when the node never came
back -- so the loop's own ending path records a named reason instead of a step that
silently spent the budget.  `_in_flight_report` reads the later of the two stamps and
names the node when the call in flight is an action; the ending records carry
`in_flight_node` beside `in_flight_phase`/`in_flight_seconds`/`in_flight`.

**Counter-examples.** (1) A node that answers and reports failure is *not* a wedge: the
screen still answers, the page is re-read next step, so the step only journals
`node_action_unconfirmed` and continues -- a retry-later fact, not a run-ending one.
(2) A tighter run deadline still wins over the action's own window (same ceiling rule as
the read).  (3) An action bound may never extend a caller's window: `bounded_action` is a

## D51. A reservation whose reader is only a callback is still a reservation

**Why.** Every transaction module in this repo has the same life: a record is
written *before* an input that can consume something, and read back *after* the
screen answers. That record is what stops a duplicate purchase: when a run dies
between the click and the observation, the next run asks the pending record what
already happened. The pairing lives across modules, so no single module can own
it, and until today nothing compared the two halves. The measurement that forced
the issue: `shop_tx.reconcile_purchase` and `shop_tx.reconcile_refresh` — the only
readers of a reserved purchase — appear in `MirrorRunner.step` **only as bare
attribute references**, handed to a helper as `shop_reconcile=` and called there.
`grep` finds no `reconcile_purchase(` in the runner. A reviewer reading `step`
would conclude a reservation is never reconciled; a refactor that deleted that one
keyword would leave every other check green and only a real interrupted run would
notice.

**Decision.** The pairing is derived and gated (`src/maalimbus/transaction_ledger.py`):
method families come from the transaction modules' own names (`intent` / `reserve*`
/ `*_intent` / `book_*` / `refuse_*` / `confirm_clear` are intents; `observe*` /
`reconcile*` / `recover*` / `commit` reconcile; `prepare` / `begin` / `reset*` /
`seal*` / `adopt*` / `close_visit` / `retire_pending` clean up; `matches` /
`refreshes_used` / `signature` / … answer questions), the sites come from
`MirrorRunner.step`'s AST, and a bare attribute reference counts as an *injected*
reader. `tools/audit_transactions.py` prints the ledger; the gate fails when an
intent has no reader or when the loop calls a method the families cannot place.

Measured on this tree: 7 transaction modules, 50 public methods, 98 touchpoints,
13 intentions, 14 reconciliations, 2 injected readers, **0 unpaired**, 0
unclassified. Two public methods are referenced by nothing
(`deployment_transaction.revived_cards`,
`grace_transaction.adopt_unspent_entry_settings`) and are reported, not gated —
a method nobody calls is a maintenance question, not a safety one.

**Counter-examples.** An intent with no reader *is* reported (synthetic source);
an intent plus `helper(reconcile=self.theme_transaction.observe)` is *not*, the
reference being the evidence; a call whose method the families cannot place
(`spend_coins`) is reported rather than bucketed; a field access (`self.x.data`)
is a query, not a method; the prefix rules keep one answer where a name looks
like two families (`reserve_confirm` is an intent, `confirm_clear` an intent,
`reconcile_purchase` a reconciliation, `close_visit` cleanup).

**Limit.** The ledger proves the reference exists, not that the helper reaches it;
that needs a run. A transaction written outside `MirrorRunner.step` is invisible
here, and the dead-API list matches method *names* across modules, so a method
whose name another module shares will not show up as dead.

## D59. A read that does not come back is not a verdict

**Why.** D43 put a bound on every native read (`bounded_read`), so a wedged screenshot can
no longer spend the run's budget. The bound then became the ending: the read raised a
plain `RuntimeError`, the step unwound, and the loop ended the run with
`the_task_raised_before_the_next_input`. That turns one 30 s emulator hiccup into a lost
420 s window — and it lands hardest exactly where an input is already out. In the retained
archive 16 of the 51 silent runs end on `window_no_progress` with their last event a settle
read: the click was sent, the settle read never came back, and the run had no way to treat
that as "this round produced no frame".

**Decision.** A failed read is an *observation failure*, not a verdict:

* `ReadNeverReturned` names it (`the_page_read_did_not_come_back_inside_its_window`) and is
  raised where the read actually fails — `MaaObserver.observe` when its node recorded no
  page — so the identity of the failure does not depend on matching an error message.
* Inside the settle loop it is one unproductive round. The frame is stood in for by
  `_unreadable_frame(before_sha)`: `scene='UNKNOWN'`, the *previous* image hash, no OCR.
  `UNKNOWN` is already a page with a budget (`unknown_rounds`) and a recovery, and keeping
  the old hash means the "the screen changed" rule sees a non-change rather than a fake
  successor.

  **Counter-example.** Before D59 this was the boundary between "an animation" and "a
  dead emulator", and the settle loop's own budget is 1–30 rounds: three rounds of a 30 s
  window still cost 90 s of a 420 s run, and on a `patient` page (the floor theme pull) the
  budget is `unknown_rounds = 30`. The bound is the run deadline, and the negative case is
  the next paragraph: the *step* is where the retries stop.
* At the top of a step it is retried `settings.read_retries` times (default 2, in the same
  defaults bag as `map_tries`/`page_tries`) and then ends the run with the read's own
  reason — a bounded retry, never a loop.

  **Counter-example.** A rule keyed on exception *class* would have swallowed pipeline
  failures too: a `RuntimeError` raised by anything else must still end the run on its own
  reason, and a test pins that (`test_a_plain_runtime_error_is_still_fatal_and_not_retried`).

**Counter-examples that shaped the numbers.** The failure count is *consecutive*, cleared
by any step that did read, because two hiccups early in a run would otherwise spend the
retry budget for every step after them. And `read_retries=0` must end on the first failure
(`test_a_zero_retry_budget_ends_the_run_on_the_first_failure`), so the retry cannot become
a way to ignore a dead device.

**Limit.** The retry is bounded per read, not per run: a device that has gone away will
spend `(read_retries + 1) × ONE_READ_SECONDS` (90 s by default) before the run ends, which
is the price of surviving a hiccup. The settle loop can also spend its whole round budget
on unreadable rounds and then carry on with `UNKNOWN`, which spends the unknown budget —
that is deliberate (an unreadable page *is* unknown), but it means the retry count is not
a bound on how long a single unreadable step may take.

**Evidence.** `tests/test_read_failure.py` (9 offline cases: the settle round survives and
still records its successor, the retried step, the bounded ending, the zero budget, the
plain error, the cleared count, the unreadable frame, the setting). `tests/test_settle_deadline.py`'s
wedged-read case now asserts the retried ending instead of the first-failure one. A
pipeline-only check `python tools/verify_pipeline_spec.py` stays `ok — 0 problem(s)` (805
nodes / 16 agent names / 6 entry tasks), and `python tools/run_tests.py -q` is green.
## D60. One budget cannot count two different events

**Why.** D59 made a failed settle read one unproductive round, and left the count to the
page budget: `rounds` (3, or 6 on the map, or `unknown_rounds` = 30 for the patient theme
pull). Those rounds were designed for a frame that arrived and did not change. A read that
never comes back is a different event: at the read window (`ONE_READ_SECONDS` = 30 s) plus
the interval, thirty patient rounds are 1080 s against a 420 s budget, so a device that
wedged could spend the whole window inside one step's settle loop and end on the deadline —
exactly the ending D37/D38/D59 were built to prevent, reached by a different road.

**Decision.** Consecutive failed reads get their own small budget,
`settings.unreadable_rounds` (default 2, bounded 0..30). The two counters are separate on
purpose:

* the page budget counts rounds that produced a frame and did not change it;
* the read budget counts *consecutive* reads that produced no frame at all, and any round
  that read something clears it.

When the read budget is exceeded the settle loop stops asking and leaves the page
unreadable — `UNKNOWN`, with the previous image hash, which the unknown budget already
owns. That is not an ending: the step records `reads_failed` and the run continues. The
step record now carries `reads_failed` (how many reads this step lost) and the note carries
`seconds`, `limit_seconds`, `consecutive`, `reads_failed` and `budget`, so the question
D59 left open — *what* wedged — is answerable from the journal afterwards.

**Counter-examples.** A read that fails twice with a good round in between must not be
stopped: the counter is consecutive, and the test drives exactly that (`reads_failed == 2`,
budget 1, the step still reaches MAP). A zero budget must stop at the first failure rather
than read once more. A page budget of four must still get its four reads when all of them
succeed; the read budget may not shorten rounds that did read. And a negative budget is
refused at construction, because it would stop the loop before its first read.

**Limit.** This bounds one step's settle loop, not the run: a device that keeps failing
across steps is now bounded by `read_retries` at the top of the step (D59), which counts
consecutive *steps*. The two are still independent numbers; a later decision could unify
them into one reading-failure budget per run, and the archive field to justify that is the
`reads_failed` this decision adds.

**Evidence.** `tests/test_read_failure.py` 16 passed (7 new D60 cases);
10 runner/plan/page suites 205 passed in 60.91 s; full suite 2245 passed in 202.11 s, exit 0; the read window and
the default are pinned by `test_the_note_says_how_long_the_read_took` and
`test_the_read_budget_is_a_setting_with_a_small_default`. No live input was sent; the
in-progress floor-2 run was left untouched.

- `portfolio(directories=None)` — the runs plus the six figures, so a report is one
  command instead of a recount.
- `tools/audit_efficiency.py` prints it; exit 2 when there is nothing to read.
- The corpus is *directories that wrote a journal*, the same definition
  `tools/audit_runs.py` uses, because a directory with no journal is not a run that
  measured zero.

**A zero is not a measurement.** Every figure that could not be computed is `None` with a
note saying why, and the tests pin the boundaries: one timestamp is not a duration, no
heartbeat is not a per-step rate, no recovery is not a recovery rate. The one figure that
*is* allowed to be `0` is the clear rate, because "0 of 142 runs reached floor 5" is an
observation with a denominator printed next to it.

- A single run with no floor is a clear rate of `0.0`; the basis says `0 of 1`.
- `portfolio()` skips a directory whose journal is empty, and the cross-check test asserts
  that `counts['no_events']` accounts for exactly those.
- The whole report is cross-checked against `tools/audit_runs.py::census` on the retained

guessed when the journal cannot supply it.

## D62. A rung that cannot be measured cannot be ordered

**Why.** The six figures phase 6 asks for include a recovery rate. D61 measured it honestly
and it was 1 of 274: of every four hundred recoveries, one moved the run on. The ladder was
then read as decoration. It is not -- the ladder presses no game control, it moves the
viewport, and a viewport gesture is not supposed to change the *page*. D58 had already
measured that 0 of 274 recoveries land on a different page name, and that number says
nothing about whether a rung did anything at all. The engine had no way to answer the
question its own ladder is built on: did spending this rung change what the reader could
see?

**Decision.** The journal already carries the evidence -- `map_observed` records the boxes
the reader found -- so nothing new is instrumented and the question can be asked of every
run that has already happened. `run_metrics.rung_effect` compares the last `map_observed`
before a `window_recovery` with the first one after it, per (gesture, page), and
`pages.LADDER_VIEW_EVIDENCE` declares the classes the archive shows. A rung is
`moves_the_view` when at least half of its measured spends changed the frame, `rarely`
otherwise, and `unmeasured` below three spends -- two observations are not evidence.
`ladder_order_problems` then ties the code to the measurement: a `rarely` rung may not sit in
front of a `moves_the_view` one, because a stop spends the ladder in order and most stops
never reach the third rung (rung 0 was spent 157 times, rung 1 seventy-seven, rungs 2-5
three to sixteen times each). On that rule the ladder changed: `drag_down` (18 of 72 on
MAP) now sits behind `drag_up` (14 of 14), `pan_left` (7 of 8) and `pan_right` (6 of 7).

**Counter-examples that shaped it.**
- *The page is part of the key.* `wait` changed the view 7 times of 9 on MAP, where the page
  is still animating, and 0 times of 38 on DRIVE, a fixed layout -- the same gesture, the
  opposite result. A declaration keyed only on the gesture would have been wrong for one of
  the two.
- *A wait is not a gesture.* It stays last whatever its number says, and it is exempt from
  the ordering rule; on a fixed layout a zero change is the design working.
- *A rung measured twice is not evidence.* The boundary needs three spends, or the first
  two observations of a rare rung would reorder the ladder.
- *The gate must fail on the reverse too.* An undeclared pair the archive measures, and a
  declared pair the archive no longer carries, are both problems.

**Limit.** The boxes are the page's own furniture (header, pack, battle, clear, enter), not
the nodes -- a drag may bring a node into view without moving any of them, so "rarely" is a
lower bound on a rung's usefulness, not a verdict. `UNKNOWN` pages have nothing to move and
measure 0 by construction. The order changed on MAP's evidence alone, because it is the only
page where every rung is spent.

**Evidence.** `python tools/audit_ladder.py` over the 142 retained runs: 270 recoveries
measured, `pinch_out` MAP 73 of 108, `drag_up` MAP 14 of 14, `pan_left` 7 of 8, `pan_right`
6 of 7, `wait` MAP 7 of 9, `drag_down` MAP 18 of 72, `pinch_out` UNKNOWN 0 of 8, `wait`

declaration and the archive agree. 17 cases in `tests/test_ladder_evidence.py`, including a
synthetic archive that must be reported as undeclared and a crafted ladder order that must
be reported as inverted. `tests/test_recovery_ladder.py` now derives its expected gestures
from the ladder instead of a hard-coded list, so the next reorder cannot pass silently.

## D63. A run that never says it was paid cannot be measured

**Why.** Phase 6 asks for a clear rate. `run_metrics.clear_rate` answers it honestly and
narrowly: it counts runs that reached five verified floors, and its own note says the
exploration half is all it can see. The reason is not a missing metric, it is a missing
record. Every task action in `agent/recognition.py` ends with
`journal.record('main_task_stopped', **result)`, but the reward branch returns a line earlier
-- so the payout, which is the only reason the loop exists, was the one outcome the journal
never held. `reward_task` itself wrote a single event, and only when it failed.

**Decision.** The reward task now writes what it decided, in three shapes that cannot be
confused: `reward_task_executed` (`passed`, `reward_received`, `reason`, `scope`,
`inputs_sent`, and `resumed` for the bookkeeping path that claims without input),
`reward_task_stopped` (now carrying `passed: False` and `reward_received: False` beside its
error), and `reward_task_skipped` for the decisions that happen before any input is sent --
no completed run, no ledger, an unaudited resume. `_note` makes the journal optional, because
several callers and the offline audits pass a stand-in. `run_metrics` gains `PAYOUT_EVENTS`,
`efficiency()['payout']` and a seventh measure, `payout_rate`, whose basis is
"`N` of `M` runs that recorded a payout outcome" -- not of every run, because a run that never
reached the reward pages has not failed to be paid, it never got there.

**Counter-examples that shaped it.**
- *No payout event is `None`, not "not claimed".* A run that died on floor two did not fail
  to claim; it never arrived. `payout: None` keeps the two apart.
- *A stopped payout is not a claim.* `reward_task_stopped` carries `passed: False`, and the
  figure reads `claimed: False` with the error as its reason.
- *A corpus with no payout event reports "not measured".* Printing `0.0` would be a claim
  about 142 runs that were never asked.

**Limit.** The 142 retained `packaged-mirror-*` runs will never gain this field, so
`payout_rate` is `None` for them and stays so; the first `packaged-reward-*` journal with the
event fills it. Widening the corpus glob is deliberately *not* part of this change: it is the
single definition all seven figures share, and moving it re-publishes every number at once
(D61), which is its own decision.

**Evidence.** `tests/test_payout_journal.py` (10 cases: skipped, stopped, verified claim,
journal-less callers, the three `efficiency()['payout']` shapes, the rate over the runs that
recorded one, and "not measured" for a corpus with none). `python tools/audit_efficiency.py`
now prints `payout_rate  not measured  basis: 0 of 0 runs that recorded a payout outcome
claimed it`. `tools/verify_reward_task_offline.py` fails at `HEAD` as well as with this change
(`assert 'not authorized' in blocked['reason']`) -- a stale expectation in that audit, named
here rather than silently absorbed.

## D64. An invisible word is a plan nobody can gate

**Why.** D57 measured the index's blind spot instead of closing it: two writers named their
plan words in a shape no static reader could follow, and the table
`PLANS_THE_INDEX_CANNOT_NAME` recorded 152 and 8 recorded sends. A word the reader cannot see
is a plan the drift gate, the successor gate and the archive comparison all skip -- so those
two plans could be edited to send a different page with every guard still green. D57's
declaration made the blind spot visible; it did not make it smaller.

**Decision.** Both writers now name their words as literals in the layer that owns the plan.
`src/maalimbus/window.py`: the battle auto-assign reason is a two-branch literal
(`win_rate_is_the_proven_auto_assign_control` / `damage_is_the_proven_auto_assign_control`,
one per mode, since `observe` returns before this point), and the starting-gift picker writes
`the_starting_gift_row_is_taken_from_the_tray` or
`the_starting_gift_is_picked_from_the_rotation_keyword` from `initial.get('gift')` instead of
reading `initial['reason']`. `src/maalimbus/runner.py` stops handing the reason over, so the
word has exactly one writer. `PLANS_THE_INDEX_CANNOT_NAME` is now `{}` -- and stays in the
code, because the gate reads it: a new unnameable writer must be declared there with the
number of sends the archive saw.

**Counter-examples that shaped it.**
- *The reader must refuse to guess.* `plan_reasons._elements` on a `BinOp` returns no name at
  all; that is why the concatenated word stayed invisible instead of being reported as
  unknown. Making it guess would invent a word the loop never sends and the gate would
  compare the archive against fiction, so the fix is literals at the writer, not inference in
  the reader.
- *Single source, enforced from the outside.* A caller that passes `initial['reason']` can no
  longer rename the plan (`tests/test_plan_index.py::
  test_a_reason_handed_over_by_a_caller_cannot_rename_the_plan`).
- *The declaration must be able to fail.* The table is emptied rather than deleted; with a
  fabricated entry the gate still reports the archive's unnamed set.

**Measured (142 retained runs).** `words the index cannot name: 0  declared: 0` (was 2 and 2);
`inputs whose outcome the archive can name: 923 of 1588 (58%)` (was 782 of 1588, 49%) --
because the 152 `win_rate…` sends used to fall in "stayed" with a page the reader could not

## D65. An effect the journal cannot see is not a verdict

**Why.** D62 judged each recovery rung by the page chrome it could find in `map_observed`
(`header_box`, `pack_box`, `panel_enter_box`, `battle_box`, `clear_selection_box`). A
viewport gesture is allowed to miss all of those and still succeed: pulling the board can
bring a destination node into view without moving the header by a pixel. The destinations
themselves never reached the journal — they were computed inside `MirrorRunner.step`
(`candidates_of`: the bright glyph the game marks, minus chrome, minus the progress
control, filtered to one step from the party) and used, then dropped. So `drag_down`
reading `18 of 72` was a **lower bound**, and D62 could not honestly say whether a rung
moved anything.

**Decision.** The loop writes what the frame offered, at the moment it offers it:

`map_nodes_offered` — `offered` (the count), `boxes` (the destinations, adjacency filter
included, because that is what the loop was actually allowed to choose from), `party` (the
point the filter used), `reason`.

The reader compares offers as a **set of box centres**, not as a sequence: the list is
ordered by adjacency, so a re-order is not a change and must not be counted as one. A rung
now reports `nodes_measured` and `nodes_changed` beside the chrome numbers, and counts as
`changed` when **either** signal moved. The writer is guarded by `candidates is not None`
— "the reader offered a destination list" — and deliberately **not** by a new `page ==
'MAP'` comparison: D44's ratchet failed the first draft on exactly that, and the ratchet
was right, because the condition this records is about the offer, not the page name.

**Counter-examples (pinned in tests).** An archive without node rows must report the node
signal as *unmeasured*, never as zero changes; a reordered offer is not a change; a node
that came into view while the chrome stood still **is** a change; an empty offer is still
written (the loop had nothing to choose from, which is itself a fact).

**Measured on 2026-10-23.** The retained 142 runs predate the writer, so
`tools/audit_ladder.py` says `rungs whose node signal was measured: 0 of 270` and prints
why. That is the honest state: the instrument exists, the lower bound stands until runs
write the rows, and the next measurement of the ladder will not be able to fall back on
"the chrome did not move" as if it were the whole answer.

**Limit.** The row is written once per MAP step, before the input, so a rung is bracketed
by the last offer before it and the first offer after it — which is what a rung acts on.
Old journals cannot be backfilled; the node signal starts with the runs that write it.
## D66. A duration without a budget is a stopwatch, not a measurement

**Why.** D61 published `mean_seconds` and D63 added `payout_rate`; neither says *where* a
run's minutes go, so any speed claim in a report would have been a guess. The journal can
answer the question without new instrumentation: every row already carries its own
`utc`, so the gap from a row to the next stamped row is the time that row cost.

**Decision.** `run_metrics.time_budget(rows)` attributes one run's seconds to the event
that spent them, excludes a gap beyond `MAX_GAP_SECONDS = 120.0` (a paused host or a clock
jump is not a step) and *reports* how many it excluded instead of dropping them silently.
`time_portfolio(budgets)` folds the runs and divides group shares by the **attributed**
seconds, not by the total, so the part the journal cannot explain is never handed to the
lines that were left. `tools/audit_time.py` prints it, `portfolio()` carries it beside the
measures, and the last row of a journal gets no attribution at all — a row whose cost
nobody observed is not a row that cost zero.

**Counter-examples (all pinned in `tests/test_time_budget.py`).**
- A gap of 300 s is excluded and counted; the same two rows 30 s apart are attributed, and
  the cap is a parameter so a deliberately short step is not excluded by accident.
- One stamp is not a budget: `total_seconds` and `unattributed_seconds` are `None`, and the
  corpus-level report says "not measured" rather than zero seconds.
- An event nobody grouped is kept under `other`; the group seconds add up to the attributed
  seconds and never to the total.
- `Z` and `+02:00` stamps are the same clock; an unparseable stamp is skipped, not guessed.

**Measured** (`python tools/audit_time.py`, 2026-10-23, the 142 retained runs):
29 538 s attributed of 38 720 s total (20 gaps beyond the cap excluded).

## D67. A rate over a proxy is not a rate

**Why.** `reads_per_step` divided the reads of 142 runs by their `loop_heartbeat` count.
The heartbeat is not a step: it is a line added on 2026-10-23 so that a run dying inside a
step still leaves the last thing it started (D37's evidence), and the builds before that
wrote none. So the corpus published **34.2 reads per step** while the same runs declare
**1 065 steps** and made **10 362 reads**: the real figure is **9.73**, and 3.5× of the
published number was the denominator. 61 of the 142 runs never declared a step at all.

**Decision.** A step rate divides reads by the step count the loop itself declares when it
stops (`mirror_loop_stopped.steps`), and both terms come from the same runs: reads are
summed over the runs that declared, never over the whole corpus. The heartbeat count is
reported beside the rate as what the journal *documented*, not as a denominator, and the
basis line says how many runs supplied a step count
(`10362 reads over 1065 steps declared by 81 of 142 runs`). When no run declares a count the
figure is `None` with a reason — a proxy is not a measurement.

**Counter-examples pinned.** A run that wrote three heartbeats and no step count has no rate
(`steps is None`), not a rate with three in the denominator; a run declaring five steps and
reading ten times is 2.0, not 10.0; a corpus of one declaring and one heartbeat-only run
reports 1.0 with `2 reads over 2 steps … 1 of 2 runs`, never 2.0 by counting the older run's
reads against the newer run's steps.

**What this changes.** Phase 6 justified "cut the reads per step" with 34.2; the number is
9.73 (and 6.31 reads per input). The expensive fact is not the count — it is 2.45 s per read
(D66's budget: `map_observed` is 46.2% of all attributed time). A rate that is wrong by 3.5×
sends the next optimisation at the wrong object, which is why this is a decision and not a
typo fix.

**Limit.** `steps` counts loop iterations, not journaled actions: a run that dies declares
nothing, so the rate is over the runs that ended on their own terms, and the basis says so.

## D68. A read that does not time itself cannot be split

**Why.** D66 put a number on every journal line by taking the gap to the next stamped row,
and it gave `map_observed` 2.45 s per read. That gap starts where the row was written and
lasts until the *next* row — which contains the next read — so it can say the reads own the
time and it cannot say whether the observation node's screencap+OCR or the loop around it
spent it. Phase 6 asks whether to cut the number of reads or the cost of one read, and the
two answers point at different code; without a split the choice is a guess.

**Decision.** Every observation writer times itself. `MapObservation`,
`BattleObservation` and the map write inside `ThemeObservation` measure
`time.monotonic()` from the top of their `run` and record `seconds` on the row they already
write, so the field costs one float per read and no new line. The reader side is
`read_cost` / `read_portfolio` (`src/maalimbus/run_metrics.py`), which report coverage —
`N of M reads carry their own duration` — and never turn an untimed corpus into zero
seconds; `read_split` subtracts the node half from the reads group, and it only does so over
runs that measured **both**, so the subtraction compares one sample with itself.

**Counter-examples pinned.** A row without a number is not 0 s. `seconds=True` is not a
duration. A comment that mentions `seconds=` is not a field: the gate walks the AST for a
real `import`-level keyword, which a text search would have accepted (the same mistake D53
made with an import inside a docstring). A run with read durations but no gaps is not in the
split. A `scene_mismatch` is the pipeline's own refusal record with no action body, so it is
not a timed read.

**Evidence.** Replaying the real `MapObserve` node over a retained MAP frame
(`python tools/verify_map_observe_replay.py --binary build/mxu-probe-271/maafw
--map-frame evidence/runtime/packaged-mirror-20261012-045906/frame-0009.png

be split.

## D70. The read's cost is the full-frame OCR, and now the row says so

**Why.** D68 gave every observation row its own `seconds`; D69 then priced the capture at
0.051 s of a 1.44 s read, which left ~1.39 s described only as "recognition". One number
with three plausible owners (the full-frame OCR, the narrow ROI re-reads, the classifier)
cannot be optimised: cutting ROI reads and cutting OCR cost are different code.

**Decision.** `LimbusRecognition.observe` counts the three phases it can name and nothing
else: the single full-frame OCR call, every narrow ROI re-read (the calls that go through
`context.run_recognition_direct` for a crop), and the remainder as classification. Every
observation writer puts the three on the row it already writes, through
`timing_fields()`, which returns **nothing** for a cached read — a cached frame spent no
time, so claiming three zeros would be a fabricated measurement.

The counter-examples are pinned: a read that says only its total is not a split of zero; a
partial split (two of three phases) is a writer bug and reads as unmeasured; a boolean is
not a duration; a `scene_mismatch` row has no action body and carries no phases; and the AST
gate walks the three writers and demands a real `timing_fields()` unpack.

**Evidence (real Maa pipeline, retained frames, `input_sent: false`).**

| frame | total | full-frame OCR | ROI re-reads | classification |
| --- | --- | --- | --- | --- |

runs written after this decision exist. Replay frames live in memory, so device capture is

## D71. An input that cannot land must not be posted

**Why.** The first authorised live run (`evidence/runtime/packaged-mirror-20261023-221109`,
`tools/selfrun_mirror.py --attempts 1 --seconds 240`) sent eight clicks that landed. The ninth
was posted and the framework answered `controller not found [controller_id=]`; the run then
recorded nothing until the harness killed it at its 240 s budget.

The guard that should have caught it compared the controller id with the empty string, and the
binding's id was `None`. `None` is not `''`, so the guard passed, the click was posted, and the
same hole was open on `swipe`, on `key`, and on the flow path -- which posts through the raw
controller after only *noting* the controller state.

**Decision.** One predicate answers "can this binding route input at all" for every door:
`binding_is_empty(controller)` is true when the id is `''` or `None`, and false when the
controller has no `id` attribute at all (a stand-in that cannot answer the question is let
through rather than accused, which is what the existing device stub needs). `click`, `swipe`,
`key` and the flow click all ask it before posting, and a refusal raises
`RuntimeError('the_controller_binding_is_empty')`, which the loop already turns into a named
ending.

**Counter-examples, pinned.** A `None` id refuses the click and posts nothing (that is the live

## D74. The task's verdict is a statement about its route, not about the screen

**Why.** D73 taught the entry task to resume a suspended run. The first live run after that
fix still ended after 128 s on `an_action_node_failed_and_the_task_was_torn_down`
(`evidence/runtime/packaged-mirror-20261023-230804`): the task drove `DRIVE` → `MIRROR_ENTRY` →
`RESUME_DIALOG` → `MAP` and then ended on `LimbusUnknown`, because **the map is outside the entry

D72 turned that into a stop, and a run that had just been handed a live map was ended by the
return code of the task that handed it over.

**Decision.** After a node action that came back unconfirmed, the loop takes **one bounded read**
in the page the action was sent from and lets the screen decide:

| what the read says | what the loop does |
| --- | --- |
| a different page | notes `the_task_ended_but_the_page_moved`, clears the action, carries on |
| the same page | ends the run with `ActionNodeFailed` (D72's protection, unchanged) |
| `UNKNOWN` or unreadable | same-page: no movement was observed, so the run ends |

The task's return code says "my route ran out"; the page says "the transition happened". Only the
second one answers the question the loop is asking.

**Evidence (live).** Third authorised run, `evidence/runtime/packaged-mirror-20261023-231231`:
`recognized DRIVE → MIRROR_ENTRY → RESUME_DIALOG` (the D73 node fired), `terminal

**Counter-examples** (`tests/test_native_action.py`, 10 tests): the same page after the failed
node is still a torn task and still ends the session; an `UNKNOWN` answer is not movement, because
nothing was seen; a page that moved leaves the session alive (`device.ended is None`).

**Limit.** This says the loop may continue when the screen moved; it does not say the transition
was *correct* — the map it reached still has to be readable, and the next live run shows what
happens when its node clicks do not advance. The `page: null` on the moved event is the old
weakness of `acting['page']`, not the new rule.

## D75. The click box's kind is a fact the reader already had

**Why.** `map_clicks` returns nine kinds of detected box and `candidates_of` threw the
kind away, keeping only the rectangle. The loop then clicked the first box the adjacency
filter kept, which for 37 of 39 readable archive frames was a `gold_badge_node` — a
190x190 tile whose *centre* is often the empty floor between two nodes. The bright glyph
the client draws on the step it will accept (`bright_lit_icon`, `lit_icon`) was present in
most frames and was almost never first.

**Decision.** The kind travels with the box: `candidates_of` stores
`record['map_candidate_kinds']` keyed by `box_key(box)` (`"678,353,40,40"`), the offer
event carries `kinds=[...]` parallel to `boxes`, and every `map_click_result` names the
kind of the box it judged (a click the loop replaced keeps the kind it was sent with,
because the offer list has already moved on). `candidates_of` then orders the adjacent
list by `CLICK_KIND_ORDER` — the marked step first, the tiles after, an unknown kind last
rather than dropped — because ordering is a policy and the reader already answered the
question it needs.

**Live evidence.** `packaged-mirror-20261023-232612`: 2 of 2 `gold_badge_node` clicks
refused (`the_page_stayed_on_the_map_after_the_click`) while the one `bright_lit_icon` box
sat fourth and was never reached. After the order changed,
`packaged-mirror-20261023-233056` clicked `lit_icon` first and the run reached
`NODE_PANEL → PRE_BATTLE_TEAM → BATTLE_HUD` — the first battle the series has reached —
and `packaged-mirror-20261023-233928` finished that battle, walked a node, skipped a
cutscene, took an `EVENT_CHOICE`, cleared its result and rolled an `EVENT_CHECK`: 11 steps,
11 clicks, one honest `mirror_loop_stopped(stop_path='agent_loop')`.

**Counter-examples.** A kind the reader invents is kept at the end, not dropped, so a
frame that offers only tiles still offers something to try. An unknown string sorts with
the tiles. A verdict for a box the current offer no longer contains falls back to the kind
remembered with the pending click.

**Limit.** The kind map is keyed by text because the loop's state and final result are
JSON: the first version keyed it by tuples and a live run ended with
`callback_failed: keys must be str, int, float, bool or None, not tuple`. The ordering is
still only a heuristic — the map's connectivity is not readable from a frame — and the
node click's own verdict still says `the_map_stayed_with_the_party_in_place` when the page

**Evidence.** `python tools/audit_map_clicks.py` prints sent/accepted/rejected per kind and
says "not measured" on an archive written before this decision. `tests/test_map_click_kinds.py`
(12 tests) pins the writer, the order, the remembered kind, the JSON-safety and the tool.

## D76. A click's verdict belongs to the read that can still contradict it

**Why.** The map click's outcome was decided inside the settle window: if the page was
still `MAP` and the party had not moved, the loop wrote
`the_page_stayed_on_the_map_after_the_click` (no candidate branch) or
`the_map_stayed_with_the_party_in_place` (party branch) and spent the refusal on
`map_refused_streak`. A click that opens a node panel does not move the party, and a
panel animation can finish after the settle window closes. Both live runs of
2026-10-23 23:39 and 23:55 show the same shape:

| run | click | verdict written at the time | page named on the very next read |
| --- | --- | --- | --- |
| `packaged-mirror-20261023-233928` | marked node `(1028,480)` | `the_map_stayed_with_the_party_in_place` | `NODE_PANEL` |
| `packaged-mirror-20261023-235553` | marked node `(1060,476)` | `the_map_stayed_with_the_party_in_place` | `NODE_PANEL` |

A refusal at streak ≥ 1 hands the window the `map.progress_button` escape hatch, which
leaves the exploration (`the_exploration_must_be_resumed_before_a_node_click`). One
wrong verdict therefore costs a whole entry cycle: on
`packaged-mirror-20261023-231231` that cycle was ~90 s and never tried another node.

**Decision.** A click whose page did not change is **not** a refusal yet. Both sites
record `outcome='unjudged'` and set `state['map_unjudged']` with the target, the kind
and the frame the click was judged against. The next `step` settles it first thing,
from the page that read names:

* any page that is not the map → `accepted`, reason
  `the_click_was_taken_after_the_verdict`, streak reset;
* still the map → `rejected`, reason
  `the_click_was_not_taken_and_the_page_stayed`, and only now does
  `map_refusal_streak` count it.

The resolver asks `map_dispatch.is_map(page)` rather than comparing with the literal
`'MAP'`: a new page literal in the loop is exactly what D44's ratchet counts, and the
ratchet failed the first draft of this change — correctly.

**What this does not fix.** The verdict is still written twice for one click (once
`unjudged`, once settled); `run_metrics.click_kinds` keeps them apart so the table
cannot claim a landing that has not happened yet. The count of refusals is unchanged —
only their timing moves one read later, which is what makes a late panel not count.

**Measured.** `packaged-mirror-20261023-235553` (authorised, 162.3 s, 9 clicks): the
run walked `EVENT_CHECK → CUTSCENE → EVENT_CHECK_RESULT → EVENT_CHECK_READY → GIFT_GET
→ MAP`, clicked the marked node at `(1060,476)` and reached `NODE_PANEL`, clicked its
enter control and landed on a screen the reader cannot name (E.G.O gift obtained +
`Check Passed`, with a `SKIP` button) where the budget ended. That run still wrote the
old final `rejected` (its two `map_click_result` rows are `superseded` and
`the_map_stayed_with_the_party_in_place`), which is exactly the evidence that moved
the second site: the fix was written from the run, not the other way round.

**Limit.** A click that opens nothing at all costs one extra read before it is called
a refusal, and the streak therefore names the un-resumed case one step later than
before. The alternative — believing the settle window — is what the table above
measures as wrong twice out of twice.

## D78. A killed process cannot write its ending, so the killer does

**Why.** `tools/selfrun_mirror.py` enforces the caller's budget from outside — it has to,
because a caller cannot take away its own wall clock — with `timeout=seconds + 15`. On
2026-10-24 00:19 an authorised 420 s run reached **floor 3** (the first floor advance of
this series) and was killed **fifteen seconds** past its budget, mid-step, so the loop
never reached its between-step check and never wrote `mirror_loop_stopped`. Its journal
ends on a read: `stop: []`. Fifteen seconds was shorter than one step, so the margin could
not do the job it existed for — the retained overshoots are 12.3, 12.3, 13.3 and 15.2 s,
and one of them sits inside the old margin already.

The consequence is not cosmetic. `run_metrics.ending` saw no stop, called the run `died`,
and `no_progress_stop_rate` counted a healthy, advancing run as a run that stopped without
progress. The measurement that is supposed to say "the loop gives up" was reading "the
harness kept its own promise".

**Decision.** The margin is a named constant (`MARGIN_SECONDS = 45`, wider than every
measured overshoot), and a kill is written by the process that performs it: when
`subprocess.run` times out, `attempt()` writes `harness.json` into the run's own directory
with `killed_by_budget`, the stop reason, the budget, the margin, the elapsed time and the
exit code. `run_metrics.ending(rows, directory)` reads that file first and answers
`budget` / `harness_budget`, so `ENDING_KINDS` is now five: a stop, an error, a death, a
budget end, and no events at all. `tools/audit_runs.py` prints `killed at the budget: N`
and does not list such a run as failed; `no_progress_stop_rate` says in its note that a
budget end is not counted.

**Counter-examples.** The same rows without the file are still a death — the bucket is
evidence, not an inference from silence. A `harness.json` that does not say
`killed_by_budget` changes nothing. `summarise(rows)` without a directory still answers
`died`, so no caller gets the bucket by accident.

**Limit.** The runs killed before this writer existed (`packaged-mirror-20261023-221109`,
`…-223237`, `…-235553`, `…-001939`) will keep reading as deaths: the file was not written
when they ended, and inventing it afterwards would be writing evidence after the fact.
Their records stay `died` the same way pre-2026-10-23 stops stay `unrecorded`.

## D79. Waiting is not patience when the hazard is flat

**Why.** `window_unknown_wait` slept the step interval (4 s) between reads of a page the
reader could not name, and that group was the second-largest cost line in the 420 s run of
2026-10-24 00:19: **88 s of 428 s in 12 rounds, 7.3 s each**. The obvious optimisation was
to wait longer (a page that has been unreadable for a while must be closer to resolving),
so that was measured first.

**Measurement (154 retained runs, 413 unknown-page episodes).** Conditional on the page
having been unreadable for *t* seconds, the chance that the **next** read names it is 12%
(t = 0–4 s), 23% (4–8), 36% (8–12), 23% (12–20), 28% (20–40) and 28% (40–300). The hazard
does not decline with time, so waiting is not patience: it is latency added to a sample
that costs 2.07 s. The same data also killed two neighbours: a page unknown immediately
after a battle read is UNKNOWN again 136 times and a battle page 5 times, so "battle
flicker" is a real page change and deserves no special pause; and time-to-resolution is
p50 11.3 s / p90 45.5 s with a median of two reads, so a long poll would simply miss.

**Decision.** A page the reader cannot name gets its own pacing: `unknown_interval`
(default **1.5 s**, validated `0 < x ≤ 30`, exposed as `--unknown-interval`) is used for
`window_unknown_wait`'s sleep and its `interval_s` field, and nothing else. It sits below
the measured cost of one read (2.07 s) on purpose: the loop should be sampling, not
sleeping. The step interval stays 4 s for every other wait.

**What this does not claim.** No wall-clock improvement is asserted from a single live
sample. The authorized 150 s run after the change
(`evidence/runtime/packaged-mirror-20261024-003759`, 167.4 s, 7 clicks, 114 events,
`stop_path=agent_loop`) shows the pacing live — two unknown waits at 1.5 s — but its three
episodes took 37–40 s to resolve, which is a battle-animation phase and not comparable
with the corpus median. The figure to compare next is the `window_unknown_wait` group in
`run_metrics.time_budget` over runs that contain the same phase.

**Limit.** The hazard was measured on archived runs whose pacing was 4 s; a shorter pause
changes the sampling density, so the hazard per *second* can only improve or stay equal —
but this corpus cannot prove that, only the next one can.

## D80. A clear rate over runs nobody gave time to clear is a statement about the budget

**Why.** `clear_rate` has read `0.0` for every corpus this series has measured — 155 runs,
best floor 3, none at floor 5. That figure is true and it is not about the loop: a complete
Mirror run is five floors, a claimed payout and a return to the lobby, and no run in the
archive was ever given more than a few minutes.

**Measured.** Of the 155 retained runs, **19** ended on `loop_deadline_exceeded` (the
caller's wall clock); the rest ended for reasons the loop itself decided (a refusal, a
watchdog, a torn task) or died. So the honest statement is two-part: the clear rate is
zero, *and* only a minority of the corpus was capped by time — the runs were short because
they ended earlier than a clear, not because they were all cut off at five minutes.

**Decision.** `efficiency()` gains `budget_ended` (the ending reason is the caller's
clock), and `metrics()` gains:

- a `clear_rate` note that states how many runs the caller's budget ended — the rate is
  then read against that number instead of against a capability claim;
- a new measure **`floor_progress`** — the mean floor reached over the runs that reached
  one, with the best floor and the count in its basis. This is the figure that moves when
  the loop gets better at walking a floor; a clear rate cannot move until a run is given
  enough time to finish.

**Counter-examples.** A run that ended on any other reason leaves `budget_ended` false; a
corpus that never walked a floor reports `None` with "none of N runs reached a floor",
never `0.0`; the progress figure is computed only over the runs that reached a floor, so a
corpus of capped-at-zero runs cannot drag the mean down as if it were evidence.

**Limit.** `floor_progress` is not a difficulty-normalised figure: floor 1 of a hard run
and floor 1 of a normal one count the same, and the diff between them is not modelled here.

## D81. An unknown page is not one behaviour

**Why.** D66 put `window_unknown_wait` at 19.9% of the attributed time and D79 measured
that waiting longer does not help — but the group is an average over states that have
nothing in common: a loading screen after a battle, a transition after the mirror menu, a
fade after a cutscene. Judging the pacing, or the cost, on the group as a whole is judging
a blend.

**Decision.** Two small changes, one on each side of the journal:

- The loop remembers the last page the reader could **name** (`state['last_named_page']`,
  written where the scene is resolved, and only when the scene is not `UNKNOWN`), and every
  `window_unknown_wait` row now carries `after=<that page>`. A wait with nothing named yet
  writes `after=None` rather than inventing a name.
- `time_budget` keeps each unknown wait's seconds under `unknown_waits[after]`, and
  `time_portfolio` folds those splits across runs; `tools/audit_time.py` prints them as
  `unknown-page waits, by the page that came before them`.

**Why the row, not an inference later.** The preceding page can be recovered from a
journal after the fact only by replaying the events in order and hoping the page was named
in between; the row that produced the wait already knows. Writing it where it is known is
the same rule as D68's `seconds` and D65's `offered`.

**Counter-examples.** A row written before D81 has no `after` and lands in the
`unrecorded` bucket instead of joining a named one — the corpus today is 520 waits, all
`unrecorded` (4 601 s), which is exactly what the tool now prints. A corpus with no
unknown waits reports no bucket at all, not an empty one pretending to be zero.

**Limit.** `after` is the last *named* page, which after a long run of unreadable frames may
be several transitions old; it is the closest thing the loop knows, not a claim about the
immediate predecessor.

## D82. A torn-down task closes the input door, not the reading one

**Why.** D72 ended the run when an action node came back unconfirmed, and D74 narrowed that:
if the page moved, the task's verdict was a statement about the task's *route*, not about the
screen, so the loop kept walking. The live run
`evidence/runtime/packaged-mirror-20261024-010918` shows what the narrowing missed. At
`05:13:08.972` the entry task ended on `LimbusUnknown`; at `05:13:10.376` the next read still

(`0.78`, `0.77`). At `05:13:19.200` the loop decided to click a map node and wrote
`window_intent`. The framework answered, in the same second,
`controller not found [req.controller_id=]` with `"controller_id":""`, and the Python side
never returned: the journal has no line until `05:23:20`, when the progress watch finally
wrote `mirror_loop_stopped(reason: the_run_kept_observing_without_writing_anything,
stop_path: no_progress_watchdog)`. The harness had already given up and killed the wrapper
at `05:20:02`, so this one run carried two true records -- and the census printed the kill
instead of the stop, which is the second half of the defect below.

**Why the census also lied.** `run_metrics.ending` consulted `harness.json` before the
journal, so this run was counted `budget`/`harness_budget` although it had written a stop of
its own. The harness may only explain a run that wrote no ending: a blocked native read
cannot be interrupted from Python, so the two records are not alternatives.

**Why the old guard could not see it.** D71 refuses an empty `controller.id`, but the handle
still reported a non-empty id after the tear-down — that limit was written down when D71
landed. The rejection happened inside the native call, where no Python check and no watchdog
thread can run (the process held the interpreter while it waited).

**Decision.** A device whose task was torn down may keep reading and may not send input. The
torn-task path records `note_binding_lost(<reason>)` on the device; every input door
(`click`, `swipe`, `key`) refuses with that reason before it posts anything; the loop's error
path turns the refusal into a named ending. The reading door stays open because the live run
proves reads still work there.

**Counter-examples this must survive.**
- A live binding still posts: `test_a_live_binding_still_posts`.
- The refusal is not sticky in the wrong direction: it only applies after `note_binding_lost`,
  and the first reason is the one kept (`test_a_lost_binding_is_named_before_the_handle_is_trusted_again`).
- Every door refuses, not just the click (`test_every_input_door_refuses_after_the_binding_is_gone`).
- The D74 continue path still reads on: after `_act` survives a torn task the device has
  `binding_lost` set, `ended` unset, and the notes are
  `node_action_unconfirmed` then `the_task_ended_but_the_page_moved`
  (`test_a_torn_task_closes_input_and_keeps_reading`).
- The kind table knows the reason (`test_the_reason_is_the_one_the_ending_and_the_kind_table_use`),
  so `audit_hold_gap` stays at zero unclassified failures.

**Rule added with the door.** `ending()` reads the journal first and `harness.json` only
when the journal carries no stop and no error (`test_a_journal_that_ended_itself_outranks_the_harness`).

**Limit.** The loop cannot repair a released binding by itself: a new task that owns a
controller would, and wiring that is a separate decision. Prevention is the only defence
available, because the block happens inside the framework's native call.

## D83. A task that can only enter cannot finish entering

**Why.** The entry task walks `DRIVE → MIRROR_ENTRY → RESUME_DIALOG → MAP` and then had no
node for the last page. Live `packaged-mirror-20261024-010918` shows all four steps in one
task: `recognized DRIVE` at 05:12:41, `MIRROR_ENTRY` at 05:12:44, `RESUME_DIALOG` at
05:12:46, and from 05:13:06 every frame of that task read `MAP`. Three reads later the task
gave up with `unknown_or_bounded_transition_exhausted`, `D74` rescued the loop from the
other side (`the_task_ended_but_the_page_moved`), and `D82` then closed the input door
because the task that owned the controller was gone.  One missing node cost the rest of
that run.

The class is not "MAP is special". It is: **a task asked to move the app from A to B must
also be able to say "already there"**, and its page vocabulary ages every time the game
adds a way to arrive.

**Decision.** `MirrorInside`, a node that recognises `MAP`, does nothing, and ends the
task — reachable from `MirrorDrive`, `MirrorResume`, `MirrorEnter` and `MirrorHard`.
Ending the task *successfully* is the honest answer: the caller wanted to be inside, and it
is.  The packaged pipeline goes 795 → 796 nodes; `tools/prepare_resources.py` carries the
same node and the same edges, and the installed tree was updated with the file.

**Counter-examples.** `tests/test_entry_task_inside.py` builds them from the node table:
dropping the node empties `MAP` out of the reachable scene set (the gate would fail), a
version that *clicks* on the map is refused, and a node nobody points at is unreachable —
because a node that exists but cannot be reached is the same defect one step earlier.

**Evidence.** `build/verify_inside_replay.py` replays the four live frames through the real
`limbus_scene` recognition and a replay controller:

| | recognised | terminal | task |
| --- | --- | --- | --- |
| before | `DRIVE`, `MIRROR_ENTRY`, `RESUME_DIALOG` | `unknown_or_bounded_transition_exhausted` (`last_scene: MAP`) | `succeeded: False` |
| after | `DRIVE`, `MIRROR_ENTRY`, `RESUME_DIALOG`, `MAP` | — | `succeeded: True` |

**Limit.** `MAP` is the only page the entry task has been observed to end on inside the run.
`BATTLE_HUD` and `DUNGEON_PROGRESS` would each need their own node and their own evidence
before they are covered, and a task still cannot tell "the player is inside" from "the
player is on a map they never asked for" — that distinction belongs to the caller, which
knows which page it clicked from.

## D1 · Maa 负责设备，Python 负责判断

`PROJECT.md:1338-1339` 把这条写成开发契约：Maa 拥有截图/输入与有界 Pipeline 调度，纯 Python 给选项排序，Agent 返回识别框与状态更新。直接后果是 `maa` 只出现在少数边界模块里，而且大多推迟到调用点：实测在**模块顶层**直接 import `maa` 的有 5 个文件——`src/maalimbus/adb_device.py:15-17`（`AdbController` / `MaaAdbInputMethodEnum` / `Toolkit`）、`src/maalimbus/battle_counter_native.py:3`、`src/maalimbus/deployment_availability_native.py:7`、`src/maalimbus/floor_trial_vision.py:3`、`src/maalimbus/shop_native.py:3`；另有 6 处把 import 放进函数体内——`windows_controller.native_methods()`（`src/maalimbus/windows_controller.py:18`）、`src/maalimbus/neural_shadow.py:132`、`src/maalimbus/reward_cost.py:39`、`src/maalimbus/overlay_dismissal.py:28`、`src/maalimbus/owned_inventory.py:113` 与 `:128`、`src/maalimbus/deployment_numbers_native.py:7`。这使得绝大多数判定可以在 128 个 `tests/*.py` 文件里用归档帧复现。

## D2 · 循环是库，页面与输入是注入的两个缝

`docs/runner.md:5-14` 记录了动机：循环原先住在 `tools/window_step.py`，那是个 CLI 工具，自己建 ADB controller、自己截图、自己点击，别的东西开不动它，也没有设备就测不了。

两个缝的定义就在 `src/maalimbus/runner.py`：

```python
class Device(Protocol):          # runner.py:251
    def screencap(self) -> np.ndarray: ...   # BGR，已在 1920x1080 空间
    def click(self, x: int, y: int) -> None: ...
    def swipe(self, x1, y1, x2, y2, duration_ms: int) -> None: ...
    def key(self, code: int) -> None: ...    # 可选，可以抛 NotImplementedError
```

三个实现：

- `MaaDevice(controller, *, wait=None, target_long_side=1920, deadline=None)`（`:273`）——包 `context.tasker.controller`，每次调用投递 job 并等完才返回，所以 `click()` 返回就等于触摸落地；构造函数设 `set_screenshot_target_long_side(target_long_side)`，这正是把帧钉到识别空间的那一步。
- `LocalDevice(...)`（`:323`）——给 CLI 那份 controller 用同样的映射，另有 `foreground()` 供 CLI 打印摘要。
- `FakeDevice(frames=(), foreground=None)`（`:387`）——重放帧并记住发出去的东西。

`Observer` Protocol 在 `:551`，只需一个 `directory: Path` 与 `observe(*, deadline=None) -> dict`。`MaaObserver(context, directory=None, *, pipeline='WindowMapObserve', battle_pipeline='WindowBattleObserve')`（`:598`）跑 Agent 自己的识别节点并读回它记录的页面；`FrameObserver(directory, frames=(), *, index=0, settings=None)`（`:567`）重放归档的 `frame-*.json`。

`MirrorRunner`（`:1277`）的签名是：

```python
MirrorRunner(device, *, settings, locale='en', registry=None, store=None,
             directory=None, journal=None, flow=None, log=None,
             observer=None, roots=None, run_id=None, result=None)
```

`step()`（`:1436`）返回 `{'page','reason','target','input_sent','event','stopped','done','observation', ...}`，其中 `stopped` 命名结束这个窗口的条件，`observation` 就是 CLI 写进 `build/window-debug/<label>/frame-*.json` 的那条记录。`run(*, steps=300, interval=6.0, round_limit=5, deadline=None)`（`:2756`）是外层循环。

同一个循环现在有两个前端：CLI（`tools/window_step.py`）与 App（`MirrorLoopAction`，`agent/recognition.py:1526-1575`）。两者都构造 `MirrorRunner`，参数集完全相同——`docs/agent-loop.md:40-48` 列出 `custom_action_param` 接受的每一个 CLI 名字。

## D3 · 一页最多一个输入，没证据就拒绝

`src/maalimbus/window.py:15-19` 把四条规则写在模块 docstring 里：

1. 一页一次计划只发一个输入；
2. 没有可靠控件的页面拒绝而不是猜坐标；
3. 只有后继页落在期望集合里这次点击才算被接受，否则记 `unexpected_successor` 并停窗；
4. 战斗回合只在游戏自己显示 `START` 时提交。

拒绝的实现是 `_refuse(page, reason)`（`window.py:106`）返回一个 `action='record'` 的计划——不是异常，也不是默认坐标。`plan_step()`（`window.py:110`）是唯一入口，`_plan_step()`（`:139`）是那张大表。

`window.py` 里还有两个辅助判断：`successor_ok(plan, page)`（`:1032`）与 `step_result(plan, *, sent, before, after, page, frame_changed=False)`（`:1052`）。另外 `ANY = '*'`（`:33`）是「关闭浮层」这类动作的期望哨兵：后继由**被覆盖的页面消失**证明，而不是由它露出了哪一页证明——浮层的卡片会走过很多不同页面，没有正面清单能穷举，但「仍然是浮层」是可判定的失败。

## D4 · 一张「永远不点」的控件黑名单

`FORBIDDEN_CONTROLS`（`src/maalimbus/window.py:50-63`）列出 14 个控件。它们在被点击时会丢掉整局运行或被放弃的奖励，但它们的文案又是识别页面身份的依据，所以**保留为锚点、拒绝为目标**：

```
'resume.halt_button', 'reward_card.cancel_button', 'gift_pick.refuse_button',
'gift_warning.confirm_button', 'entry_confirm.cancel_button', 'level_warning.cancel_button',
'star_confirm.cancel_button', 'initial_gifts.refuse_button', 'gift_search_forgo.cancel_button',
'event_check.skip_button',           # 点了等于没人尝试掷骰，直接放弃这次检定
'run_reward.give_up_button',         # 丢掉五层楼的运行
'run_reward_confirm.cancel_button',  # 关掉领取询问而不领取
'window_reset.confirm_button',       # 每周重置通知的 Confirm 会离开地牢
'expired_session.cancel_button'      # 关掉过期会话就留下未领取的奖励
```

强制点在 `window.py:128-135`：任何计划的目标若落在黑名单里，直接改写成 `control_is_forbidden` 拒绝。仅有两处显式豁免：

- `page == 'STAR_CONFIRM'` 且目标 `star_confirm.cancel_button` 且原因为 `incomplete_graces_return_to_selection`；
- `page == 'GIFT_PICK'` 且目标 `gift_pick.refuse_button` 且原因为 `refuse_proven_owned_single_free_gift`。

## D5 · 输入之前先持久化意图

每一个 `*_transaction.py` 都是同一个形状：**先落盘再输入，没被证明的后置条件绝不允许第二次输入**。`shop_transaction.py:1` 的 docstring 说得最直白：「Reserve before attempting input. A reservation means the action may have happened」。

`storage.write_json`（`src/maalimbus/storage.py:24`）用唯一临时名（`mkstemp`）+ `flush` + `os.fsync` + `os.replace` 保证上一次的完整状态永远是完整的；`read_json`（`:40`）默认带 2 MiB 上限，`INTERFACE_LIMIT = 16 * 1024 * 1024`（`:21`）是为 PI 那份 3.4 MiB 的 `interface.json` 单独放宽的。

对应地，`run_wiring.settle()`（`src/maalimbus/run_wiring.py:81`）在事件被账本拒收时（`ValueError`）不是抛出去，而是记一次 `on_refusal` 然后**结束循环**——账本是权威，循环不能绕过它继续走。`settle()` 的循环还会在 `store.record()` 返回 `fresh == False`（完全相同的观测已经在账本上）时收手，因为再问一次也只会重复。

## D6 · 账本只接受页面真正能证明的事件

`run_wiring.ledger_event()`（`src/maalimbus/run_wiring.py:41`）是纯函数，输入是页面名 + 当前账本状态，输出是「结清什么」或者 `None`。三条已实现的推导：

- 站着的楼层 *n* 证明第 *n-1* 层已清（`run_wiring.py:51-55`）。第 1 层什么都不证明。
- 运行摘要（`RUN_CLAIM`，「Exploration Complete」100%）是最终胜利，但必须在五层都已入账之后（`:56-67`），因为摘要本身就是从整局画出来的。代码注释保留了这条规则为什么重要：`build/window-run-continue-2.json` 走到 RUN_CLAIM（step 52-55）却没记下任何东西，于是轮换从未前进。
- 已完成的运行用掉一个每周奖励，只能由「这一步是这次运行自己的付款」来授权（`earned_its_payout()`，`:208`）。注释同样保留了反例：一份不携带 `settled_at` 的旧账本无法判断谁最后结算，于是它返回 `False`——「不知道」不是花掉每周资源的理由（每周只有 3 个、每周重置、不结转，引用 Steam 讨论 597403944640085425）。

另有两个入口处理「游戏把运行丢掉了」：

- `expire()`（`:129`）——每周重置使会话过期时（「The previous session has expired. / Please claim your rewards.」，实机 `evidence/runtime/window-20261007-170653/frame-0009.json`），确认那一页就是「领取遗留奖励」的输入，于是把运行归档为 abandoned；轮换停在同一个队伍上准备下一次尝试，归档记录保留它已经到达的楼层与证明它的那一帧。
- `reconcile()`（`:156`）——队伍选择页只对新地牢绘制；还有进度中的运行会画 Dungeon Progress 对话框（`Resume` / `Halt Exploration`，实机 `evidence/runtime/window-20261006-025617/frame-0002.json`）。所以账本仍标为活动时走到选择页，就意味着游戏已经没有这局了。这里有一条硬约束：`phase == 'entry_pending'` 时直接 `raise ValueError('Entry confirmation pending; do not discard or retry')`（`:179`）。另有一条特例：如果这局已经 `victory` + `reward` 而只差走回入口，那么在选择页记一次 `entry_returned` 收据比丢进垃圾桶更值（`:183-197`）。

## D7 · 输入不是收款

`run_wiring.ledger_event()` 对三个页面返回 `None`（`:68-77`）：奖励确认页（`RUN_REWARD_CONFIRM`）、每周奖励询问页（`RUN_REWARD_BONUS`）、以及尚未拿到 `reward` 时的队伍页（`DUNGEON_TEAM`）。理由写在注释里：只有独立的、已验证的收据/余额事务才能记入付款。

这条与 `docs/design.md:358-371`（「Claim 与 weekly-bonus Confirm 是输入，不是 reward_received 事件」）互相印证，并由 `src/maalimbus/reward_receipt_audit.py:1`（「只读的最终付款证明；输入与任务成功都不意味着收据」）执行。同一个原则也出现在 `src/maalimbus/paid_reward_action.py:1`（「一个刚识别、持久化的奖励控件；输入绝不记作付款」）与 `src/maalimbus/run_summary.py:1`（「独立的已完成 Hard 运行摘要，绝不是付款凭证」）。

## D8 · 私有状态与 cwd / PyInstaller 解包解耦

`src/maalimbus/runtime_paths.py:8` 的 `application_root(*, executable=None, frozen=None, source_file=None, override=None)` 给出三条路径：

- 显式 `override` 优先；
- 冻结时用可执行文件的**祖父**目录（`Path(executable or sys.executable).resolve().parents[1]`，`:15`）——注释说明 Agent 与 Runner 都住在应用根的直接子目录里；
- 否则用源码文件的祖父目录（`:16`）。

模块级 `ROOT`（`:19`）在冻结时忽略 `MAALIMBUS_ROOT`，未冻结时才读它。

`data_directory(root=ROOT)`（`:23`）在 `config/user-data-root.json` 存在时重定向私有状态，并对重定向目录做三重防护：

| 检查 | 失败时抛出的错误 |
| --- | --- |
| 必须是绝对路径且存在的目录 | `Private-state directory is unavailable` |
| 目标及其所有祖先不得是符号链接或 junction | `Linked private-state directory` |
| 目标内不得再有 `user-data-root.json` | `Chained private-state binding` |

并且读取该标记文件时先校验键集合恰为 `{'version', 'directory'}` 且 `version == 1`，否则抛 `Invalid private-state binding`（`:30-31`）。

`ledger_path(value, root=ROOT)`（`:43`）是账本路径的唯一解释器：绝对路径直用；以 `config` 开头的相对路径经过 `data_directory()`，且 `..` 出现时抛 `Unsafe private ledger path`；其余相对路径按应用根解析。

## D9 · 一个 controller，跨进程的 OS 锁

`src/maalimbus/controller_lease.py:1` 是「One OS lock shared by native CLI and packaged Agent entry points」。`PROJECT.md:1344` 把「One controller, bounded session, finite node hits」列为开发契约。实测后果：`PROJECT.md:71-74` 记录了两个失败测试正好是真实运行的 App 持有 `%LOCALAPPDATA%/MaaLimbus/controller.lock`（`lease_path` 把所有 `controller.lock` 重定向到那里）造成的，App 不在跑时就消失。

## D10 · 为什么观察节点必须走 `Context.run_task`

`docs/agent-loop.md:93-103` 记录了这次事故与修法：`MaaObserver` 通过 `tasker.post_task(name)` 跑节点，而在自定义动作里不能是 `context.tasker`——框架的 task runner 是单 worker，投到那里的节点会排在**正在等它的那个任务**后面，等待撞上 deadline，然后框架的错误路径会停掉正在运行的任务，也就是这次运行本身。

所以动作给 `MaaObserver` 一个 `AgentTasker` 代理（`agent/recognition.py:1410`），它同时是 context（`.tasker` 是它自己）和 tasker（`post_task` → `Context.run_task`），跑在调用线程上同步执行。

`docs/agent-loop.md:22-27` 另有一条容易踩的语义：`MirrorLoop` 是 `{"recognition": "DirectHit", "action": "Custom", ...}`，它的 `400000` timeout 只约束 `DirectHit` 到 `MirrorLoopDone` 这一步；真正停住整局的是运行自己的 `budget`。`on_error` 为空是因为失败的运行通过自己的 journal 汇报，而不是通过 pipeline。

## D11 · PI 的 Win32 profile 是唯一的控制器真相

`src/maalimbus/windows_controller.py:9` 的 `controller_profile(interface_path, name)` 从 `assets/interface.json` 里找唯一匹配 `name` 且 `type == 'Win32'` 的 controller，匹配数不是 1 就抛 `Unknown Windows controller: {name}`；`native_methods(profile)`（`:17`）把 `screencap`/`mouse`/`keyboard` 三个字符串映射成 `MaaWin32ScreencapMethodEnum` / `MaaWin32InputMethodEnum`。`DEFAULT_CONTROLLER = 'windows-window'`（`:6`）。

PI 侧的三个 Win32 profile 与一个 Adb profile（`assets/interface.json:16/31/46/61`）：

| 名字 | 行 | screencap | mouse | keyboard |
| --- | --- | --- | --- | --- |
| `windows-window` | `interface.json:16` | `Background` | `SendMessageWithCursorPos` | `PostMessage` |
| `windows-background` | `interface.json:31` | `Background` | `SendMessageWithWindowPos` | `PostMessage` |
| `windows` | `interface.json:46` | `ScreenDC` | `Seize` | `Seize` |

### 续三：下一局证明的是点击，不是读图（2026-10-22）

`MirrorRunner` 现在有两只看门狗：`STALL_SECONDS`（300s，盯 `artifacts['heartbeat']`，防取帧函数不返回）与新的 `PROGRESS_SECONDS`（900s，盯 `artifacts['event_heartbeat']`，即 `note()` 最后一次写入的时间）。后者触发时写 `agent-no-progress.json`（带 `last_event`/`step`/`page`/`event_age_seconds`）并同样结束进程，好让外层驱动把这一局记成一条有页面的失败，而不是空转。

为什么两只要分开：能看见不等于在动。前者是"识别调用卡住"，后者是"循环还活着但不再产生任何决策"——它们的证据不同（有没有新帧 vs 有没有新事件），能采的动作也不同。

## D25 整帧扫描读不到细字，需要一块专用读取（2026-10-22）

`evidence/runtime/packaged-mirror-20261022-034711/frame-0026.png` 上明确印着 `Total Participants 8 / 12`，但该帧的 122 条 OCR 结果里没有任何一条是这块面板。原因不在坐标：`assets/resource/base/pipeline/mirror.json` 的 793 个节点里识别类型只有 `DirectHit`(755) 与 `Custom`(38)，**没有任何 OCR 节点**——文本全部来自观测任务对整帧扫一遍的副产物，细字有纹理底板时就会漏。

因此这一页的计数修复不在 Python 里，而在读取链路：需要一个 ROI 限定在计数面板、单独放大后再识别一次的读取途径（pipeline 节点 + 对应 custom recognition），循环在该页调用它拿 `n / 12`。在此之前，`party_vision` 的"读不出返回 None、不猜"仍然是正确行为——错的是它拿不到输入。

教训：连续两轮我都在调裁剪比例，而真正的问题是那块像素**从来没有被送进识别**。先问"数据有没有到这一层"，再问"这一层有没有算对"。

## D26 过场动画不是"读不懂的页面"（2026-10-22）

`evidence/runtime/packaged-mirror-20261022-043142` 打完整场战斗后停在 `window_unknown_wait`，随后升级为 `page_unreadable_after_waiting`。查帧可知那不是页面：`frame-0069` 只有 8 条碎片读数（`scading`、`Gaze of Awe`、`179`、`+5`、`5`、`151`），没有任何控件词，而且下一帧就完全不同——那是技能命中特效。

原逻辑把每一帧 `UNKNOWN` 都记进 `unknown_seen`，于是**一场普通战斗的结束动画被记成"这一页读不懂"并终止整次运行**。

现在的判定用两条合起来：**没有控件词**（`CONTROLS` 那一组）**且与上一帧不同**。两条都满足才是过场，只等待、不消耗 `unknown_seen`，另有独立上限兜底；**同一帧反复出现就不是动画**——静止而读不懂的页面仍走原来的等待→恢复→终止路径。

教训：`UNKNOWN` 是"这一帧没有页面的名字"，不是"这一帧是个页面"。把两者混在一起，就会把每一次动画都当成识别失败。

### D27 同一回合提交三次仍不动，就算棋盘在拒绝，不再重发

判"提交被吞"的旧条件要求 `plan.advance` 为真、且后继里出现 `expect` 中的页面；而战斗的提交意图 `advance` 默认是 `False`（`src/maalimbus/window.py:91` 的 `_plan` 默认值），`expect` 又同时含 `BATTLE_HUD`、`BATTLE_PLANNING` 与 `UNKNOWN`。两边合起来意味着：**棋盘忽略了这次点击，与它接受了这次点击，在页面层面完全同形**，于是"被吞"永远判不出来，循环把忽略当成成功，继续下一轮。

唯一能分开两者的事实是 HUD 自己的 `turn`，它每帧都在读。判据因此改成：同一 `turn` 再次提交、且距上次超过 25 秒（实测一次真回合 43 秒），记 `battle_submit_not_accepted`；同一 `turn` 累计到 3 次，记 `battle_submit_ignored_repeatedly` 并把 `turn_wait_until` 清零——清零等于把这一页交还给进度看门狗，于是这一局以"被拒绝的提交"为原因进入恢复，而不是在同一回合上无限空转。

判据抽成 `submit_was_ignored()`，有 6 条断言：同回合超窗为真、回合变了为假、窗口内为假、没提交过为假、本帧没读到 `turn` 为假、只差空白仍算同回合。

### D28 标题里的点不是排版，是身份：`Exploring·Floor` 仍是地图页

`HEADER_LABEL_PATTERN` 写成 `^Exploring(?:\s*Floor)?$`，把一个点当成了排版噪声；OCR 却真的会把间隔渲染成 `·`（U+00B7）。实测同一张地图相邻两帧，
`frame-0005` 读出 `Exploring Floor 3` 判成 `MAP`，`frame-0006` 读出 `Exploring·Floor` 就整页失去身份判成 `UNKNOWN`。一局 36 帧里 32 帧如此，
于是"没有意图、没有点击判定"，下游的点击投递与回合提交根本得不到行使机会。

修法不是再补一个字形特例：`normalise_header_text()` 把 `·`、`•`、`⋅`、`·`、`・`、`|` 一律折成空格并合并空白，`floor_label` 在折叠后的行上匹配。
折叠后 `frame-0006` 得到 `floor=None, pack='Sinking Pang'`——**页面是地图，层数不臆造**：数字确实没读到，就保持空。

教训：页面身份只能由该页自己的字词决定；把分隔符当噪声，会把整个页面判成不存在。

### D29 地图上"能不能走"在边的亮度里，不在节点外观里

真机把三个假设依次否掉了：小金星徽章每个节点都有，不代表可走（第四层共四个带徽章的节点，adb 直点全部无反应）；点"相邻"节点同样无反应；可走与不可走的分界是**连线的亮度**——亮青色边可走，灰色边不可走（`build/t94-now.png` 上肉眼可辨）。

项目里本来就有这条判据：`path_end(image, player)` 沿亮青边从玩家走到远端，`advance_candidates(markers, player)` 取相邻节点，`map_clicks` 里也有 `cyan_node`。它们全部以 `node_markers` 为前提，而 `node_markers` 靠节点脚下的月牙徽章做模板匹配，在当前层配色下返回 **0**；于是青边通路整条失效，只剩徽章与亮点这两种必然无效的候选。

同一层上 `path_end` 直接喂入已定位的玩家（`player_by_ring` 得到 `(972,428)`）仍返回 `None`——所以缺陷不止在入口，青边读取本身在该配色下也不成立。

结论：地图候选的正确来源是"与玩家由亮边相连的节点"，而它需要一条不依赖模板的节点集合与边的读取。在此之前，任何"换排序、调半径、改点击点"的修法都是在下游打补丁。

补充（同一层实测）：亮青边不是"亮"，是**高饱和低亮度**——HSV 实测 `H≈95-98, S≈220-250, V≈13-55`，用 `V>=120` 的掩码一个像素也取不到，这也是 `path_end` 在该帧返回 `None` 的直接原因之一。另外沿"玩家→节点"直线用 ±5 像素窗口取样无法区分可走与不可走（五个节点只得 0.81–1.0），因为背景格线本身也是青色的；判别必须落在**这条边自身**的采样上（细窄垂线取样），并把它的强度与该层其余灰边作相对比较。

### D30 地图比视口宽：平移是读取的一部分，不是恢复的附属品

**现象**。2026-10-22 的第 3 层（`Sinking Pang`）停在同一层 5/7 上反复失败：所有候选点击都 `rejected`，点自己也毫无反应，而暂停菜单一点就开（29 万像素变化），说明输入通道正常、页面也不忙。

**实测**。在实机上从队伍位置向外拖 400 ms：画面整体右移、**右侧冒出一批此前任何一帧都没有的节点**，而队伍、层数、货币都没变（29 272 像素变化，`build/t100-swipe-700.png` 对照 `build/t100-s0.png`）。也就是说：镜牢的一层**比一屏宽**，读取器只看当前视口，于是"没有可走节点"这个结论在视野不全时就是假的。

**为什么这是上游缺陷**。`RECOVERY_LADDER` 原本只有 `drag_down` / `drag_up` 两档纵向拖动，加上 `pinch_out` 与 `wait`：
一层的失败模式里，纵向（列表类页面）与横向（宽地图）是两种不同的"看不全"，只覆盖一种就等于把另一类当成"这页没路可走"。而 `no_candidate_node_observed` 正是这样得出的。

**决定**。梯子补上 `pan_left` / `pan_right`（`RECOVERY_PAN = (620, 540, 1300, 540)`，同一 1920×1080 空间，400 ms），排在两档纵向拖动之后、`wait` 之前；四档都是"移动视野、不按任何游戏控件"，因此仍可在未知布局的页面上安全尝试。判据：`tests/test_recovery_ladder.py` 现在要求四档各自生效一次（`len(device.swipes) == 4`，纵向两档 + 横向两档），并且梯子用尽后仍然结束而不是无限平移。

**边界**。平移只让读取器**有机会**看到整层，不保证那一步就一定可点；第 3 层 5/7 那两步是否还有别的原因（例如需要先通过某个交互）仍未证实，所以这一条记为"读取范围"的修复，不当作通关证据。

### D31 点击没落地不取决于分辨率，也不取决于点击点：先要把"队伍在哪"与"相邻才可点"分开

**两次单变量实验**（同一层、同一台设备、同一个 agent）：

1. **截图长边 1920 与设备原生 1280**：两种配置各发出 8 次点击，`map_click_result` 都是 3 条 `rejected`，行为完全一致。若原因是"1920 坐标没被缩回 1280"，那么去掉放大就该生效——没有。**排除坐标缩放。**
2. **逐点密集对照**：对 4 个候选（`gold_badge_node` `(479,264)`/`(479,424)`、`lit_ring` `(1247,248)`/`(310,406)`）各点一次，框内变化 2158/470/996/1106 像素——都是悬停级别，没有面板、没有位移。而对被点节点框做前后帧差，**36100 像素里 0 个变化**。

**已经成立的对照**：同一台机器上 `adb shell input tap` 点暂停键立刻开菜单（约 29 万像素变化）；此前手点一个**相邻**节点时面板立刻弹出（`Sinking Pang` + `Enter`）。所以输入通道、点击送达、页面可交互这三件事都不成立为原因。

**结论（写下而不是猜）**：剩下的解释只有"游戏只接受队伍当前所在节点相邻的点"，而 `player_by_ring` 认的橙色圆环可能只是**可达性高亮**，不是队伍本身。若队伍定位错了，一切可达性判断都建立在错的原点，于是"点谁都一样没反应"。

**因此下一步的判据（不是继续调排序）**：用"走过的节点会变暗/失去徽章"这一事实反解队伍位置，再用受控三点实验（队伍自己 / 亮边另一端 / 无关节点）验证"相邻才可点"。在此之前不动 `map_clicks` 的候选来源。

### D32 礼物目标必须来自队伍档案，不能是常量 `bleed`

**实测链**。任务设置 `mirror_initial_keyword` 的值是 `saved`；`src/maalimbus/mirror_task_options.py:16-21` 对 `saved` 不做任何覆盖；于是落到 `src/maalimbus/runner.py:169` 的默认值 `'gift_keyword': 'bleed'`。结果是：无论档案里是哪一队，礼物都按流血买。

**为什么这是缺陷**。`config/user-team-profiles.json` 里 slot 2 的 `keywords` 与 `formation_keywords` 都是 `["Charge","Tremor"]`（烧充队），而 slot 1 是 `["Bleed","Poise"]`。给烧充队买流血饰品等于把队伍与构筑拧着来；这正是"队伍修对了也打不过"的一半原因。

**决定一：槽位来自任务设置，不来自账本。** 第一版实现从 `user-run-ledger.json` 的 `active.team` 取槽位——那只是**上一局留下的记录**。玩家在 GUI 点任务开始时，游戏按任务设置自己切队（`mirror_team_mode = single`、`mirror_single_team = 2`），所以 `configured_slot()` 以任务设置为准，只有 `rotation` 模式才回退账本。**`MirrorRunner` 因此不需要持有队伍**：`next_sinner(state, team)` 的 `team` 仍由调用方传入，"这局是几号位"由任务设置与游戏决定。

**决定二：多体系队伍不能被压成一个词。** 第一版取 `sorted(队伍体系)[0]`，等于又在"充"和"震"之间替玩家做了一次选择，跟写死 `bleed` 是同一类错误。现在 `systems()` 返回全部体系（充震队是 `('charge','tremor')`），`gift_plan.wanted()` 接受 `'charge+tremor'` 或以 `+` 连接/直接传入的集合：按顺序合并、去重、全无匹配才回退 `default`。单个关键词的语义完全不变。`from_active_team()` 保留单值语义，只服务仍只吃一个关键词的调用方。

**判据**。`tests/test_team_gift_keyword.py`：任务设置优先于账本、`rotation` 仍跟账本、集合不丢体系；`tests/test_gift_plan.py`：多体系按序合并、跨体系重复只出现一次、未知体系回退默认；`wanted(plan,'tremor')` 与改动前逐字相同。全量 `1832 passed`。

**决定三：起始礼物页按体系逐栏匹配。** Grace of the Sisyphus Star 是"一栏一个体系"的选择页（Burn/Bleed/Tremor/Rupture/Sinking/Poise/Charge/Slash），复合关键词不是一个栏名，所以 `initial_gifts.group_target()` 现在按 `systems()` 的顺序逐段尝试，取页面上真实存在的第一栏；单关键词行为不变。实机判据：`initial_gift` 事件里出现实际选中的礼物名与其体系，而不是 `0/1`。



**续记（DSH）：计数读到了，判定还在用旧的读法。** D25 只在 agent 的记录里接了 4× 面板读（`party_vision.counter_reads`），`runner.py` 的队伍页判定仍调用 `participants(原始 OCR)`，于是在 `Total Participants n / 12` 明明印着的页上拿到 `None`，`party_intent` 因此从未产生（`packaged-mirror-20261022-063747`：4 次 `pre_battle_identity_report` 全无计数器、无 party_intent、无停止事件）。现在 `party_vision.deployment_count()` 先看整帧记录，读不到再直接问放大后的面板（`counter_reads`），runner 的队伍页改用它；`MirrorRunner.run_recognition_direct` 由 agent 在构造后注入，缺省为 `None` 时不启用回退。

## D33（2026-10-22）可达性只在已经量出来的格点上判断

13 次带判定的点击（`evidence/runtime/packaged-mirror-20261022-063646`）里 3 次被接受、10 次被拒。先试过"从接受/拒绝反推网格"，当场被否：那三个被接受的点彼此只差 50–100 px，说明它们是同一个格子的读数漂移，而不是三个相邻格。

`runner.one_step_from` 因此用 (190, 176, 95)：同排列距一格，或相邻排错半列。队伍位置取 `state['map_player']`，过滤后若为空则退回全部候选（不允许因为几何而卡死）。

**续记二：停止的是记账，不是读帧。** `packaged-mirror-20261022-070445` 以 `no_candidate_node_observed` 停局，但它最后四帧（frame-0017…0020）每帧都能读 4 个候选；真实原因是这 4 个 box 全在 `MapProgress.tried` 里，`remaining()` 扣空后落进了"无候选"分支。现在 `remaining()` 为空而本帧仍有候选时，清空 `tried` 重试一次，并记 `map_tried_reset`（带 `offered` 与理由）。读帧与格点常数未改。

**续记三：队伍点的调用契约。** `map_vision.player_of(image, markers)` 的第二个参数是 marker 列表；`runner.py` 曾把 `player_marker()` 返回的单个整数传进去，`player_readings` 遂在 `marker.node` 上抛 `AttributeError`。现改为 `player_of(frame, [])`（空列表是受支持的"无 marker"用法），并加异常保护。实测依据：`evidence/runtime/packaged-mirror-20261022-063646/frame-0023` 上一帧读数为 `player_readings -> [(694,384),(703,301)]`、`player_of -> (694,384)`、`train_player -> (694,384)`，两种独立读法一致；同一帧 `gold_marks` 为 0，说明该层候选并非来自徽章。

## D34（2026-10-23）"控件不在帧里"是一类，不是一个页面一条理由

窗口层的 77 条拒绝理由里，46 条以 `_not_anchored` 结尾，另有两条用不同拼写说同一件事
（`battle_has_no_proven_control`、`owned_gift_refuse_control_missing`）。它们不是 46 个页面的差异，
而是**同一个机制失败被逐页命名**：每遇到一张新页就新增一个字符串，于是没有任何调用方能对整类作出反应，
缺一个按钮就等于停窗。

`src/maalimbus/anchor.py` 把这一类收成一处：`anchor_of()` 从理由名解出缺失的控件，
`classify_refusal()` 给出 `stop_kind`（`anchor_missing` / `page_unreadable` / `held`）并附上
`anchor`、`anchor_page`（可选 `recovery_tried`）。`window._refuse()` 是**唯一**出口，理由原文一个字不改，
所以账本与既有断言不受影响。

守卫测试 `tests/test_anchor.py::test_every_refusal_in_the_window_layer_reaches_this_contract`
扫描 `window.py` 里所有 `_refuse(...)` 字面量：新建一个非锚定类拒绝而不在此声明，测试即失败——
这条反例是该类的防复发机制，也是本次改动唯一新增的"约束"。

## D36（2026-10-23）一局只有一种结束，而且它必须能被读出来

**背景。** 连续几局实机都出现同一形状：`stop_reason: null`、进程被杀、或循环"静默地"转圈几分钟。日志里能看到的只是"没有新事件"，看不出是谁停的、为什么停。

**决策。** 结束方式收敛成一张表，每种都带可检索的字段：

| 结束方式 | 谁写的 | 证据字段 |
|---|---|---|
| 循环自己判定页面级失败 | `runner._end_session` | `mirror_loop_stopped.reason` |
| 等待步连续 40 次无新页 | `wait_decision` | `loop_waited` + `the_loop_waited_without_a_new_page` |
| 超出调用方预算 | 步间检查 | `loop_deadline_exceeded` |
| 看门狗到期 | `stall_watchdog` | `window_no_progress`（并受预算钳制） |
| 控制器在点击中丢失 | `jobs.InputLost` | `the_controller_was_lost_before_the_next_input` |
| 外部按预算终止 | 驾驶器 | `the_budget_ended_the_run`（附 `note`） |

**两条不可让渡的约束。** 一是"慢点击"与"控制器已丢"必须是两个状态：前者在画面仍可读时软处理（长转场合法地超过作业期限），后者立即停，不再往空句柄上点击。二是看门狗不得活得比它守护的预算更久，被预算钳制时也不再买宽限窗口——否则"预算"就不是预算。

**反例与局限。** 该表不能覆盖"画面仍可读、但点击被框架以空 `controller_id` 拒绝"这一态：实机已对齐到 `RESUME_DIALOG` 那一次点击，成因仍在查。这类状态目前只能靠预算兜底，不能靠自身收口。

## D37（2026-10-23）一次读取不得长过它的界，看门狗必须写下那一个结束

**为什么。** 2026-10-23 连续五局（15:33、15:47、16:07、16:17、16:32，`packaged-mirror-20261023-153338` … `163257`）都是同一个形状：`loop_heartbeat step=4 page=DRIVE` → `map_observed RESUME_DIALOG` → `window_intent RESUME_DIALOG` → **整整 380 s 日志静默** → 只剩一条 `window_no_progress`。`tools/audit_runs.py` 对整份归档给出的数字是 **142 局、81 局有 stop、51 局死得没有 stop**，其中 16 局最后一条事件就是 `window_no_progress`。

两个缺陷共享这个形状，而且 D36 的表格早就写下了它们、只是没有落实：

1. **预算是"步间"的，管不住原生调用。** 点击之后的就地 settle 读取不传 deadline，于是继承全局预算；一次卡住的节点读取可以吃掉剩下的全部预算，而循环无法打断一个已经在飞的调用。同一类缺陷当天已在 `7b91b6e` 里修过——但只修了模块级的 `_settle()`，`MirrorRunner.step` 里的第二处没动。修在两道门中的一道，等于没修。
2. **进度看门狗不写结束。** 画面看门狗（`_record_stall`）在 `os._exit(4)` 之前写规范的 `mirror_loop_stopped`；进度看门狗（`_record_no_progress`）只写自己的诊断。于是 D36 表格里"看门狗到期"那一行的结束记录，对真正开火的那个看门狗并不存在。

**决定。**
- `MirrorRunner._observe` 把每次读取钳在 `ONE_READ_SECONDS = 30.0`（并与剩余预算取 `min`），并在 `artifacts['reading']` 记下它进入的 phase。超时的读取现在**作为一次读取失败、在步内失败**，循环走普通的具名出口（`the_task_raised_before_the_next_input` + `no page for this frame`），而不是等看门狗。
- `_reading_report()` 把这段记录变成结束记录的一部分：`in_flight_phase`、`in_flight_seconds`，调用还在飞时 `in_flight: true`（返回后是 `lasted_seconds`）。
- `_write_ending(stop_path, record)` 是两个看门狗唯一的结束写入口：`mirror_loop_stopped` 带 reason / stop_path / step / page / last_event 与在飞字段。`stop_path` 取值 `'stall_watchdog'` 与 `'no_progress_watchdog'`。

**必须继续通过的反例。** 已经返回的慢读取带 `lasted_seconds`、`in_flight: false`（慢不等于卡死）；一直有帧的循环不惊动画面看门狗；看门狗不得长过它守护的运行（`jobs.bounded_limit`：450 s 预算把 900 s 窗口钳到剩余时间，任一侧为 `None` 时原样返回）。

**局限。** `runner.py` 里还剩一处只拿到全局 deadline 的步内原生等待：老位置 3412 的节点动作 `run_node(self.tasker, plan['node'], self.deadline)`——故意没钳，因为 pipeline 节点可能自带内部等待。诊断用的 CLI 路径（`one_shot_click`、`one_shot_swipe`、`observed_page`、`lux_task`、`reward_task`）仍用调用方的 deadline，它们不在循环里。本决定加上的规则是：**runner 自己的读取门要有界**；再开一道门需要它自己的理由，而不是共用一条。

**证据** —— `tests/test_settle_deadline.py`（9 条）：无调用方 deadline 时 runner 读取仍有界；更紧的运行 deadline 仍然优先；卡死的节点读取会返回而不是吃掉整局；卡死的读取在 10 s 内结束本局，且失败的名字出现在 `mirror_session_ended` 里。`tests/test_stall_watch.py`（10 条）：进度看门狗先写 `window_no_progress`、再写 `mirror_loop_stopped(stop_path=no_progress_watchdog)`，带 `in_flight_phase='settle'`、`page='RESUME_DIALOG'`、`step=4`、`in_flight_seconds > 300`；已返回的读取不算卡死；画面看门狗也带同样的面包屑；看门狗不长过它守护的运行。

## D38（2026-10-23）看门狗随它守护的那一局一起退休

**为什么。** `stall_watchdog` 是一个会结束**进程**（`os._exit(4)`）的守护线程，但它不知道它守护的那一局是否还在。2026-10-23 实测：`pytest tests/test_agent_loop.py` 18 条测试 5.7 s 全过、返回 0，随后进程被**一局早已结束的运行**留下的进度看门狗在 **5.7 s 后**杀掉——两次，退出码 4、没有摘要。同一形状也解释了"51/142 局死得没有 stop"的一部分：`os._exit` 什么都不写，而一局结束后才开火的看门狗根本没有日志可写。

看门狗留着很便宜，却无法界定范围：`exit(4)` 说不出"这个进程是因为 X 局卡死才死的"，所以只能让看门狗自己去问。

**决定。**
- `stall_watchdog(..., alive=None)` 在每次等待之前与之后各查一次 `alive()`；已退休的看门狗直接返回，不写记录、不退出。
- `MirrorRunner._start_stall_watch` 把凭证放在 `self._watch_live`（`threading.Event`，在两个线程启动前 set），两个看门狗都拿到 `alive=live.is_set`；同一个 runner 再调一次 `run()` 会重新武装。
- `MirrorRunner.run` 现在是薄包装：`try: return self._walk(...) finally: self._retire_watches()`。走路由公开方法搬进 `_walk`，这样任何出口（包括循环没接的异常）都不可能跳过退休。

**必须继续通过的反例。** 运行还活着、页面真冻住时，看门狗仍然结束进程（`test_the_third_wait_still_ends_the_process`、`test_the_watch_ends_a_loop_that_stopped_producing_frames`）。退休只关于"这一局结束了"，从不关于"这次停顿不方便"。

**局限。** 退休只在每个等待周期开头检查，所以看门狗如果正**在** `on_stall` 里而这一局结束，它仍可能把那条记录写完。这是有意的：记录是证据；随后那次退出因为下一轮会重查 `alive()` 而不可达——但一个卡在 `on_stall` 里的看门狗仍能拖死进程。`on_stall` 写文件不加锁，所以风险是残缺记录，不是挂起。

**证据。** `tests/test_stall_watch.py`：`test_a_watch_whose_run_is_over_never_ends_anything`（不等待、不写、不退出）、`test_a_watch_retires_between_two_waits`、`test_the_loop_retires_its_watches_when_it_returns`（真实 `run()` 返回后 `_watch_live` 已清空，再启动会重新武装）。端到端：同一进程里 `python -m pytest tests/test_agent_loop.py -q` 之后停 20 s，从 `exit 4` 变成 `survived 20s`。

## D39（2026-10-23）已经自己判定过的记录，不是待分类的散文

**为什么。** 三条守卫至少在 HEAD 上红了一天，被当噪音背着了：

- `tests/test_stop_kinds.py`：`196 unmapped reason names (baseline 187)`
- `tests/test_reason_provenance.py::test_every_reason_name_has_exactly_one_role`：`new provenance conflicts: {'the_click_left_no_trace'}`
- `tests/test_reason_provenance.py::test_a_failure_name_without_a_kind_only_gets_rarer`：`7 failure names without a kind (baseline 0)`

七个名字全都是"已经自己说了自己是什么"的记录里的标签：`click_trace.classify` 返回 `{'kind', 'action', 'reason'}`；`jobs.controller_ready` 返回 `{'ready', 'reason'}`；`wait_decision` 返回 `{'note', 'stop', 'reason'}`。provenance 走查器对所有 dict 只有一条规则——「`_refuse`/`_stop` 位置里的 `reason` 是失败，否则散文只有在规划函数里才算意图，其余都算失败」——于是 `the_controller_id_is_present`（就绪检查的**成功**）被当成候选失败，守卫便要求词表去命名三个根本不是失败的东西。

更深的缺陷在**度量**上，不在那七个名字：数标签而不是数失败，守卫就在把错的量做棘轮——诚实的代码让它红，不诚实的代码让它绿；它的基线（187）被一路上调来吸收漂移，这正是守卫本来要防的那种失败模式。

**决定。**
- `reason_provenance.DECIDED_KEYS = ('kind', 'verdict')`、`DECIDED_BOOLS = ('ready', 'passed', 'ok', 'succeeded', 'stop')`：记录在这些键下带常量时，它的 `reason` 是*证据*（`decided@<owner>`），不是需要发明分类的失败。裸 `{'reason': …}` 记录不变，仍然算失败。
- `tests/test_stop_kinds.py` 改为数棘轮真正的对象：`UNMAPPED_FAILURE_BASELINE = 26`（provenance 判为失败 ∧ 未映射），取代 `UNMAPPED_BASELINE = 187`（全部 198 个字面量，其中 82 个是意图、4 个是结果）。
- `tools/audit_vocabulary.py` 并排打印两个角色模型，让分歧变成一个数字：`unmapped 196`、`provenance 判失败 26`、`散文模型判失败 42`、`两个模型在 95 个未映射名字上不一致`。

**必须继续通过的反例。** `_refuse(result, 'the_page_never_moved', None)` 既是失败又是标签（`{'failure', 'evidence'}`）——"已判定"不能豁免拒绝对位点。带布尔旗标但没有判定键的记录（`{'note': …, 'stop': False, 'reason': …}`）只因为 `stop` 在 `DECIDED_BOOLS` 里才算证据；裸 `{'reason': 'the_screen_never_answered'}` 仍是失败。

**局限。** `DECIDED_BOOLS` 是白名单而不是通则：用别的键（`status`、`state`）自我判定的新记录在被加进名单前会被误读。名单刻意很小，审计工具会打印分歧数，所以漂移会以数字出现，而不是以一条被人消音的红守卫出现。

**证据。** `tests/test_reason_provenance.py`：`test_a_record_that_names_its_own_class_needs_no_kind`、`test_a_decision_in_prose_alone_is_still_a_failure`、`test_a_refused_name_is_a_failure_wherever_it_is_also_a_label`、`test_the_exemption_is_not_switched_on_for_a_bare_boolean_flag`。`python tools/run_tests.py tests/test_reason_provenance.py tests/test_stop_kinds.py tests/test_anchor.py -q` → 30 passed；`python tools/audit_vocabulary.py` → exit 0，只剩两条被批准的冲突。

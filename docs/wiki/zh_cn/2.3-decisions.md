## D1 · Maa 负责设备，Python 负责判断

`PROJECT.md:1338-1339` 把这条写成开发契约：Maa 拥有截图/输入与有界 Pipeline 调度，纯 Python 给选项排序，Agent 返回识别框与状态更新。直接后果是 `maa` 只出现在少数边界模块里，而且大多推迟到调用点：实测在**模块顶层**直接 import `maa` 的有 5 个文件——`src/maalimbus/adb_device.py:15-17`（`AdbController` / `MaaAdbInputMethodEnum` / `Toolkit`）、`src/maalimbus/battle_counter_native.py:3`、`src/maalimbus/deployment_availability_native.py:7`、`src/maalimbus/floor_trial_vision.py:3`、`src/maalimbus/shop_native.py:3`；另有 6 处把 import 放进函数体内——`windows_controller.native_methods()`（`src/maalimbus/windows_controller.py:18`）、`src/maalimbus/neural_shadow.py:132`、`src/maalimbus/reward_cost.py:39`、`src/maalimbus/overlay_dismissal.py:28`、`src/maalimbus/owned_inventory.py:113` 与 `:128`、`src/maalimbus/deployment_numbers_native.py:7`。这使得绝大多数判定可以在 128 个 `tests/*.py` 文件里用归档帧复现。

## D2 · 循环是库，页面与输入是注入的两个缝

`docs/runner.md:5-14` 记录了动机：循环原先住在 `tools/window_step.py`，那是个 CLI 工具，自己建 ADB controller、自己截图、自己点击，别的东西开不动它，也没有设备就测不了。

两个缝的定义就在 `src/maalimbus/runner.py`：

```python
class Device(Protocol):          # runner.py:251
    def screencap(self) -> np.ndarray: ...   # BGR，已在 1920x1080 空间
    def click(self, x: int, y: int) -> None: ...
    def swipe(self, x1, y1, x2, y2, duration_ms: int) -> None: ...
    def key(self, code: int) -> None: ...    # 可选，可以抛 NotImplementedError
```

三个实现：

- `MaaDevice(controller, *, wait=None, target_long_side=1920, deadline=None)`（`:273`）——包 `context.tasker.controller`，每次调用投递 job 并等完才返回，所以 `click()` 返回就等于触摸落地；构造函数设 `set_screenshot_target_long_side(target_long_side)`，这正是把帧钉到识别空间的那一步。
- `LocalDevice(...)`（`:323`）——给 CLI 那份 controller 用同样的映射，另有 `foreground()` 供 CLI 打印摘要。
- `FakeDevice(frames=(), foreground=None)`（`:387`）——重放帧并记住发出去的东西。

`Observer` Protocol 在 `:551`，只需一个 `directory: Path` 与 `observe(*, deadline=None) -> dict`。`MaaObserver(context, directory=None, *, pipeline='WindowMapObserve', battle_pipeline='WindowBattleObserve')`（`:598`）跑 Agent 自己的识别节点并读回它记录的页面；`FrameObserver(directory, frames=(), *, index=0, settings=None)`（`:567`）重放归档的 `frame-*.json`。

`MirrorRunner`（`:1277`）的签名是：

```python
MirrorRunner(device, *, settings, locale='en', registry=None, store=None,
             directory=None, journal=None, flow=None, log=None,
             observer=None, roots=None, run_id=None, result=None)
```

`step()`（`:1436`）返回 `{'page','reason','target','input_sent','event','stopped','done','observation', ...}`，其中 `stopped` 命名结束这个窗口的条件，`observation` 就是 CLI 写进 `build/window-debug/<label>/frame-*.json` 的那条记录。`run(*, steps=300, interval=6.0, round_limit=5, deadline=None)`（`:2756`）是外层循环。

同一个循环现在有两个前端：CLI（`tools/window_step.py`）与 App（`MirrorLoopAction`，`agent/recognition.py:1526-1575`）。两者都构造 `MirrorRunner`，参数集完全相同——`docs/agent-loop.md:40-48` 列出 `custom_action_param` 接受的每一个 CLI 名字。

## D3 · 一页最多一个输入，没证据就拒绝

`src/maalimbus/window.py:15-19` 把四条规则写在模块 docstring 里：

1. 一页一次计划只发一个输入；
2. 没有可靠控件的页面拒绝而不是猜坐标；
3. 只有后继页落在期望集合里这次点击才算被接受，否则记 `unexpected_successor` 并停窗；
4. 战斗回合只在游戏自己显示 `START` 时提交。

拒绝的实现是 `_refuse(page, reason)`（`window.py:106`）返回一个 `action='record'` 的计划——不是异常，也不是默认坐标。`plan_step()`（`window.py:110`）是唯一入口，`_plan_step()`（`:139`）是那张大表。

`window.py` 里还有两个辅助判断：`successor_ok(plan, page)`（`:1032`）与 `step_result(plan, *, sent, before, after, page, frame_changed=False)`（`:1052`）。另外 `ANY = '*'`（`:33`）是「关闭浮层」这类动作的期望哨兵：后继由**被覆盖的页面消失**证明，而不是由它露出了哪一页证明——浮层的卡片会走过很多不同页面，没有正面清单能穷举，但「仍然是浮层」是可判定的失败。

## D4 · 一张「永远不点」的控件黑名单

`FORBIDDEN_CONTROLS`（`src/maalimbus/window.py:50-63`）列出 14 个控件。它们在被点击时会丢掉整局运行或被放弃的奖励，但它们的文案又是识别页面身份的依据，所以**保留为锚点、拒绝为目标**：

```
'resume.halt_button', 'reward_card.cancel_button', 'gift_pick.refuse_button',
'gift_warning.confirm_button', 'entry_confirm.cancel_button', 'level_warning.cancel_button',
'star_confirm.cancel_button', 'initial_gifts.refuse_button', 'gift_search_forgo.cancel_button',
'event_check.skip_button',           # 点了等于没人尝试掷骰，直接放弃这次检定
'run_reward.give_up_button',         # 丢掉五层楼的运行
'run_reward_confirm.cancel_button',  # 关掉领取询问而不领取
'window_reset.confirm_button',       # 每周重置通知的 Confirm 会离开地牢
'expired_session.cancel_button'      # 关掉过期会话就留下未领取的奖励
```

强制点在 `window.py:128-135`：任何计划的目标若落在黑名单里，直接改写成 `control_is_forbidden` 拒绝。仅有两处显式豁免：

- `page == 'STAR_CONFIRM'` 且目标 `star_confirm.cancel_button` 且原因为 `incomplete_graces_return_to_selection`；
- `page == 'GIFT_PICK'` 且目标 `gift_pick.refuse_button` 且原因为 `refuse_proven_owned_single_free_gift`。

## D5 · 输入之前先持久化意图

每一个 `*_transaction.py` 都是同一个形状：**先落盘再输入，没被证明的后置条件绝不允许第二次输入**。`shop_transaction.py:1` 的 docstring 说得最直白：「Reserve before attempting input. A reservation means the action may have happened」。

`storage.write_json`（`src/maalimbus/storage.py:24`）用唯一临时名（`mkstemp`）+ `flush` + `os.fsync` + `os.replace` 保证上一次的完整状态永远是完整的；`read_json`（`:40`）默认带 2 MiB 上限，`INTERFACE_LIMIT = 16 * 1024 * 1024`（`:21`）是为 PI 那份 3.4 MiB 的 `interface.json` 单独放宽的。

对应地，`run_wiring.settle()`（`src/maalimbus/run_wiring.py:81`）在事件被账本拒收时（`ValueError`）不是抛出去，而是记一次 `on_refusal` 然后**结束循环**——账本是权威，循环不能绕过它继续走。`settle()` 的循环还会在 `store.record()` 返回 `fresh == False`（完全相同的观测已经在账本上）时收手，因为再问一次也只会重复。

## D6 · 账本只接受页面真正能证明的事件

`run_wiring.ledger_event()`（`src/maalimbus/run_wiring.py:41`）是纯函数，输入是页面名 + 当前账本状态，输出是「结清什么」或者 `None`。三条已实现的推导：

- 站着的楼层 *n* 证明第 *n-1* 层已清（`run_wiring.py:51-55`）。第 1 层什么都不证明。
- 运行摘要（`RUN_CLAIM`，「Exploration Complete」100%）是最终胜利，但必须在五层都已入账之后（`:56-67`），因为摘要本身就是从整局画出来的。代码注释保留了这条规则为什么重要：`build/window-run-continue-2.json` 走到 RUN_CLAIM（step 52-55）却没记下任何东西，于是轮换从未前进。
- 已完成的运行用掉一个每周奖励，只能由「这一步是这次运行自己的付款」来授权（`earned_its_payout()`，`:208`）。注释同样保留了反例：一份不携带 `settled_at` 的旧账本无法判断谁最后结算，于是它返回 `False`——「不知道」不是花掉每周资源的理由（每周只有 3 个、每周重置、不结转，引用 Steam 讨论 597403944640085425）。

另有两个入口处理「游戏把运行丢掉了」：

- `expire()`（`:129`）——每周重置使会话过期时（「The previous session has expired. / Please claim your rewards.」，实机 `evidence/runtime/window-20261007-170653/frame-0009.json`），确认那一页就是「领取遗留奖励」的输入，于是把运行归档为 abandoned；轮换停在同一个队伍上准备下一次尝试，归档记录保留它已经到达的楼层与证明它的那一帧。
- `reconcile()`（`:156`）——队伍选择页只对新地牢绘制；还有进度中的运行会画 Dungeon Progress 对话框（`Resume` / `Halt Exploration`，实机 `evidence/runtime/window-20261006-025617/frame-0002.json`）。所以账本仍标为活动时走到选择页，就意味着游戏已经没有这局了。这里有一条硬约束：`phase == 'entry_pending'` 时直接 `raise ValueError('Entry confirmation pending; do not discard or retry')`（`:179`）。另有一条特例：如果这局已经 `victory` + `reward` 而只差走回入口，那么在选择页记一次 `entry_returned` 收据比丢进垃圾桶更值（`:183-197`）。

## D7 · 输入不是收款

`run_wiring.ledger_event()` 对三个页面返回 `None`（`:68-77`）：奖励确认页（`RUN_REWARD_CONFIRM`）、每周奖励询问页（`RUN_REWARD_BONUS`）、以及尚未拿到 `reward` 时的队伍页（`DUNGEON_TEAM`）。理由写在注释里：只有独立的、已验证的收据/余额事务才能记入付款。

这条与 `docs/design.md:358-371`（「Claim 与 weekly-bonus Confirm 是输入，不是 reward_received 事件」）互相印证，并由 `src/maalimbus/reward_receipt_audit.py:1`（「只读的最终付款证明；输入与任务成功都不意味着收据」）执行。同一个原则也出现在 `src/maalimbus/paid_reward_action.py:1`（「一个刚识别、持久化的奖励控件；输入绝不记作付款」）与 `src/maalimbus/run_summary.py:1`（「独立的已完成 Hard 运行摘要，绝不是付款凭证」）。

## D8 · 私有状态与 cwd / PyInstaller 解包解耦

`src/maalimbus/runtime_paths.py:8` 的 `application_root(*, executable=None, frozen=None, source_file=None, override=None)` 给出三条路径：

- 显式 `override` 优先；
- 冻结时用可执行文件的**祖父**目录（`Path(executable or sys.executable).resolve().parents[1]`，`:15`）——注释说明 Agent 与 Runner 都住在应用根的直接子目录里；
- 否则用源码文件的祖父目录（`:16`）。

模块级 `ROOT`（`:19`）在冻结时忽略 `MAALIMBUS_ROOT`，未冻结时才读它。

`data_directory(root=ROOT)`（`:23`）在 `config/user-data-root.json` 存在时重定向私有状态，并对重定向目录做三重防护：

| 检查 | 失败时抛出的错误 |
| --- | --- |
| 必须是绝对路径且存在的目录 | `Private-state directory is unavailable` |
| 目标及其所有祖先不得是符号链接或 junction | `Linked private-state directory` |
| 目标内不得再有 `user-data-root.json` | `Chained private-state binding` |

并且读取该标记文件时先校验键集合恰为 `{'version', 'directory'}` 且 `version == 1`，否则抛 `Invalid private-state binding`（`:30-31`）。

`ledger_path(value, root=ROOT)`（`:43`）是账本路径的唯一解释器：绝对路径直用；以 `config` 开头的相对路径经过 `data_directory()`，且 `..` 出现时抛 `Unsafe private ledger path`；其余相对路径按应用根解析。

## D9 · 一个 controller，跨进程的 OS 锁

`src/maalimbus/controller_lease.py:1` 是「One OS lock shared by native CLI and packaged Agent entry points」。`PROJECT.md:1344` 把「One controller, bounded session, finite node hits」列为开发契约。实测后果：`PROJECT.md:71-74` 记录了两个失败测试正好是真实运行的 App 持有 `%LOCALAPPDATA%/MaaLimbus/controller.lock`（`lease_path` 把所有 `controller.lock` 重定向到那里）造成的，App 不在跑时就消失。

## D10 · 为什么观察节点必须走 `Context.run_task`

`docs/agent-loop.md:93-103` 记录了这次事故与修法：`MaaObserver` 通过 `tasker.post_task(name)` 跑节点，而在自定义动作里不能是 `context.tasker`——框架的 task runner 是单 worker，投到那里的节点会排在**正在等它的那个任务**后面，等待撞上 deadline，然后框架的错误路径会停掉正在运行的任务，也就是这次运行本身。

所以动作给 `MaaObserver` 一个 `AgentTasker` 代理（`agent/recognition.py:1410`），它同时是 context（`.tasker` 是它自己）和 tasker（`post_task` → `Context.run_task`），跑在调用线程上同步执行。

`docs/agent-loop.md:22-27` 另有一条容易踩的语义：`MirrorLoop` 是 `{"recognition": "DirectHit", "action": "Custom", ...}`，它的 `400000` timeout 只约束 `DirectHit` 到 `MirrorLoopDone` 这一步；真正停住整局的是运行自己的 `budget`。`on_error` 为空是因为失败的运行通过自己的 journal 汇报，而不是通过 pipeline。

## D11 · PI 的 Win32 profile 是唯一的控制器真相

`src/maalimbus/windows_controller.py:9` 的 `controller_profile(interface_path, name)` 从 `assets/interface.json` 里找唯一匹配 `name` 且 `type == 'Win32'` 的 controller，匹配数不是 1 就抛 `Unknown Windows controller: {name}`；`native_methods(profile)`（`:17`）把 `screencap`/`mouse`/`keyboard` 三个字符串映射成 `MaaWin32ScreencapMethodEnum` / `MaaWin32InputMethodEnum`。`DEFAULT_CONTROLLER = 'windows-window'`（`:6`）。

PI 侧的三个 Win32 profile 与一个 Adb profile（`assets/interface.json:16/31/46/61`）：

| 名字 | 行 | screencap | mouse | keyboard |
| --- | --- | --- | --- | --- |
| `windows-window` | `interface.json:16` | `Background` | `SendMessageWithCursorPos` | `PostMessage` |
| `windows-background` | `interface.json:31` | `Background` | `SendMessageWithWindowPos` | `PostMessage` |
| `windows` | `interface.json:46` | `ScreenDC` | `Seize` | `Seize` |

### 续三：下一局证明的是点击，不是读图（2026-10-22）

`MirrorRunner` 现在有两只看门狗：`STALL_SECONDS`（300s，盯 `artifacts['heartbeat']`，防取帧函数不返回）与新的 `PROGRESS_SECONDS`（900s，盯 `artifacts['event_heartbeat']`，即 `note()` 最后一次写入的时间）。后者触发时写 `agent-no-progress.json`（带 `last_event`/`step`/`page`/`event_age_seconds`）并同样结束进程，好让外层驱动把这一局记成一条有页面的失败，而不是空转。

为什么两只要分开：能看见不等于在动。前者是"识别调用卡住"，后者是"循环还活着但不再产生任何决策"——它们的证据不同（有没有新帧 vs 有没有新事件），能采的动作也不同。

## D25 整帧扫描读不到细字，需要一块专用读取（2026-10-22）

`evidence/runtime/packaged-mirror-20261022-034711/frame-0026.png` 上明确印着 `Total Participants 8 / 12`，但该帧的 122 条 OCR 结果里没有任何一条是这块面板。原因不在坐标：`assets/resource/base/pipeline/mirror.json` 的 793 个节点里识别类型只有 `DirectHit`(755) 与 `Custom`(38)，**没有任何 OCR 节点**——文本全部来自观测任务对整帧扫一遍的副产物，细字有纹理底板时就会漏。

因此这一页的计数修复不在 Python 里，而在读取链路：需要一个 ROI 限定在计数面板、单独放大后再识别一次的读取途径（pipeline 节点 + 对应 custom recognition），循环在该页调用它拿 `n / 12`。在此之前，`party_vision` 的"读不出返回 None、不猜"仍然是正确行为——错的是它拿不到输入。

教训：连续两轮我都在调裁剪比例，而真正的问题是那块像素**从来没有被送进识别**。先问"数据有没有到这一层"，再问"这一层有没有算对"。

## D26 过场动画不是"读不懂的页面"（2026-10-22）

`evidence/runtime/packaged-mirror-20261022-043142` 打完整场战斗后停在 `window_unknown_wait`，随后升级为 `page_unreadable_after_waiting`。查帧可知那不是页面：`frame-0069` 只有 8 条碎片读数（`scading`、`Gaze of Awe`、`179`、`+5`、`5`、`151`），没有任何控件词，而且下一帧就完全不同——那是技能命中特效。

原逻辑把每一帧 `UNKNOWN` 都记进 `unknown_seen`，于是**一场普通战斗的结束动画被记成"这一页读不懂"并终止整次运行**。

现在的判定用两条合起来：**没有控件词**（`CONTROLS` 那一组）**且与上一帧不同**。两条都满足才是过场，只等待、不消耗 `unknown_seen`，另有独立上限兜底；**同一帧反复出现就不是动画**——静止而读不懂的页面仍走原来的等待→恢复→终止路径。

教训：`UNKNOWN` 是"这一帧没有页面的名字"，不是"这一帧是个页面"。把两者混在一起，就会把每一次动画都当成识别失败。

### D27 同一回合提交三次仍不动，就算棋盘在拒绝，不再重发

判"提交被吞"的旧条件要求 `plan.advance` 为真、且后继里出现 `expect` 中的页面；而战斗的提交意图 `advance` 默认是 `False`（`src/maalimbus/window.py:91` 的 `_plan` 默认值），`expect` 又同时含 `BATTLE_HUD`、`BATTLE_PLANNING` 与 `UNKNOWN`。两边合起来意味着：**棋盘忽略了这次点击，与它接受了这次点击，在页面层面完全同形**，于是"被吞"永远判不出来，循环把忽略当成成功，继续下一轮。

唯一能分开两者的事实是 HUD 自己的 `turn`，它每帧都在读。判据因此改成：同一 `turn` 再次提交、且距上次超过 25 秒（实测一次真回合 43 秒），记 `battle_submit_not_accepted`；同一 `turn` 累计到 3 次，记 `battle_submit_ignored_repeatedly` 并把 `turn_wait_until` 清零——清零等于把这一页交还给进度看门狗，于是这一局以"被拒绝的提交"为原因进入恢复，而不是在同一回合上无限空转。

判据抽成 `submit_was_ignored()`，有 6 条断言：同回合超窗为真、回合变了为假、窗口内为假、没提交过为假、本帧没读到 `turn` 为假、只差空白仍算同回合。

### D28 标题里的点不是排版，是身份：`Exploring·Floor` 仍是地图页

`HEADER_LABEL_PATTERN` 写成 `^Exploring(?:\s*Floor)?$`，把一个点当成了排版噪声；OCR 却真的会把间隔渲染成 `·`（U+00B7）。实测同一张地图相邻两帧，
`frame-0005` 读出 `Exploring Floor 3` 判成 `MAP`，`frame-0006` 读出 `Exploring·Floor` 就整页失去身份判成 `UNKNOWN`。一局 36 帧里 32 帧如此，
于是"没有意图、没有点击判定"，下游的点击投递与回合提交根本得不到行使机会。

修法不是再补一个字形特例：`normalise_header_text()` 把 `·`、`•`、`⋅`、`·`、`・`、`|` 一律折成空格并合并空白，`floor_label` 在折叠后的行上匹配。
折叠后 `frame-0006` 得到 `floor=None, pack='Sinking Pang'`——**页面是地图，层数不臆造**：数字确实没读到，就保持空。

教训：页面身份只能由该页自己的字词决定；把分隔符当噪声，会把整个页面判成不存在。

### D29 地图上"能不能走"在边的亮度里，不在节点外观里

真机把三个假设依次否掉了：小金星徽章每个节点都有，不代表可走（第四层共四个带徽章的节点，adb 直点全部无反应）；点"相邻"节点同样无反应；可走与不可走的分界是**连线的亮度**——亮青色边可走，灰色边不可走（`build/t94-now.png` 上肉眼可辨）。

项目里本来就有这条判据：`path_end(image, player)` 沿亮青边从玩家走到远端，`advance_candidates(markers, player)` 取相邻节点，`map_clicks` 里也有 `cyan_node`。它们全部以 `node_markers` 为前提，而 `node_markers` 靠节点脚下的月牙徽章做模板匹配，在当前层配色下返回 **0**；于是青边通路整条失效，只剩徽章与亮点这两种必然无效的候选。

同一层上 `path_end` 直接喂入已定位的玩家（`player_by_ring` 得到 `(972,428)`）仍返回 `None`——所以缺陷不止在入口，青边读取本身在该配色下也不成立。

结论：地图候选的正确来源是"与玩家由亮边相连的节点"，而它需要一条不依赖模板的节点集合与边的读取。在此之前，任何"换排序、调半径、改点击点"的修法都是在下游打补丁。

补充（同一层实测）：亮青边不是"亮"，是**高饱和低亮度**——HSV 实测 `H≈95-98, S≈220-250, V≈13-55`，用 `V>=120` 的掩码一个像素也取不到，这也是 `path_end` 在该帧返回 `None` 的直接原因之一。另外沿"玩家→节点"直线用 ±5 像素窗口取样无法区分可走与不可走（五个节点只得 0.81–1.0），因为背景格线本身也是青色的；判别必须落在**这条边自身**的采样上（细窄垂线取样），并把它的强度与该层其余灰边作相对比较。

### D30 地图比视口宽：平移是读取的一部分，不是恢复的附属品

**现象**。2026-10-22 的第 3 层（`Sinking Pang`）停在同一层 5/7 上反复失败：所有候选点击都 `rejected`，点自己也毫无反应，而暂停菜单一点就开（29 万像素变化），说明输入通道正常、页面也不忙。

**实测**。在实机上从队伍位置向外拖 400 ms：画面整体右移、**右侧冒出一批此前任何一帧都没有的节点**，而队伍、层数、货币都没变（29 272 像素变化，`build/t100-swipe-700.png` 对照 `build/t100-s0.png`）。也就是说：镜牢的一层**比一屏宽**，读取器只看当前视口，于是"没有可走节点"这个结论在视野不全时就是假的。

**为什么这是上游缺陷**。`RECOVERY_LADDER` 原本只有 `drag_down` / `drag_up` 两档纵向拖动，加上 `pinch_out` 与 `wait`：
一层的失败模式里，纵向（列表类页面）与横向（宽地图）是两种不同的"看不全"，只覆盖一种就等于把另一类当成"这页没路可走"。而 `no_candidate_node_observed` 正是这样得出的。

**决定**。梯子补上 `pan_left` / `pan_right`（`RECOVERY_PAN = (620, 540, 1300, 540)`，同一 1920×1080 空间，400 ms），排在两档纵向拖动之后、`wait` 之前；四档都是"移动视野、不按任何游戏控件"，因此仍可在未知布局的页面上安全尝试。判据：`tests/test_recovery_ladder.py` 现在要求四档各自生效一次（`len(device.swipes) == 4`，纵向两档 + 横向两档），并且梯子用尽后仍然结束而不是无限平移。

**边界**。平移只让读取器**有机会**看到整层，不保证那一步就一定可点；第 3 层 5/7 那两步是否还有别的原因（例如需要先通过某个交互）仍未证实，所以这一条记为"读取范围"的修复，不当作通关证据。

### D31 点击没落地不取决于分辨率，也不取决于点击点：先要把"队伍在哪"与"相邻才可点"分开

**两次单变量实验**（同一层、同一台设备、同一个 agent）：

1. **截图长边 1920 与设备原生 1280**：两种配置各发出 8 次点击，`map_click_result` 都是 3 条 `rejected`，行为完全一致。若原因是"1920 坐标没被缩回 1280"，那么去掉放大就该生效——没有。**排除坐标缩放。**
2. **逐点密集对照**：对 4 个候选（`gold_badge_node` `(479,264)`/`(479,424)`、`lit_ring` `(1247,248)`/`(310,406)`）各点一次，框内变化 2158/470/996/1106 像素——都是悬停级别，没有面板、没有位移。而对被点节点框做前后帧差，**36100 像素里 0 个变化**。

**已经成立的对照**：同一台机器上 `adb shell input tap` 点暂停键立刻开菜单（约 29 万像素变化）；此前手点一个**相邻**节点时面板立刻弹出（`Sinking Pang` + `Enter`）。所以输入通道、点击送达、页面可交互这三件事都不成立为原因。

**结论（写下而不是猜）**：剩下的解释只有"游戏只接受队伍当前所在节点相邻的点"，而 `player_by_ring` 认的橙色圆环可能只是**可达性高亮**，不是队伍本身。若队伍定位错了，一切可达性判断都建立在错的原点，于是"点谁都一样没反应"。

**因此下一步的判据（不是继续调排序）**：用"走过的节点会变暗/失去徽章"这一事实反解队伍位置，再用受控三点实验（队伍自己 / 亮边另一端 / 无关节点）验证"相邻才可点"。在此之前不动 `map_clicks` 的候选来源。

### D32 礼物目标必须来自队伍档案，不能是常量 `bleed`

**实测链**。任务设置 `mirror_initial_keyword` 的值是 `saved`；`src/maalimbus/mirror_task_options.py:16-21` 对 `saved` 不做任何覆盖；于是落到 `src/maalimbus/runner.py:169` 的默认值 `'gift_keyword': 'bleed'`。结果是：无论档案里是哪一队，礼物都按流血买。

**为什么这是缺陷**。`config/user-team-profiles.json` 里 slot 2 的 `keywords` 与 `formation_keywords` 都是 `["Charge","Tremor"]`（烧充队），而 slot 1 是 `["Bleed","Poise"]`。给烧充队买流血饰品等于把队伍与构筑拧着来；这正是"队伍修对了也打不过"的一半原因。

**决定一：槽位来自任务设置，不来自账本。** 第一版实现从 `user-run-ledger.json` 的 `active.team` 取槽位——那只是**上一局留下的记录**。玩家在 GUI 点任务开始时，游戏按任务设置自己切队（`mirror_team_mode = single`、`mirror_single_team = 2`），所以 `configured_slot()` 以任务设置为准，只有 `rotation` 模式才回退账本。**`MirrorRunner` 因此不需要持有队伍**：`next_sinner(state, team)` 的 `team` 仍由调用方传入，"这局是几号位"由任务设置与游戏决定。

**决定二：多体系队伍不能被压成一个词。** 第一版取 `sorted(队伍体系)[0]`，等于又在"充"和"震"之间替玩家做了一次选择，跟写死 `bleed` 是同一类错误。现在 `systems()` 返回全部体系（充震队是 `('charge','tremor')`），`gift_plan.wanted()` 接受 `'charge+tremor'` 或以 `+` 连接/直接传入的集合：按顺序合并、去重、全无匹配才回退 `default`。单个关键词的语义完全不变。`from_active_team()` 保留单值语义，只服务仍只吃一个关键词的调用方。

**判据**。`tests/test_team_gift_keyword.py`：任务设置优先于账本、`rotation` 仍跟账本、集合不丢体系；`tests/test_gift_plan.py`：多体系按序合并、跨体系重复只出现一次、未知体系回退默认；`wanted(plan,'tremor')` 与改动前逐字相同。全量 `1832 passed`。

**决定三：起始礼物页按体系逐栏匹配。** Grace of the Sisyphus Star 是"一栏一个体系"的选择页（Burn/Bleed/Tremor/Rupture/Sinking/Poise/Charge/Slash），复合关键词不是一个栏名，所以 `initial_gifts.group_target()` 现在按 `systems()` 的顺序逐段尝试，取页面上真实存在的第一栏；单关键词行为不变。实机判据：`initial_gift` 事件里出现实际选中的礼物名与其体系，而不是 `0/1`。



**续记（DSH）：计数读到了，判定还在用旧的读法。** D25 只在 agent 的记录里接了 4× 面板读（`party_vision.counter_reads`），`runner.py` 的队伍页判定仍调用 `participants(原始 OCR)`，于是在 `Total Participants n / 12` 明明印着的页上拿到 `None`，`party_intent` 因此从未产生（`packaged-mirror-20261022-063747`：4 次 `pre_battle_identity_report` 全无计数器、无 party_intent、无停止事件）。现在 `party_vision.deployment_count()` 先看整帧记录，读不到再直接问放大后的面板（`counter_reads`），runner 的队伍页改用它；`MirrorRunner.run_recognition_direct` 由 agent 在构造后注入，缺省为 `None` 时不启用回退。

## D33（2026-10-22）可达性只在已经量出来的格点上判断

13 次带判定的点击（`evidence/runtime/packaged-mirror-20261022-063646`）里 3 次被接受、10 次被拒。先试过"从接受/拒绝反推网格"，当场被否：那三个被接受的点彼此只差 50–100 px，说明它们是同一个格子的读数漂移，而不是三个相邻格。

`runner.one_step_from` 因此用 (190, 176, 95)：同排列距一格，或相邻排错半列。队伍位置取 `state['map_player']`，过滤后若为空则退回全部候选（不允许因为几何而卡死）。

**续记二：停止的是记账，不是读帧。** `packaged-mirror-20261022-070445` 以 `no_candidate_node_observed` 停局，但它最后四帧（frame-0017…0020）每帧都能读 4 个候选；真实原因是这 4 个 box 全在 `MapProgress.tried` 里，`remaining()` 扣空后落进了"无候选"分支。现在 `remaining()` 为空而本帧仍有候选时，清空 `tried` 重试一次，并记 `map_tried_reset`（带 `offered` 与理由）。读帧与格点常数未改。

**续记三：队伍点的调用契约。** `map_vision.player_of(image, markers)` 的第二个参数是 marker 列表；`runner.py` 曾把 `player_marker()` 返回的单个整数传进去，`player_readings` 遂在 `marker.node` 上抛 `AttributeError`。现改为 `player_of(frame, [])`（空列表是受支持的"无 marker"用法），并加异常保护。实测依据：`evidence/runtime/packaged-mirror-20261022-063646/frame-0023` 上一帧读数为 `player_readings -> [(694,384),(703,301)]`、`player_of -> (694,384)`、`train_player -> (694,384)`，两种独立读法一致；同一帧 `gold_marks` 为 0，说明该层候选并非来自徽章。

## D34（2026-10-23）"控件不在帧里"是一类，不是一个页面一条理由

窗口层的 77 条拒绝理由里，46 条以 `_not_anchored` 结尾，另有两条用不同拼写说同一件事
（`battle_has_no_proven_control`、`owned_gift_refuse_control_missing`）。它们不是 46 个页面的差异，
而是**同一个机制失败被逐页命名**：每遇到一张新页就新增一个字符串，于是没有任何调用方能对整类作出反应，
缺一个按钮就等于停窗。

`src/maalimbus/anchor.py` 把这一类收成一处：`anchor_of()` 从理由名解出缺失的控件，
`classify_refusal()` 给出 `stop_kind`（`anchor_missing` / `page_unreadable` / `held`）并附上
`anchor`、`anchor_page`（可选 `recovery_tried`）。`window._refuse()` 是**唯一**出口，理由原文一个字不改，
所以账本与既有断言不受影响。

守卫测试 `tests/test_anchor.py::test_every_refusal_in_the_window_layer_reaches_this_contract`
扫描 `window.py` 里所有 `_refuse(...)` 字面量：新建一个非锚定类拒绝而不在此声明，测试即失败——
这条反例是该类的防复发机制，也是本次改动唯一新增的"约束"。

## D36（2026-10-23）一局只有一种结束，而且它必须能被读出来

**背景。** 连续几局实机都出现同一形状：`stop_reason: null`、进程被杀、或循环"静默地"转圈几分钟。日志里能看到的只是"没有新事件"，看不出是谁停的、为什么停。

**决策。** 结束方式收敛成一张表，每种都带可检索的字段：

| 结束方式 | 谁写的 | 证据字段 |
|---|---|---|
| 循环自己判定页面级失败 | `runner._end_session` | `mirror_loop_stopped.reason` |
| 等待步连续 40 次无新页 | `wait_decision` | `loop_waited` + `the_loop_waited_without_a_new_page` |
| 超出调用方预算 | 步间检查 | `loop_deadline_exceeded` |
| 看门狗到期 | `stall_watchdog` | `window_no_progress`（并受预算钳制） |
| 控制器在点击中丢失 | `jobs.InputLost` | `the_controller_was_lost_before_the_next_input` |
| 外部按预算终止 | 驾驶器 | `the_budget_ended_the_run`（附 `note`） |

**两条不可让渡的约束。** 一是"慢点击"与"控制器已丢"必须是两个状态：前者在画面仍可读时软处理（长转场合法地超过作业期限），后者立即停，不再往空句柄上点击。二是看门狗不得活得比它守护的预算更久，被预算钳制时也不再买宽限窗口——否则"预算"就不是预算。

**反例与局限。** 该表不能覆盖"画面仍可读、但点击被框架以空 `controller_id` 拒绝"这一态：实机已对齐到 `RESUME_DIALOG` 那一次点击，成因仍在查。这类状态目前只能靠预算兜底，不能靠自身收口。

## D37（2026-10-23）一次读取不得长过它的界，看门狗必须写下那一个结束

**为什么。** 2026-10-23 连续五局（15:33、15:47、16:07、16:17、16:32，`packaged-mirror-20261023-153338` … `163257`）都是同一个形状：`loop_heartbeat step=4 page=DRIVE` → `map_observed RESUME_DIALOG` → `window_intent RESUME_DIALOG` → **整整 380 s 日志静默** → 只剩一条 `window_no_progress`。`tools/audit_runs.py` 对整份归档给出的数字是 **142 局、81 局有 stop、51 局死得没有 stop**，其中 16 局最后一条事件就是 `window_no_progress`。

1. **预算是"步间"的，管不住原生调用。** 点击之后的就地 settle 读取不传 deadline，于是继承全局预算；一次卡住的节点读取可以吃掉剩下的全部预算，而循环无法打断一个已经在飞的调用。同一类缺陷当天已在 `7b91b6e` 里修过——但只修了模块级的 `_settle()`，`MirrorRunner.step` 里的第二处没动。修在两道门中的一道，等于没修。

**决定。**
- `MirrorRunner._observe` 把每次读取钳在 `ONE_READ_SECONDS = 30.0`（并与剩余预算取 `min`），并在 `artifacts['reading']` 记下它进入的 phase。超时的读取现在**作为一次读取失败、在步内失败**，循环走普通的具名出口（`the_task_raised_before_the_next_input` + `no page for this frame`），而不是等看门狗。
- `_reading_report()` 把这段记录变成结束记录的一部分：`in_flight_phase`、`in_flight_seconds`，调用还在飞时 `in_flight: true`（返回后是 `lasted_seconds`）。

**必须继续通过的反例。** 已经返回的慢读取带 `lasted_seconds`、`in_flight: false`（慢不等于卡死）；一直有帧的循环不惊动画面看门狗；看门狗不得长过它守护的运行（`jobs.bounded_limit`：450 s 预算把 900 s 窗口钳到剩余时间，任一侧为 `None` 时原样返回）。

**证据** —— `tests/test_settle_deadline.py`（9 条）：无调用方 deadline 时 runner 读取仍有界；更紧的运行 deadline 仍然优先；卡死的节点读取会返回而不是吃掉整局；卡死的读取在 10 s 内结束本局，且失败的名字出现在 `mirror_session_ended` 里。`tests/test_stall_watch.py`（10 条）：进度看门狗先写 `window_no_progress`、再写 `mirror_loop_stopped(stop_path=no_progress_watchdog)`，带 `in_flight_phase='settle'`、`page='RESUME_DIALOG'`、`step=4`、`in_flight_seconds > 300`；已返回的读取不算卡死；画面看门狗也带同样的面包屑；看门狗不长过它守护的运行。

## D38（2026-10-23）看门狗随它守护的那一局一起退休

**为什么。** `stall_watchdog` 是一个会结束**进程**（`os._exit(4)`）的守护线程，但它不知道它守护的那一局是否还在。2026-10-23 实测：`pytest tests/test_agent_loop.py` 18 条测试 5.7 s 全过、返回 0，随后进程被**一局早已结束的运行**留下的进度看门狗在 **5.7 s 后**杀掉——两次，退出码 4、没有摘要。同一形状也解释了"51/142 局死得没有 stop"的一部分：`os._exit` 什么都不写，而一局结束后才开火的看门狗根本没有日志可写。

看门狗留着很便宜，却无法界定范围：`exit(4)` 说不出"这个进程是因为 X 局卡死才死的"，所以只能让看门狗自己去问。

**决定。**
- `stall_watchdog(..., alive=None)` 在每次等待之前与之后各查一次 `alive()`；已退休的看门狗直接返回，不写记录、不退出。
- `MirrorRunner._start_stall_watch` 把凭证放在 `self._watch_live`（`threading.Event`，在两个线程启动前 set），两个看门狗都拿到 `alive=live.is_set`；同一个 runner 再调一次 `run()` 会重新武装。
- `MirrorRunner.run` 现在是薄包装：`try: return self._walk(...) finally: self._retire_watches()`。走路由公开方法搬进 `_walk`，这样任何出口（包括循环没接的异常）都不可能跳过退休。

**必须继续通过的反例。** 运行还活着、页面真冻住时，看门狗仍然结束进程（`test_the_third_wait_still_ends_the_process`、`test_the_watch_ends_a_loop_that_stopped_producing_frames`）。退休只关于"这一局结束了"，从不关于"这次停顿不方便"。

**局限。** 退休只在每个等待周期开头检查，所以看门狗如果正**在** `on_stall` 里而这一局结束，它仍可能把那条记录写完。这是有意的：记录是证据；随后那次退出因为下一轮会重查 `alive()` 而不可达——但一个卡在 `on_stall` 里的看门狗仍能拖死进程。`on_stall` 写文件不加锁，所以风险是残缺记录，不是挂起。

**证据。** `tests/test_stall_watch.py`：`test_a_watch_whose_run_is_over_never_ends_anything`（不等待、不写、不退出）、`test_a_watch_retires_between_two_waits`、`test_the_loop_retires_its_watches_when_it_returns`（真实 `run()` 返回后 `_watch_live` 已清空，再启动会重新武装）。端到端：同一进程里 `python -m pytest tests/test_agent_loop.py -q` 之后停 20 s，从 `exit 4` 变成 `survived 20s`。

## D40（2026-10-23）没发生过的观察不是成功

**为什么。** `tools/recovery_outcome.py` 用"之后看到的页面"给一次恢复打分。当恢复之后既没有 `window_intent` 也没有 `map_click_result` 时，`pairs()` 产出 `(event, None)`（那里的注释就写着 "no evidence"），而 `summarise()` 随后执行：

```python
if page != was:          # page 是 None
    entry['changed'] += 1
```

`None != 'MAP'` 为真，于是**每一次根本没要求任何输入的恢复都被记成了"改变了页面"**。在全量 939 个留存 run 上实测（2026-10-23）：`recompute_state` 被报成 `39/60 changed (65%)`，但那 60 次里有 20 次后面根本没有输入跟着；真实数字是 `19/40 (48%)`。`escalate_ladder` 报 `14/21 (67%)`，真实是 `7/14 (50%)`。

这不是外观问题：`pages.RECOVERY_BY_KIND` 里让 `recompute_state` 退役的注释引用的是**「0 of 51」**，而用同一个工具重跑同一份档案**复现不出来**——那个数字不可能来自当时写下的这个评分器。用一个工具产不出的数字支撑的决策，等于用一个关于数字的记忆支撑的决策。

**决定。**
- `summarise()` 按 `(action, kind)` 返回 `total`、`changed`、`same`、`no_evidence` 四项；`page is None` 只增加 `no_evidence`。
- 比率只按**有证据**的次数算（`changed / (changed + same)`），`main()` 把无证据数单独列一列，并打印一句 `a recovery with no input after it is not evidence of a change`。
- `tests/test_recovery_outcome.py` 把三种形状分别钉住：真的变了、页面没动、根本没有观察。

**必须继续通过的反例。** 要求了输入、但输入之后**没有任何页面**（run 在读取前就结束了）仍然算无证据，而不是"恢复失败"。输入**当时**那个页面是正要离开的页面，只有输入**之后**的页面才是判据：`recovery → intent(page=MAP) → observed(SHOP)` 记一次变化，`recovery → intent(MAP) → observed(MAP)` 记一次未变。

**局限。** 如果输入落在日志结束之后，这次恢复只能算无证据——它缩小的是**分母**而不是放大分子，方向是安全的，但也意味着有证据的样本很小：`recompute_state` 40 次、`escalate_ladder` 14 次。工具现在把样本量印在比率旁边；选择 `escalate_ladder` 的依据是两者**打平**（48% 对 50%）加上「只等待的动作不可能改变画面」，而不是把它说成赢家。

**证据。** `tests/test_recovery_outcome.py`（6 个测试）。修复后 `python tools/recovery_outcome.py`：

```
runs: 939
  action       kind                         changed/evidenced        no evidence
  recompute_state unknown                       19/40  changed  48%    20 no input followed
  escalate_ladder unknown                        7/14  changed  50%     7 no input followed
```

## D42（2026-10-23）守卫不能去拿全机锁，拒绝也不能换掉类别

**为什么。** `tests/test_controller_lease.py` 与 `tests/test_update_install.py` 里有两个测试建了一个**名叫** `controller.lock` 的临时文件交给 `ControllerLease`。而 `lease_path()` 故意把这个名字映射到 `%LOCALAPPDATA%/MaaLimbus/controller.lock`，好让源码 CLI 与安装后的 Agent 在全机共用一把锁——于是这两个测试拿的是**生产**锁。2026-10-23 实测：`test_real_controller_lock_blocks_installation` 是整轮唯一失败（`1 failed, 2068 passed`），原因只是另一个 agent 正持有 controller，连 `ControllerLease(global)` 都拿不到。一个结果取决于「这台机器现在忙不忙」的单元测试，不是在测代码。

更深处还有一层。该测试对「安装被拒绝」断言的是 `pytest.raises(OSError)`，而 commit `2ee48ba`（2026-10-23 12:00）引入了 `class LeaseUnavailable(RuntimeError)`——改好了拒绝的**名字**，却悄悄换掉了它的**类别**。从那一刻起，安装闸门唯一的守卫再也匹配不上，`install_staged` 可以在争用时抛出无人接管的类型而没有任何测试变红；而且这个失败当时看不见，因为整轮套件还在 exit 4、连摘要都打不出来。

**必须继续通过的反例。** 跨进程那条测试仍然证明**第二个进程**拿不到已被持有的租约（`blocked.returncode != 0`），释放后又能拿到——互斥语义没变，只是文件换了地方。被持有的租约仍然在任何换文件之前挡住 `install_staged`（`(install/'MaaLimbus.exe').read_bytes() == b'old'`）。

**局限。** 映射按名字生效，所以将来若真要用**生产** `controller.lock` 语义的测试，本质上不可能自洽；现在没有这样的测试，而且这个映射是被断言过的、不是假设的。`LeaseUnavailable` 成为 `OSError` 也意味着：需要区分「另一个进程占着 controller」与「租约文件读不了」的调用方，必须捕获具名类——这两种情况现在读起来都是同一种拒绝，而这正是安装器想要的。

**证据。** `python tools/run_tests.py tests/test_controller_lease.py tests/test_update_install.py -q` → 18 passed（此前 1 failed, 14 passed）。本决定之前的整轮：`1 failed, 2068 passed`；状态记在 `PROJECT.md`。

## D43（2026-10-23）上限属于门，不属于记得加边界的那一个调用者

**为什么。** 同一个缺陷出现了两次，两次的修复都落在「两处里的一处」。`7b91b6e` 给 settle
*helper* 加了边界，却漏掉 `MirrorRunner.step` 里那段内联的 settle 读（2026-10-23 15:33-16:32
的五局就在那里静坐了 380 s）。`dea7028` 随后给 `MirrorRunner._observe` 加了边界——那是
**runner 的门**——而 `MaaObserver.observe` 那扇门（`tools/lux_task.py`、`tools/reward_task.py`
和 window 层都从这里读）一直是开的。常量本身也在说同一件事：`ONE_READ_SECONDS` 定义在使用它的
循环**之后** 2900 行，紧挨着「顺带需要它」的诊断辅助函数。

**决定。** 一个公式，一个地方：

```python
def bounded_read(deadline, *, limit=None, clock=time.monotonic):
    limit = ONE_READ_SECONDS if limit is None else float(limit)
    own = clock() + limit
    return own if deadline is None else min(float(deadline), own)
```

- `ONE_READ_SECONDS = 30.0` 上移到 `DEEP_STEP_SECONDS` 旁边，与其他有实测依据的循环上限放在一起；
- `MaaObserver.observe` **逐次尝试**取上限：重试最多多花一个窗口，而不是把整次调用的窗口翻倍，
  整次调用上界为 `read_tries × ONE_READ_SECONDS`；
- 模块级 `observe()` 对交给**任何** `Observer` 实现的值取上限，于是回放观察者和未来的实现看到同一份契约；
- `MirrorRunner._observe` 复用同一个辅助函数，现在只负责**报告**这次读取（phase、age、`in_flight`），
  不再是这次读取唯一的边界；`_settle` 也改用辅助函数，不再把算式写第二遍。

**反例。** 要得更少的调用者仍然只得到更少（上限只会收紧，绝不延长）；`FrameObserver` 回放照样返回一帧；
而 runner 的那条面包屑不是边界——`test_a_read_is_bounded_with_no_runner_and_no_deadline`
是在**根本没有 `MirrorRunner`** 的情况下从门里读的。

**局限。** 有两处读取刻意走在门外，这里点名而不是忘掉：`tools/battle_auto_assign.py`、
`tools/battle_step.py`、`tools/map_advance.py` 是自带 deadline 的一次性诊断；`MirrorRunner.step`
的节点动作（旧行号 3412，现 `run_node(self.tasker, plan['node'], self.deadline)`）只受 run 预算约束，
因为**动作**本来就可能比一次读取长。若哪天真在动作里卡住，那就是下一个单元。

**证据。** 实机只读（MuMu `127.0.0.1:16416`）：`evidence/runtime/map-live-20261023-175057`
用 `WindowMapObserve` 对同一张 1920×1080 读取 20 次——每次 0.38-1.02 s，p50 1.00 s，
合计 18.4 s，`input_sent: false`——所以 30 s 是实测读取的 30 倍余量，比它保护的 420 s 预算低两个数量级。
`tests/test_settle_deadline.py`：`test_a_read_is_bounded_with_no_runner_and_no_deadline`、
`test_a_retry_gets_its_own_window_and_not_the_whole_call`、
`test_a_tighter_caller_window_still_wins`、
`test_bounded_read_is_a_ceiling_and_never_an_extension`、

`tests/test_native_reads.py` 是棘轮：允许启动 pipeline 节点的作用域只有 `MaaObserver.observe`

两个检测器都能看见「新加的一处读取」。

## D44（2026-10-23）棘轮数的是总体，不是写法

**背景。** D35 规定"页面分派不允许无声增长"，执行手段是 `re.search(r"page == 'X'")`。同一天用 AST 遍历循环真正使用的读取方式重新测量：**149 行 / 125 个站点 / 34 个页面名**（MAP 独占 29），而正则只看到 **85 行 / 23 个名字**。漏掉的 64 行是 `page != 'X'`（9）、`page in (...)`（11）、`settled_page in (...)`（8）、`page in 常量`（7）以及 `state.get('page')`。也就是说，守卫宣称的规则它只覆盖了三分之二：某一页可以用五种写法中的任意一种多长出一个内联判断，而测试套件仍然全绿。这是一类缺陷的第三次出现——D39 的守卫数的是标签而不是失败、`tests/test_map_dispatch.py` 把表里的数字抄了一份、这次数的是同一问题的某一种写法。

**反例。** 八种写法都被计数，包括 `page in ()`、`settled_page in WAIT_PAGES`（记到 `'?'`）以及反写的 `'MAP' == page`；`plan.get('availability') in ('a', 'b')` **不是**页面分派（检测器自己的第一个误报，现已成测试）；在 `runner.py` 之后追加一个 `page in ('MAP',)` 站点会让真正的棘轮变红并点名 MAP；`test_map_dispatch` 里的 `INLINE_RUNNER['MAP'] <= 20` 被替换，因为它复述了表里的答案而不是去问检测器。

**局限。** 计数器量的是**站点**而不是决策：`page in ('A', 'B')` 是一个站点两行，`page == 'A' or page == 'B'` 是两个站点，所以成组会被奖励，但这个数字不是复杂度指标。它解析不了常量，于是 `page in WAIT_PAGES` 只在总量上可见、无法逐页可见。它只读 `runner.py` 与 `window.py`；`agent/recognition.py` 的 scene 字面量是生产者，不是分派。

## D46. 上限属于每一扇门，而动作不是读取

**为什么。** D37 与 D43 给每一次*读取*加了天花板：`bounded_read` 坐在
`MaaObserver.observe` 与模块级 `observe` 上，任何取页都不能超出它自己的窗口。可循环里还有第二种
原生调用，它一直用着整份运行预算：`MirrorRunner.step` 用
`run_node(self.tasker, plan['node'], self.deadline)` 发节点动作。这与促使 D37 的那次读取是同一种
形状——一次调用、吃掉剩余全部预算、`_walk` 的步间检查插不进去——所以那一类缺陷只修了一半。
它同时也是不可见的：只有 `_observe` 会写 `artifacts['reading']`，于是卡在 `run_node` 里的运行会报
`in_flight: false`，读起来就像什么都没在飞。`evidence/runtime` 里那 51 次没有停止记录就死掉的运行，
从外面看就是这个样子。

**决定。** 一套公式，两扇有名字的门。`_ceiling(deadline, limit, clock)` 是那套算术（调用方更紧的窗口
优先，永不延长）；`bounded_read` 与 `bounded_action` 是它服务的两条规则，各有自己的常量，这样读者能
看清自己看的是哪条规则，测试也能分别钉住。`MirrorRunner._act` 就是动作那扇门：调用前先把
`artifacts['acting']` 记下 phase/node/page/limit，用 `bounded_action(self.deadline)` 上界；节点一直不回来
时抛 `ActionNeverReturned`（`reason = 'the_action_node_did_not_finish_inside_its_window'`），于是循环自己的
结束路径会写下有名字的理由，而不是"这一步悄悄花掉了预算"。`_in_flight_report` 取两份戳记里更晚的那一份，
并在飞的是动作时把节点名一起写进结束记录：`in_flight_node` 与
`in_flight_phase`/`in_flight_seconds`/`in_flight` 并列。

**反例。** （1）节点回来了但报告失败，*不是*卡死：屏幕还在应答，下一步会重读该页，所以这一步只记
`node_action_unconfirmed` 并继续——那是"之后再试"的事实，不是结束运行的事实。（2）更紧的运行死线仍然
优先于动作自己的窗口（与读取同一条天花板规则）。（3）动作上限永远不能延长调用方的窗口：
`bounded_action` 取 min，测试用固定时钟把两个方向都跑一遍。

**棘轮。** `tests/test_native_reads.py` 原先只钉住节点*在哪里*被启动，现在还钉住它*拿到的是什么窗口*：
每一处 `run_node(...)` 都必须传一扇门的调用，或传同一作用域里由门赋过的局部变量（`_act` 属于后者，
因为它需要先把这个窗口记下来）。新代码若写 `self.deadline`，测试会带着文件、作用域和行号失败。

**局限。** `ONE_ACTION_SECONDS = 60.0` 是*策略*上限，不是测量值，常量本身就这么写。142 次留存的运行里
只有一条 `window_intent` 带 `node`（唯一会发动作的计划是 DRIVE 的 `MirrorDrive`），而它的 ISO 时间戳

## D48. 计划的 reason 是一个有写方的词，它的类别不能从拼写里读出来

**为什么。** `plan['reason']` 是写给人看的散文，但在循环内部它是一个键：

## D51. 只作为回调传递的读者，仍然是读者

**为什么。** 本仓库每个交易模块都是同一套生命周期：在可能消耗资源的输入**之前**写下一条

**决定。** 把配对**派生出来并加闸**（`src/maalimbus/transaction_ledger.py`）：方法族来自交易

是意图；`observe*` / `reconcile*` / `recover*` / `commit` 是对账；`prepare` / `begin` /
`reset*` / `seal*` / `adopt*` / `close_visit` / `retire_pending` 是清理；`matches` /
`refreshes_used` / `signature` … 是查询），触点来自 `MirrorRunner.step` 的 AST，裸属性引用
计为**注入的读者**。`tools/audit_transactions.py` 打印账本；当某个意图没有任何读者、或循环

**反例。** 有意图没有读者会被报出（合成源码）；意图加

不是方法；名字看起来像两个族时规则只给一个答案（`reserve_confirm` 是意图、`confirm_clear`
是意图、`reconcile_purchase` 是对账、`close_visit` 是清理）。

**局限。** 账本能证明引用存在，不能证明辅助函数真的走到它，那需要一次运行。写在
`MirrorRunner.step` 之外的交易对它不可见；"无人引用"按方法**名**跨模块匹配，因此某个方法若
与别的模块同名，就不会出现在死方法列表里。

## D52. 一句承诺写十遍，就是十句承诺

**为什么。** 离线回放是这个项目在碰游戏之前证明"某个页面会这样走"的主要手段，
它必须守的承诺只有一句话：*保留帧不是游戏，所以除非场景声明了它期望的那一次点击，
否则什么都不点。* 2026-10-23 的测量结果是：工具层把这一句承诺写成了十六份。
`tools/` 下有 16 个直接继承 `CustomController` 的类（十个叫 `verify_*_replay.py`，
五个嵌在 `main()` 里、名字毫不相关，例如 `autolabel_sinner_retained.py`，再加一个
`verify_real_theme_drag.py`），另有 29 个工具通过 `from verify_*_replay import Replay`
继承其中某一份——其中 17 个是从 `verify_grace_balance_replay.py` 借的，那是一个
讲星之光余额的工具。同一组机械回答有 16 个版本：`connect`、`request_uuid`、
`get_features`、`screencap`，四个不同的 uuid 字符串，每个都在说自己的工具，而不是这一层。
没有任何东西比较过它们，所以其中任何一份都可能悄悄漂走而测试全绿。

**决定。** 一层，`src/maalimbus/replay.py`，分两半：

- `ReplayFrames`——不需要 Maa 库的那一半：帧、这一层的 uuid、返回副本的
  `screencap`，以及**除非场景声明了它期望的输入否则一律拒绝**的输入面
  （`expects(kind, position, *args)`）；每次尝试记在 `attempts`，每次被接受的
  输入记在 `inputs`；
- `ReplayController(ReplayFrames, CustomController)`——同样的东西加上 Maa 基类，
  好让 pipeline 能绑定它。

规则是：`connect`、`request_uuid`、`get_features`、`disconnect`（以及只返回当前
帧时的 `screencap`）在整个仓库里只有一份实现。留在工具里的，是真正属于它自己的
部分——它展示哪一帧、它期望哪一次输入——所以 `verify_deployment_replay.py` 保留
它的点击预期，`verify_team_replay.py` 保留它的滑动边界，而 `verify_map_replay.py`
现在只剩它自己的帧。

**反例**（全部在 `tests/test_replay_surface.py`）。自己写 `connect` 的工具会被报出；
基类不是这一层的工具会被报出，即使它没有重写任何机械方法；`expects` 返回 `False`
仍然拒绝且不记录；`screencap` 返回副本，改返回的数组改不动 fixture；没有帧的回放
抛出带 `no frame` 字样的错误，而不是 `AttributeError`；只负责拒绝的覆写是多余的——
拒绝本来就是默认，于是删掉了 60 行这类代码。

**证据。** 之前：16 份实现、`*_replay` 家族里 39 个工具互相 import、`request_uuid`
写了 16 遍。之后：`tools/replay_inventory.py` → `replay tools: 188  owning a
controller: 16  inheriting the shared layer: 16  problems: none`；`request_uuid`
只有一处实现（`assert owners == ['replay.py:ReplayFrames']`）；17 个文件净 −60 行；
`tests/test_replay_surface.py` → 12 passed；全量 `2189 passed in 182.37 s, pytest exit 0`。

**局限。** 这一层证明的是"拒绝、取帧、记账"，不是"某个场景的期望是合理的"。
它也没有把 import 图摊平：29 个工具仍然通过邻居拿到 `Replay`，清单如实报出这条
链，而不是假装它不存在。回放终究告诉不了你游戏会不会那样回应。

## D54. 一个只会存帧的类体不是子类

**为什么。** D52 给了回放层一个家，D53 给了它一个"造得出来"的证明。两条都停在同一行：
四十个工具仍然从邻居那里拿控制器类（`from verify_grace_balance_replay import Replay`），
而 D53 只是把它们数了出来。把十二个源类读一遍就发现它们不是同一种东西：

- 五个带着自己循环需要的期望——`verify_star_replay.Replay.click`、
  `verify_theme_replay.Replay.swipe`、`verify_deployment_replay.Replay.click`、
  `verify_native_replay.Replay.click`、`verify_battle_plan_replay.Replay.click_key`；
- 三个什么都不带：`verify_grace_balance_replay.Replay` 就是 `self.image = image` 加
  `screencap`，`verify_map_replay.Replay` 就是 `self.frame = frame`，
  `verify_sinner_neural_native.Offline` 是一帧 640x640 的全零。

**决定。** 一个类体只是把手里的帧存起来的类不是控制器，它是构造函数的一个参数。三十二个
工具现在直接引用这一层（`from maalimbus.replay import ReplayController as Replay`），
三个"全零帧"的改用 `blank_replay`，两个把 Maa 自己的 `CustomController` 从邻居转引的工具
改从 `maa.controller` 引。剩下十二个工具，其源类声明了自己循环期望的输入；它们必须逐条
按那个期望摊平，不能机械替换，所以被数清、被点名，而不是被删掉。

**门守住的反例。** 清单钉住十二，并点名剩下五个源模块，于是新增一条邻居 import 会让测试
变红，即使总数碰巧不变。`blank_replay` 在运行时套件里被证明：按要求的尺寸给出全零帧、
记下一次被拒绝的点击、不发送任何输入。

**局限。** 摊平证明的是控制器那一半：帧、拒绝、`screencap` 的副本。它不证明工具的领域
期望仍然成立——`measure_unavailable_native.py` 会跑完自己的 OCR，然后栽在自己的
`deployment_transaction` 断言上，与用邻居的全零帧时完全一样，这一点如实报出。

**证据（2026-10-23）。** `tools/replay_inventory.py`：`tools that take a controller class

## D55. 只为补一个方法而存在的子类，说明这一层缺了这个能力

D54 把"12 个工具从邻居那里拿控制器类"报了出来，也把它当成了已处理。问清每条边的用途，会发现它分成两半，只有一半是缺陷。

五条边是"同一个场景被同场景的另一个工具复用"：deployment 回放同时驱动 `verify_mxu_deployment_replay.py` 与 `verify_packaged_deployment_replay.py`，battle-plan 回放驱动 `verify_packaged_battle_replay.py`，native 回放驱动 `verify_packaged_replay.py`，theme 回放驱动 `verify_packaged_theme_replay.py`。它们各自用自己的 case 标号构造那个类，依赖的是该类自己的分 case 帧与输入断言——这是依赖，不是重复，保留。

另外七个根本不要 star 的卡面断言。其中五个继承它（`ToggleReplay` / `GroupReplay` / `ReceiptReplay` / `RefuseReplay` / `EntryReplay`），只为覆盖一个方法，而每个覆盖的最后两行都一样：

```python
self.clicks.append([x, y])
if self.after is not None: self.frame = self.after.copy()
```

另外两个（`verify_difficulty_proof_replay.py`、`verify_owned_receipt_replay.py`）直接构造它，因为它们只想要一帧能回答 `screencap` 的画面。七个工具、一个缺失的能力：**被接受的输入可以推进到下一帧，而被接受的点击要留记录。**

**决定。** 这两件事都属于场景，所以进这一层：`ReplayFrames(..., advance=False)` 在被接受的输入之后、且还有下一帧时推进 `position`；`clicks` 以 `[x, y]` 记录被接受的点击（拒绝永不落入，`attempts` 仍记录所有尝试）；`screencap` 先读 frames 列表再读单帧 `frame`，否则推进根本看不见。七个工具删掉自己的类，改为模块级期望（`expects_toggle`、`expects_group`、`expects_receipt`、`expects_refuse`、`expects_entry`）并构造 `ReplayController(frames, expects=..., advance=...)`；原来在构造后设置的 `controller.forgo = args.forgo` 一类开关，改成期望的参数——这更严格：控制器不再能中途改主意。

**必须继续失败的反例。** 被拒绝的输入不得推进画面、不得入记录；最后一帧仍是最后一帧；场景期望仍要拒绝另一个盒子与非点击输入；新增一条"从邻居拿类"的边，即使总数不变也要报出来。

## D56. 度量缺口的仪器本身，就是缺口

D49 宣布 28 个计划词"无法被判定"：既没有给 `window.step_result` 的 `expect`，也没有
runner 里读回这个词的钩子，所以"点击被吞"和"点击送达"分不开。这个数字是错的，而且错
在让代码看起来比实际更糟的方向。

`plan_reasons._elements` 只返回**字符串常量**，而一次点击的"驳回"证明不是字符串常量：
它是符号 `ANY`，意思是"页面必须变，变到哪我不说"。`_plan_index` 用
`len(_elements(expect))` 计数，于是 `expect=(ANY,)` 数成 0。那 28 个词每一个都带着它。
2026-10-23 补上 `_dismissal` 与 `_advances` 后重测：80 个会发输入的计划里，45 个有具名
后继、43 个带驳回、21 个被 runner 钩子点名、44 个是 `advance`（用像素替代页面），
**没有一个无法判定**。

**为什么会错。** D49 交付的门问的是一个"仪器不用读符号也能回答"的问题——"这个计划有
证明吗？"——然后把答案当成结论发布。没有任何东西拿它和一个"有证明但没被数到"的计划
对照，因为计数器是唯一的读者，而它在同一个地方盲了两次：对 `ANY`，以及对同族的
`advance`（用一帧的变化替代页面变化）。

**决定。** 三件事不再是散文。

1. `plan_reasons.acting_plans()` 现在除 `expects`、`hooked` 外还报告 `dismissal` 与
   `advance`，`unproven()` 返回 `[]`。`pages.PLANS_WITHOUT_PROOF` 更名为
   `PLANS_WITH_ONLY_A_DISMISSAL`——28 个"唯一证明是页面必须变"的词，值为
   `page_must_change`，数量只减不增。"比具名后继弱的证明"与"没有证明"是两个断言，常量
   名现在说的是哪一个。

2. 代码回答不了的下一个问题交给归档。`maalimbus.plan_outcomes` 读遍
   `evidence/runtime/packaged-mirror-*/events.jsonl`，把每条 `window_intent` 与它之后
   第一个被命名的页面配对，给词分类：`unanimous`、`few`、`mixed`、`never_changed`、
   `unseen`。实测：52 个词、1643 次意图、773 次页面变了、815 次没变、55 次无证据；
   23 个词每次都变，11 个词从未变。

3. 对"从未变"的 11 个，页面从来不是它们的证明——这里若再天真读一次，就会凭空造出
   活儿：

   - **7 个是 `advance` 计划**，证明是像素变化。`team_card_joins_the_next_unpicked_identity`
     109 次里 107 次页面不动，因为填队伍位是**状态**变化；它的证明是帧，不是缺陷。
   - **2 个确实欠一个状态证明**：`the_starting_gift_row_is_taken_from_the_tray`（8/8）、
     `the_starting_gift_is_picked_from_the_rotation_keyword`（6/6）。它们只有驳回、没有
     像素证明，归档说画面不动。它们被声明在 `pages.PLANS_AWAITING_A_STATE_PROOF`，值
     = "没动的次数"，让证据跟着声明走。
   - **2 个待查**：`refreshing_the_shelf_for_the_gift_the_plan_wants`（5 次）、
     `scrolling_visible_team_list_for_saved_slot`（1 次）点名了一个归档从未见过的后继。
     只报告、不设门：一次观测是样本，不是规律。

**反例。** `tests/test_plan_outcomes.py` 用合成事件流钉住读法：`semantic_frame_proposal`
不是页面（它不带页面，把它当页面会让每次观测都变成"缺证据"）；心跳记录它醒来时的页面；
先停掉的运行留下的是无证据；一次落地算 `few`、三次才算 `unanimous`；从未动的词是
`never_changed` 而不是 `unseen`。对声明的门是自纠的：某个被声明的词一旦开始让页面变，
归档会把它分到 `mixed`，`test_every_declared_word_is_one_the_archive_owes` 就会红。

**局限。** 归档只能看见页面，且只来自比这条决定更旧的代码；`window_intent` 不保存状态

## D57. 后继集合是名字，而索引有它的视野边界

**为什么。** D56 公布了两个"待查"：`refreshing_the_shelf_for_the_gift_the_plan_wants`
（发出 5 次，页面从未动）和 `scrolling_visible_team_list_for_saved_slot`（1 次）——它们
的计划点名了一个归档从未见过的后继。两个都又是仪器的问题：货架刷新点名的后继是
`('SHOP', 'SHOP_PURCHASE', 'UNKNOWN')`，队伍滑动点名的是 `('DUNGEON_TEAM',)`。刷新之后
仍在商店里、滑动之后仍在队伍页上，**页面不动正是计划自己说的正确结果**。旧读法拿观测到的
页面去比"页面变没变"，从不比"计划自己声明了什么"，于是 1643 条记录里的 725 条被数成了
"哪儿也没到达"。

**决定。** 一次输入的结果，用它**自己那份计划**声明的后继集合来判定：

* 观测到的页面是计划点名的——算落点；无论它与计划起手的页面是否相同（同页的情形单记
  `declared_same`，这样"计划就指望这一页"与"计划指望页面变"仍然分得开）；
* 页面变了但不在计划点名的集合里——`unexpected`，这是真信号；
* 页面还是原来那页、计划也没点名它——`same`，驳回失败；
* 之后没有任何页面——`no evidence`，永远不算成功。

同一轮还量了静态索引**能叫出**多少词：归档的 52 个词里有三个在源码里找不到对应的计划——
一个是由参数默认值拼出来的理由（`win_rate_is_the_proven_auto_assign_control`，152 次），
一个经由状态字典传递（`the_starting_gift_row_is_taken_from_the_tray`，8 次）。两处修补
把大部分补上：写在绑定它的作用域内的元组常量（`name, reason = ('gift_search.refuse_button',
'the_player_asked...')`）现在能解析；`or` 兜底（`state.get('reason') or '<词>'`）两侧的词
都算数。剩下两个写进 `pages.PLANS_THE_INDEX_CANNOT_NAME`，值就是各自解释的发送次数，门把
这张表与归档逐一对照。

**反例。** 计划没点名的页面是 `unexpected`，不是落点（`.../map` 用例）；链路能叫出名字的词
**不许**写进声明（这张表描述索引的视野，不是放词的地方）；把词表从模块级挪到函数级本身也是
一个反例发现的 bug——模块级的表让一个在三个分支里复用的名字收进了三个词，于是"拒绝"看起来
像"点击"。

**证据。** `python tools/audit_plan_evidence.py`：52 个词、1643 次意图，其中 602 次落在计划

**像素**证明是否满足——`advance` 计划的页面不动是设计，而归档看不见帧。因此这张表是对"索引
能读到什么"的陈述，不是"剩下两个词无法判定"的证明：起始礼物那一行由一个带

## D58. 归档每次都看到的落点，是计划里漏掉的一行，不是意外

## D59. 读不回来的一次读，不是一次判定

**为什么。** D43 给每一次原生的读装上了上限（`bounded_read`），卡住的截图再也吃不掉整局预算。可是上限随即变成了"结局"：读抛出普通的 `RuntimeError`，整步展开，循环用
`the_task_raised_before_the_next_input` 结束这一局。于是模拟器一次 30 秒的抖动 = 一整局 420 秒的预算丢掉，而且偏偏砸在"输入已经发出去"的位置上。留存归档里，51 个沉默结束的运行中有 16 个以
`window_no_progress` 收尾、最后一条事件正是 settle 读：点击已经发出，settle 读没有回来，而这一局没有"这一轮没有帧"这个状态可用。

**决定。** 一次失败的读是*观测失败*，不是判定：

* `ReadNeverReturned` 给它一个名字（`the_page_read_did_not_come_back_inside_its_window`），并在真正失败的地方抛出（`MaaObserver.observe` 的节点没有记录到页时），所以这个失败的身份不依赖匹配错误字符串。
* 在 settle 循环里，它就是一轮没有产出。帧由 `_unreadable_frame(before_sha)` 顶替：`scene='UNKNOWN'`、**沿用上一帧**的图像哈希、没有 OCR。`UNKNOWN` 本来就是有页面身份、有预算（`unknown_rounds`）、有恢复路径的一页；沿用旧哈希，是为了让"画面变了没有"这条规则看到的是"没变"，而不是伪造一个后继。

  **反例。** D59 之前，这里正是"动画"和"设备死了"的分界线，而 settle 自己的预算是 1–30 轮：三轮 30 秒窗口仍然要花掉一局 420 秒里的 90 秒；patient 页（主题包下拉）的预算是
  `unknown_rounds = 30`。真正的界线是运行截止时间，以及下一段：停止重试发生在*步*这一层。
* 在一步的开头，它按 `settings.read_retries`（默认 2，与 `map_tries`/`page_tries` 同一个默认值袋）重试，然后带着这次读自己的原因结束这一局——有界重试，不是循环。

  **反例。** 一个按异常*类*判断的规则会把流水线失败一起吞掉：其他来源的 `RuntimeError` 必须仍以自己的原因结束运行，测试钉住了这一点（`test_a_plain_runtime_error_is_still_fatal_and_not_retried`）。

**塑造了数字的反例。** 失败计数是*连续*的，任何一次读成功的步都会清零——否则运行早期两次抖动，会把后面每一步的重试预算都花光。`read_retries=0` 必须在第一次失败就结束（`test_a_zero_retry_budget_ends_the_run_on_the_first_failure`），这样重试就不可能变成忽略死设备的方式。

**局限。** 重试是按次有界的，不是按局：设备真的消失了，一局要花掉 `(read_retries + 1) × ONE_READ_SECONDS`（默认 90 秒）才结束，这就是"扛住一次抖动"的价格。settle 循环也可能把整轮预算都花在读不出来的轮上，然后用 `UNKNOWN` 继续，进而花掉未知预算——这是有意的（读不出来的页*就是*未知页），但它意味着重试次数并不限制"一个读不出来的步能有多久"。

**证据。** `tests/test_read_failure.py` 九个离线用例（settle 轮活下来且仍记下后继、重试后的步、有界的结局、零预算、普通错误、计数清零、不可读帧、设置默认值）。`tests/test_settle_deadline.py` 的卡死读用例改为断言"重试后的结局"，而不是"第一次失败即结束"。只读流水线检查 `python tools/verify_pipeline_spec.py` 仍是 `ok — 0 problem(s)`（805 节点 / 16 agent 名 / 6 个入口任务），`python tools/run_tests.py -q` 全绿。
## D60. 一个预算不能同时数两件事

**为什么。** D59 把一次失败的 settle 读变成"一轮无产出"，并把计数交给了页面预算：`rounds`（3；MAP 上 6；耐心等待的主题包下拉是 `unknown_rounds` = 30）。这些轮次是为"帧到了但没变"设计的。而读不回来是另一种事件：按读窗口（`ONE_READ_SECONDS` = 30 秒）加间隔算，30 轮耐心轮次是 1080 秒，对着 420 秒的预算——于是一台卡住的设备可以在一整步的 settle 循环里把整个窗口花光，最后落在截止时间上，而这正是 D37/D38/D59 一路想避免的那种结局，只是换了一条路到达。

**决定。** 连续的读失败有了自己的小预算 `settings.unreadable_rounds`（默认 2，取值 0..30）。两个计数故意分开：

* 页面预算数的是"读到了帧但画面没变"的轮次；
* 读预算数的是"连续多少次一个帧都没读到"，任何一次读到东西的轮次都会把它清零。

读预算用尽时，settle 循环停止再问，把页面留成不可读——`UNKNOWN` 加沿用旧图像哈希，这本来就是 unknown 预算负责的局面。**这不是结局**：该步会记录 `reads_failed`，运行继续。步记录现在带 `reads_failed`（这一步丢了几次读），事件里带 `seconds`、`limit_seconds`、`consecutive`、`reads_failed`、`budget`，于是 D59 留下的问题——到底卡在哪——事后可以从日志回答。

**反例。** 失败两次但中间夹着一次成功读的，不许被拦停：计数是连续的，测试正是这么驱动的（`reads_failed == 2`、预算 1、这一步仍然走到 MAP）。预算为 0 必须在第一次失败就停，而不是再多读一次。页面预算为 4 且四次都读成功时，四次必须都发生，读预算不能缩短"读到了"的轮次。负数预算在构造时就被拒绝，因为那会让循环在第一次读之前就停下。

**局限。** 这只约束了一步之内的 settle 循环，不约束整局：跨步持续失败的设备由步开头的 `read_retries`（D59）兜底，那是"连续多少步"的计数。两个数字目前仍然彼此独立；将来可以把它们合成"每局读失败预算"，而这次新增的 `reads_failed` 字段正是那个决定所需的证据。

**证据。** `tests/test_read_failure.py` 16 passed（新增 7 个 D60 用例）；10 个 runner/计划/页面套件 205 passed in 60.91 s；全套 2245 passed in 202.11 s, exit 0；读窗口与默认值分别由 `test_the_note_says_how_long_the_read_took`、`test_the_read_budget_is_a_setting_with_a_small_default` 钉住。全程未发送任何实机输入；未动的第 2 层进度保持原样。
> **由 D67 修订。** 下文引用的 `reads_per_step`（34.2）用心跳条数做了分母；按各局声明的步数计算是 9.73。

## D61. 效率数字只能有一个主人，而零不是测量结果

**为什么。** 第六阶段要六个数字：通关率、平均耗时、识别调用量、无进展停止率、恢复率、误操作与重复交易风险。此前的每一轮都是手工引用，而且来自三个不同程序（`tools/audit_runs.py`、`tools/audit_silent.py`、`tools/recovery_outcome.py`）；其中两次手工统计错得足以改变结论：D50 的普查报出 `81 + 51 = 132`（142 局中有 10 局只写了 `mirror_loop_error`），D56 的"28 个无法判断的输入"其实全都被一个读者看不见的"驳回证明"判着。手工产出的数字，是没有人能重新导出的数字。

**决定。** 定义归 `src/maalimbus/run_metrics.py`（它本来就是停止普查的归属地）：

- `efficiency(rows)` —— 单局：`seconds`、`reads`、`steps`、`reads_per_step`、`reached_floor`、`explored`、`ending`、`recoveries`、`advanced`、`recovery_advanced_rate`、`unconfirmed_purchases`。
- `metrics(runs)` —— 语料层面六个数字，每个都带 `value`、`basis`（它是从哪个分数算出来的）以及 `note`（值为 `None` 或需要限定条件时说明原因）。
- `portfolio(directories=None)` —— 每局记录加六个数字，于是"写报告"变成一条命令，而不是一次重数。
- `tools/audit_efficiency.py` 只负责打印；没有可读数据时退出码 2。
- 语料定义是"写出了 journal 的目录"，与 `tools/audit_runs.py` 相同——没有 journal 的目录不是"测得 0 的一局"，而是"没有东西可测"。

**零不是测量结果。** 任何算不出来的数字都是 `None` 加一句原因，测试把这些边界钉住：一个时间戳不是时长，没有心跳不是每步读数，没有恢复不是恢复率。唯一允许为 `0` 的是通关率，因为"142 局中 0 局到达第 5 层"是一个带分母的观测。

**反例（`tests/test_run_efficiency.py`，17 例）。**

- 从没买过东西的语料报 `unconfirmed_purchases: 0`，basis 是 `no run of 142 wrote a purchase event`，note 说明"风险是不存在，不是被测得为零"；而当每一笔消费都被确认时，同样是 `0`，但 basis 与 note 都不同——两种零是不同的事实，不能长得一样。

## D62. 改不了视野的恢复手段，就没法排序

**为什么。** 第六阶段要的六个数字里有恢复率。D61 诚实地测出来是 1/274：每四百次恢复有

花掉这一级，观察面看见了别的吗？

**决定。** 证据本来就在日志里——`map_observed` 记录了读取器找到的框——所以不需要新加

## D63. 说不清有没有领到奖的运行，量不出通关率

**为什么。** 第六阶段要通关率。`run_metrics.clear_rate` 诚实地、也只能狭窄地给出答案：它数

**塑造它的反例。**

**局限。** 142 局留存的 `packaged-mirror-*` 永远不会补上这个字段，所以它们的

**证据。** `tests/test_payout_journal.py`（10 例：跳过、停下、已验证的领取、无 journal 的

`tools/verify_reward_task_offline.py` 在 `HEAD` 与本改动下同样失败

## D65. 日志看不见的效果，不能当成判决

**为什么。** D62 用 `map_observed` 里能找到的界面框（header、pack、panel、battle、
clear_selection）判断每一级恢复手段有没有起作用。可是视野手势本来就允许一个框都不动
就算成功：把棋盘拖动一下，可能把某个候选节点带进视野，而页眉一个像素也没移。而"这一帧
提供了哪些目的地"从来没进过日志——它在 `MirrorRunner.step` 里由 `candidates_of`
算出来（游戏标亮的那个亮色字形、去掉界面框、去掉进度按钮、过滤到与队伍相邻），用一次
就丢了。于是 `drag_down` 的 `18/72` 只是个**下界**，D62 没法诚实地回答"这一级到底动没
有动"。

**决定。** 循环在提供目的地的当下，把提供的东西写下来：

`map_nodes_offered` —— `offered`（个数）、`boxes`（目的地，含相邻过滤，因为那才是循环
真正被允许选择的集合）、`party`（过滤用的队伍点）、`reason`。

读者按**框中心的集合**比较两次提供，而不是按顺序：这个列表是按相邻度排序的，重排不是
变化，不能算成"动过"。每一级现在除界面数字外还报 `nodes_measured` 与 `nodes_changed`，
只要**任一**信号变化就算 `changed`。写这条日志的条件是 `candidates is not None`
（"读者给了一份目的地列表"），而**故意不是**新写一个 `page == 'MAP'`：D44 的棘轮在草稿
上就把它拦了下来，而棘轮是对的——这里记录的是"提供了什么"，不是"页面叫什么名字"。

**反例（都写进测试）。** 没有节点行的归档必须把节点信号报成**未测量**，不能报成零变化；
重排不算变化；界面不动而节点进了视野**算**变化；空提供也要写下来（循环当时无可选，
本身就是事实）。

**测量（2026-10-23）。** 保留的 142 局都在写者之前，所以
`tools/audit_ladder.py` 现在打印 `rungs whose node signal was measured: 0 of 270` 并说明
原因。这就是诚实的现状：仪器已经装上，下界要等新运行写出这些行才会变成判决，而下一轮测
阶梯时，"界面没动"不再能冒充完整答案。

**局限。** 这行每次 MAP 步骤写一次、在输入之前，所以一级手段由它前面最近的一次提供和它
后面第一次提供来夹住——这正是这一级作用的对象。旧日志无法补写，节点信号从写出它的运行
开始。
## D66. 只有总时长、没有预算是秒表，不是测量

**为什么。** D61 给出了 `mean_seconds`，D63 补上了 `payout_rate`；两者都不回答"这几分钟花在
哪里"，所以在此之前任何提速结论都只能是猜。日志本身就能回答这个问题，不需要新埋点：每一行都
有自己的 `utc`，因此"从这一行到下一行有时间戳的事件"之间的间隔，就是这一行花掉的时间。

**决定。** `run_metrics.time_budget(rows)` 把一局的秒数记到花掉它的那个事件上；超过
`MAX_GAP_SECONDS = 120.0` 的间隔被排除（主机被挂起或时钟跳变不是一步），并且把**排除了几条**
如实报出来，而不是悄悄丢掉。`time_portfolio(budgets)` 把各局合并，占比的分母是**已归属**的秒数
而不是总秒数，这样日志解释不了的那部分永远不会被摊给剩下几行。`tools/audit_time.py` 负责打印，
`portfolio()` 把它和六个指标并列；日志的最后一行不获得归属——没人观测过成本的行走，不等于成本为 0。

**反例（都钉在 `tests/test_time_budget.py`）。**
- 300 s 的间隔被排除并计数；同样两行相隔 30 s 时被归属；cap 是参数，所以故意很短的一步不会被误排除。
- 一个时间戳不构成预算：`total_seconds` 与 `unattributed_seconds` 为 `None`，语料级报告写"未测量"
  而不是 0 秒。
- 没有被归组的事件落在 `other` 里；各组秒数之和等于已归属秒数，永远不等于总秒数。
- `Z` 与 `+02:00` 是同一个时钟；解析不了的时间戳被跳过，不做猜测。

（另有 20 个超过上限的间隔被排除）。

| 分组 | 秒 | 占比 | 次数 |
| --- | --- | --- | --- |
| 读取 | 15 682 | 53.1% | 10 355 |
| 等待 | 5 867 | 19.9% | 1 026 |
| 输入 | 3 822 | 12.9% | 1 974 |
| 恢复 | 2 559 | 8.7% | 273 |

占时间最多的行：`map_observed` 13 650 s（46.2%，**每次读取 2.45 s**）、`window_unknown_wait`

## D67. 用代理量算出的比率，不是比率

**缘由。** `reads_per_step` 把 142 局的识别次数除以 `loop_heartbeat` 的条数。心跳不是步：
它是在 2026-10-23 才加的一行，用来让"在某一步里死掉"的局仍留下最后开始的东西（D37 的证据），
而此前的构建根本不写它。于是语料公布了 **34.2 次/步**，可同一批局自己声明了 **1 065 步**、
做了 **10 362 次识别**：真值是 **9.73**，被公布的数字里有 3.5 倍来自分母。142 局中有 61 局
从未声明步数。

**决定。** 步进比率的分母是循环自己停止时声明的步数（`mirror_loop_stopped.steps`），
而且分子分母必须来自同一批局：识别次数只在声明过步数的局上累加，绝不拿全语料去比。
心跳条数作为"日志记录了多少"写在比率旁边，不参与分母；`basis` 明确写出有多少局提供了步数
（`10362 reads over 1065 steps declared by 81 of 142 runs`）。没有任何局声明步数时，输出
`None` 并给理由——代理量不是测量。

**固定下来的反例。** 写了三条心跳却没有步数的局没有比率（`steps is None`），不是"分母为 3"；
声明 5 步、读了 10 次的局是 2.0，不是 10.0；一个"有声明"加一个"只有心跳"的语料报 1.0 并写明
`2 reads over 2 steps … 1 of 2 runs`，绝不能把旧局的识别次数算到新局的步数上。

**改变了什么。** 第六阶段曾用 34.2 支撑"减少每步识别次数"；真实数字是 9.73（每次输入
6.31 次识别）。真正的成本不在次数，而在**每次识别 2.45 s**（D66 的预算：`map_observed` 占
全部已归属时间的 46.2%）。一个错 3.5 倍的比率会把下一步优化指向错误的对象——所以这是决策，
不是改错别字。

**局限。** `steps` 数的是循环迭代，不是日志里记录的动作；中途死掉的局不声明任何东西，
因此这个比率只覆盖"自己正常结束"的局，`basis` 会把这点写出来。

## D68. 不会计时的读取，拆不开

**为什么。** D66 用"到下一行的时间差"给每种日志行算了耗时，于是 `map_observed` 得到每次读取
2.45 s。可这个差值从该行写下的时刻开始、到**下一行**为止，中间包含着下一次读取，所以它能说明
"时间花在读取上"，却不能说明花在观察节点的截图+OCR 上，还是花在节点外面的循环上。第六阶段要
决定的是"少读几次"还是"每次读便宜点"，两条路指向不同的代码；不拆开，这个选择就是猜。

**决定。** 每个观察写者给自己计时。`MapObservation`、`BattleObservation` 和
`ThemeObservation` 里的地图写入，都在 `run` 顶部取 `time.monotonic()`，并在本来就要写的行上
记录 `seconds`——一次读取多一个浮点数，不多一行日志。读的一侧是 `read_cost` /
`read_portfolio`（`src/maalimbus/run_metrics.py`）：它报告覆盖率
（`N of M reads carry their own duration`），绝不把"没有计时"的语料读成零秒；`read_split`
只把"节点那一半"从 reads 组里减掉，而且只在**两样都测到了**的运行上减，保证减法比的是同一批样本。

**钉住的反例。** 没有数字的行不是 0 s。`seconds=True` 不是时长。只出现在注释里的
`seconds=` 不是字段——闸门走 AST 找真正的关键字参数，字符串搜索会误判（D53 已经因为"文档字符串
里的 import"吃过一次同样的亏）。有读取时长但没有时间戳的运行不进拆分。`scene_mismatch` 是
流水线自己的拒绝记录，没有动作体，所以它不是"计时读取"。

**证据。** 用真实 `MapObserve` 节点回放一张归档地图帧（命令见英文条目）退出码 0、
`passed: true`，两条 `map_observed` 行都带上自己的时长：地图帧 **1.44 s**、RESUME_DIALOG 帧
**1.08 s**，且 `input_sent: false`。同一事件在归档里的差值统计是每次 2.45 s，因此每次读取约有
一秒花在设备截图与包装上，而不是 OCR——下一个问题现在问得出来了。

**局限。** 回放的帧来自内存，真实 adb 截图不在这 1.08–1.44 s 之内，实机数字会更大。142 局旧运行
都写在字段出现之前，永远报"未测量"；只有本决定之后的运行才能被拆分。
## D69. 截图那一半只是被点名，没有被计价

**为什么。** D68 把一次读取记到 2.45 s（差值）与 1.08–1.44 s（节点自测），于是"节点之外还有一秒"
这件事是有数的，但那一秒是什么没有数。最顺手的候选是设备截图：1920×1080 过一趟 adb 不便宜，而方法
由框架挑，所以"剩下的大概是截图"就成了忙起来会写、但不会去核的那句话。

**决定。** 点名之前先计价。`tools/measure_screencap.py` 为每种被提供的方法各建一个控制器，**输入法用 Null**，
计时 N 次截图，并且"一次都没回来的方法"报成未测量，而不是 0 秒。`pin_input` 早就有的那一半现在有了
`adb_device.pin_screencap` 对应，下一次做方法 A/B 不必手搓控制器。

**实测**（`evidence/runtime/screencap-20261023-215900/screencap.json`，MuMu 12，`input_sent: false`）：

| 方法 | 每次截图中位耗时 | 失败 |
| --- | --- | --- |
| `EmulatorExtras`（唯一被提供的方法） | **0.051 s** | 0 / 5 |

所以截图不是那一秒。节点里剩下的约 1.39 s 是识别与流水线往返——下一件事就是把它拆开，而拆它所需的
仪器这一轮已经装好。

**反例。** 一次都没回来的方法必须读成未测量（没发生的截图不是"很快"）；pin 读取不得改动 `input_methods`，
否则做截图 A/B 会悄悄改掉输入策略；"框架不认识的名字"与"绑定没提供的方法"是两种拒绝；传进来的记录不得被改写，
因为调用方还留着它。

**局限。** 这台设备只提供一种方法，所以即使存在更快的方法也选不出来：工具只给现有的方法计价。
`EmulatorExtras` 是模拟器自己的通道，因此便宜；在纯 adb 绑定上，要怪识别之前应当先跑这次测量。

## D70. 一次读取的成本就是整帧 OCR，现在这一行自己会说了

**为什么。** D68 让每条观察行自报 `seconds`；D69 又把一次 1.44 s 读取中的 0.051 s 归给截图，
于是剩下约 1.39 s 只被叫作"识别"。一个数字有三个合理的花法（整帧 OCR、窄 ROI 重读、分类器），
就没法优化——"减少 ROI 重读"和"降低 OCR 成本"是两处完全不同的代码。

**决定。** `LimbusRecognition.observe` 只统计它能点名的三段：唯一那次整帧 OCR、所有针对裁剪框的
窄 ROI 重读（走 `context.run_recognition_direct` 的那些），其余计入分类。每条观察行通过
`timing_fields()` 把三段写在自己那一行上；**缓存命中时返回空**——缓存帧没花时间，
报三个 0 就是伪造测量。

反例已固定：只报总时长不是"零拆分"；只报两段（缺一段）是写者的 bug，读成未测量；布尔不是时长；
`scene_mismatch` 没有动作体，不带分段；AST 闸门遍历三个写者，要求真正解包 `timing_fields()`。

**证据（真实 Maa 流水线 + 归档帧，`input_sent: false`）。**

| 帧 | 总时长 | 整帧 OCR | ROI 重读 | 分类 |
| --- | --- | --- | --- | --- |
| MAP（`packaged-mirror-20261012-045906/frame-0009.png`） | 1.01 s | **0.84 s** | 0.00 s（0 次） | 0.12 s |
| RESUME_DIALOG（`map-live-20261023-214443/frame.png`） | 0.76 s | **0.63 s** | 0.00 s（0 次） | 0.08 s |

整帧 OCR 是分类器的 **8 倍**，而这两页上 ROI 通道一次都没跑。因此下一步该动的是 OCR 调用本身
（裁剪、阈值、或者某类页面根本不需要整帧），而不是 ROI 重读次数——这是"每次读取只有一个总数"
的仪表根本支撑不了的方向判断。

**局限。** 两帧不是分布，且都是不需要 ROI 通道的 POST 类页面；带待定页眉的 MAP 页会有三次 ROI 重读。
归档的 142 局没有分段字段，语料会一直报"分段未测量"，直到出现本决定之后写出的运行。
回放帧在内存里，设备截图仍在这些数字之外（由 D69 单独度量）。

## D71. 落不下去的输入，不该被发出去

**原因。** 第一次获授权的实机运行（`evidence/runtime/packaged-mirror-20261023-221109`）发出八次点击并都落地。
第九次发出去后，框架回答 `controller not found [controller_id=]`，随后整局再无任何记录，直到看门狗按 240 s 预算杀掉它。

本该拦住它的守卫只把控制器 id 与空字符串比较，而这次绑定的 id 是 `None`。`None` 不等于 `''`，
于是守卫放行、点击被发出；同一个洞在 `swipe`、`key` 和 flow 路径上都是敞开的——flow 路径在“记一条控制器状态”之后就直接用原始控制器投递点击。

**决定。** 用一个谓词回答“这个绑定能不能投递输入”：当 id 为 `''` 或 `None` 时
`binding_is_empty(controller)` 为真；当控制器根本没有 `id` 属性时为假（连问题都答不了的替身不该被指控，
现有设备桩正是这种）。`click`、`swipe`、`key` 与 flow 点击都在投递前询问它，拒绝时抛
`RuntimeError('the_controller_binding_is_empty')`，循环本来就会把它变成一个有名字的结束。

**反例（已固定）。** `None` 绑定的点击被拒绝且什么都没发（这正是那次实机回归，
`tests/test_click_binding.py::test_a_none_id_refuses_the_click`）；正常绑定照常投递；
没有 `id` 属性的桩不被指控；`swipe`/`key` 与 `click` 回答一致；
flow 路径是在点击被构造之前询问，而不是在它被投递之后；谓词断言为唯一一个元组
`EMPTY_BINDINGS == ('', None)`，以后的输入门不能发明第三种“空”的写法。

**证据。**

| | D71 之前 | D71 之后 |
| --- | --- | --- |
| `None` 绑定上的点击 | 发出、被框架拒绝、整局挂到预算用尽 | 发出前拒绝，以有名字的原因结束 |
| 覆盖的输入门 | 只有 `click`，只认 `''` | `click`/`swipe`/`key`/flow 点击，`''` 与 `None` |
| 测试 | 没有绑定相关测试 | `tests/test_click_binding.py` 7 例 |

**局限。** 这次改动只让失败变响，不让它不可能。第八次与第九次点击之间有什么把绑定清空了，而截图仍在工作，
那是下一个问题：日志已经记住了页面（`RESUME_DIALOG`）、坐标（966, 591）与理由，
控制器句柄必须在整局里被持续观察，而不是被假定。

## D72. 回答"不"的节点，已经把任务结束了

**原因。** 连续两次获授权的实机运行丢在同一次点击上：`packaged-mirror-20261023-221109` 点了 (966, 591)、
`-223237` 点了 (958, 595)，两次都以 `controller not found [controller_id=]` 被框架拒绝。两份日志在三秒前都有同一行：
`node_action_unconfirmed`，紧跟在 `terminal {reason: unknown_or_bounded_transition_exhausted}` 之后。
Maa 在流水线节点失败时会拆掉任务，所以后面的点击根本无法路由——而且没有任何东西说出这件事。
两局都一直挂到看门狗按预算杀掉。

D71 的守卫抓不到它：它从句柄读到的 id 不是空的，空 id 只出现在框架自己构造的请求里。**问句柄，等于问错了证人。**

**决定。** 动作节点失败即结束运行。`_act` 仍写 `node_action_unconfirmed`（这行仍是证据），
然后调用 `device.end_session(ActionNodeFailed.reason)`——此后任何输入都会抛 `the session ended (...)`——
并抛出 `ActionNodeFailed`，其原因为 `an_action_node_failed_and_the_task_was_torn_down`。
循环既有的处理会把它变成一次有名字的停止，而不是静默。

**反例（已固定）。** 从不返回的节点仍以 `ActionNeverReturned` 结束，不是这一种；回答成功的节点照旧返回判定、继续下一步；
失败之后设备拒绝点击并给出 `the session ended`
（`tests/test_native_action.py::test_an_action_that_came_back_unconfirmed_ends_the_run`）。
测试用的假设备同样模拟这次拒绝，避免"任务已拆但设备照收输入"的假绿。

**证据。**

| | D72 之前 | D72 之后 |
| --- | --- | --- |
| 动作节点失败 | 记一行、循环继续、下一击无处可去 | 记一行、结束会话、以有名字的原因停下 |
| 实机怎么结束 | 看门狗按预算杀掉（退出码 124，226 / 222 事件） | 循环自己结束 |
| 谁还能投递输入 | 任何持有设备对象的人 | 没有人：`end_session` 拒绝每一道门 |

**局限。** 它让运行在正确的时刻停下，但不解释 `MirrorDrive` 为什么两次都以
`unknown_or_bounded_transition_exhausted` 失败。那是下一个问题——而它现在是一局的**最后一行**，
不再是埋在结束前 400 个事件里的一行。

## D73. 一个无法继续"它被要求继续的那一局"的任务

**为什么。** 两次获授权实机运行都点了镜牢卡片、落到 `RESUME_DIALOG`（未完成的一局必然回这个对话框），
然后以 `LimbusUnknown` / `unknown_or_bounded_transition_exhausted` 结束
（`evidence/runtime/packaged-mirror-20261023-221109`、`-223237`）。打包任务的节点表里有
`MirrorDrive`（卡片）、`MirrorEnter`（入场页）、`MirrorTeamEvidence`，**唯独没有对话框本身的节点**——
于是"已经在一局里"这个状态，对那个被要求继续它的任务来说是死路。Python 窗口层认得这一页，打包任务不认得。

**决定。** 入场任务为它最可能遇到的状态补一个节点：`MirrorResume` 识别 `RESUME_DIALOG`，
在按钮带里读出 `resume` 词，并点击识别给出的框。ROI 来自实机帧自己的 OCR 证据：1920x1080 下
`Resume` 位于 `[902, 579, 114, 34]`（`evidence/runtime/packaged-mirror-20261023-224524/frame-0026.json`），
节点读 `[.38, .505, .62, .585]`——够宽以容纳位移后的对话框，下边界 632 px 又停在
`Halt Exploration`（647 px）之上。`MirrorHard` 与 `MirrorDrive` 都能走到它，失败同样落到 `LimbusUnknown`。

**证据（离线、真实流水线、实机自己的帧）。** `build/verify_resume_replay.py` 把
`assets/resource/base` 装进真实 `Tasker`（用真实的 `limbus_scene` 识别），回放
`frame-0024`（DRIVE）、`frame-0026`（RESUME_DIALOG）、`frame-0025`（MIRROR_ENTRY）：

| 版本 | 点击 | 识别 | 结局 |
| --- | --- | --- | --- |
| 改前 | `[[647, 485]]` | `DRIVE` | 在 `RESUME_DIALOG` 上 `unknown_or_bounded_transition_exhausted` |
| 改后 | `[[690, 500], [963, 602], [1644, 740]]` | `DRIVE`、`RESUME_DIALOG`、`MIRROR_ENTRY` | 走到入场页 |

中间那次 `(963, 602)` 就是 `Resume` 按钮。**没有发送任何游戏输入**：回放控制器声明了期望，其余一律拒绝。

**反例**（`tests/test_entry_task_resume.py`，9 例）：没有 token 的节点永远拿不到点击框；
ROI 拉大到覆盖 `Halt Exploration` 会被报出；locale 缺 `resume` 词会被报出；
点击目标必须来自识别结果，不能是坐标。

**局限。** 这是一个转移，不是一个"续跑算法"。它从入场链路里续上**被挂起的镜牢局**；
它不判断"该不该续"（那是窗口层的职责），而且证明它的是一段三帧回放，不是一次通关。

## D74. 任务的判决说的是它自己的路线，不是屏幕

**为什么。** D73 让入场任务学会续上被挂起的一局。修完之后第一次实机运行仍在 128 秒后以
`an_action_node_failed_and_the_task_was_torn_down` 结束
（`evidence/runtime/packaged-mirror-20261023-230804`）：任务把 `DRIVE` → `MIRROR_ENTRY` →
`RESUME_DIALOG` → `MAP` 一路走通，然后在 `LimbusUnknown` 上终止——因为**地图不在入场任务自己的
`next` 名单里**，地图归 Python 循环。`wait_task` 报 `succeeded: False`，D72 把它变成停止，
于是一局刚被交回一张活地图的运行，被"交接的那个任务"的返回码结束了。

**决定。** 节点动作返回"未确认"之后，循环在**动作发出的那一页**做**一次有界读取**，让屏幕来决定：

| 读取结果 | 循环怎么做 |
| --- | --- |
| 换了一页 | 记 `the_task_ended_but_the_page_moved`，清掉标记，继续 |
| 还是同一页 | 以 `ActionNodeFailed` 结束本次运行（D72 的保护不变） |
| `UNKNOWN` 或读不到 | 视同未移动：没有观察到变化，运行结束 |

任务的返回码说"我的路线走完了"，屏幕说"这个转移已经发生"。只有后者回答循环真正在问的问题。

**证据（实机）。** 第三次获授权运行 `evidence/runtime/packaged-mirror-20261023-231231`：
`recognized DRIVE → MIRROR_ENTRY → RESUME_DIALOG`（D73 的节点确实触发）、`terminal
unknown_or_bounded_transition_exhausted`、`node_action_unconfirmed`，随后出现
**`the_task_ended_but_the_page_moved {page: null, node: MirrorDrive, now: MAP}`**，
循环继续在地图上读取、点击、恢复，直到它自己的预算结束本次运行（`exit 124`，215 秒）。
这条序列在这次决定之前，128 秒就结束了。

**反例**（`tests/test_native_action.py`，10 例）：失败节点之后还是同一页，仍是"被拆的任务"，
仍然结束会话；`UNKNOWN` 不算移动，因为什么都没看到；页面移动后会话保持存活
（`device.ended is None`）。

**局限。** 这条规则只允许"屏幕动了就继续"，并不保证这个转移是对的——它到达的地图仍必须可读；
下一次实机运行显示的正是"地图上的节点点击推不动页面"。
`the_task_ended_but_the_page_moved` 上的 `page: null` 是 `acting['page']` 的老毛病，不是新规则。

## D75. 点击框的种类，识别器早就知道

**为什么。** `map_clicks` 会给出九种检测框，而 `candidates_of` 把种类丢掉了，只留矩形。
循环随后点击邻接过滤留下的第一个框——在 39 个可读的归档地图帧里，37 次都是
`gold_badge_node`：190×190 的格子，它的**中心**常常是两个节点之间的空地。客户端画在
"它肯接受的那一步"上的高亮字形（`bright_lit_icon`、`lit_icon`）几乎每帧都在，却几乎从不
排在第一位。

**决定。** 让种类跟着框走：`candidates_of` 把 `record['map_candidate_kinds']` 以
`box_key(box)`（`"678,353,40,40"`）为键存下，`map_nodes_offered` 事件带与 `boxes` 平行的
`kinds=[...]`，每条 `map_click_result` 都说出它所判的框是哪种（被循环替换掉的点击保留
它发出时记住的种类，因为报价列表已经换过了）。随后 `candidates_of` 用
`CLICK_KIND_ORDER` 排序：被标记的那一步在前，格子居后，不认识的种类排在最后而**不是丢掉**
——排序是策略，而识别器早就回答了这个策略需要的问题。

**实机证据。** `packaged-mirror-20261023-232612`：2 次 `gold_badge_node` 点击全被拒
（`the_page_stayed_on_the_map_after_the_click`），而唯一的 `bright_lit_icon` 框排在第四，
从未被点到。改序之后，`packaged-mirror-20261023-233056` 首次点击 `lit_icon`，运行走通
`NODE_PANEL → PRE_BATTLE_TEAM → BATTLE_HUD`——这一系列第一次进入战斗——而
`packaged-mirror-20261023-233928` 打完了那场战斗、走过一个节点、跳过演出、做出
`EVENT_CHOICE`、清掉结果并掷了一次 `EVENT_CHECK`：11 步、11 次点击，一条诚实的
`mirror_loop_stopped(stop_path='agent_loop')`。

**反例。** 识别器临时造出来的种类排在最后而不会被丢掉，所以只报格子的帧仍然有东西可试；
未知字符串与格子同列。若判决对应的框已不在当前报价里，就退回到随待判点击记住的种类。

**局限。** 种类表用文本作键，因为循环的状态与最终结果要 JSON 化：第一版用元组作键，
一次实机运行以 `callback_failed: keys must be str, int, float, bool or None, not tuple`
结束。排序仍只是启发式——地图的连通性无法从单帧读出；而且节点点击自身的判决在页面随后
进入 `NODE_PANEL` 时仍会写成 `the_map_stayed_with_the_party_in_place`，因为它比较的是队伍
的像素，不是下一次读取命名的页面。

**证据。** `python tools/audit_map_clicks.py` 按种类打印发出/接受/拒绝计数，并在本决定
之前写成的归档上说"未测量"。`tests/test_map_click_kinds.py`（12 个测试）钉住写入、排序、
记住的种类、JSON 安全与工具本身。

## D76. 一次点击的判决，属于那个还能推翻它的读取

**为什么。** 地图点击的成败原本在 settle 窗口内部就定死了：页面仍是 `MAP`、队伍也没动，
循环就写下 `the_page_stayed_on_the_map_after_the_click`（无候选分支）或
`the_map_stayed_with_the_party_in_place`（队伍分支），并把它算进
`map_refused_streak`。可是打开节点面板的点击**不会移动队伍**，而面板动画完全可能在
settle 窗口关闭之后才完成。2026-10-23 23:39 与 23:55 两次实机运行是同一个形状：

| 运行 | 点击 | 当时写下的判决 | 紧接其后的读取命名了什么 |
| --- | --- | --- | --- |
| `packaged-mirror-20261023-233928` | 标记节点 `(1028,480)` | `the_map_stayed_with_the_party_in_place` | `NODE_PANEL` |
| `packaged-mirror-20261023-235553` | 标记节点 `(1060,476)` | `the_map_stayed_with_the_party_in_place` | `NODE_PANEL` |

而 `map_refused_streak ≥ 1` 就会把 `map.progress_button` 逃生口交给 window，于是它离开
探索（`the_exploration_must_be_resumed_before_a_node_click`）。**一次错判决 = 一整个重新
进入的循环**：`packaged-mirror-20261023-231231` 上这个循环约 90 秒，而且始终没试下一个节点。

**决定。** 页面未变的点击**还不算拒绝**。两处站点都改记 `outcome='unjudged'`，并把
目标、种类与判决所用的帧存进 `state['map_unjudged']`；下一个 `step` 一开始就用**那次读取
命名的页面**清算它：

- 任何非地图页面 → `accepted`，原因 `the_click_was_taken_after_the_verdict`，连击清零；
- 仍是地图 → `rejected`，原因 `the_click_was_not_taken_and_the_page_stayed`，
  这时才由 `map_refusal_streak` 计数。

清算函数用 `map_dispatch.is_map(page)` 而不是拿字面量 `'MAP'` 比较：循环里新加一个页面
字面量正是 D44 的棘轮要数的东西，而它**确实**把本改动的第一版判红了。

**这次没有修的部分。** 一次点击仍会写两条判决（先 `unjudged`，后清算）；
`run_metrics.click_kinds` 把它们分开统计，所以那张表不会声称一次尚未发生的落地。拒绝的
**数量**不变，变的只是时间点晚一次读取 —— 这正是"晚开的面板不算拒绝"所需要的。

**实测。** `packaged-mirror-20261023-235553`（获授权，162.3 秒，9 次点击）：运行走过
`EVENT_CHECK → CUTSCENE → EVENT_CHECK_RESULT → EVENT_CHECK_READY → GIFT_GET → MAP`，
点中 `(1060,476)` 的标记节点后到达 `NODE_PANEL`，再点它的进入控件，落到一个识别器叫不出
名字的界面（E.G.O 遗物获得 + `Check Passed`，右下有 `SKIP`），预算在那里结束。那次运行仍
写下旧的终局 `rejected`（两行 `map_click_result` 是 `superseded` 与
`the_map_stayed_with_the_party_in_place`）—— 证据不是结论的产物，结论是从证据里改出来的。

**局限。** 一次什么都没打开的点击要多花一次读取才会被称作拒绝，连击因此比以前晚一步
进入"未恢复探索"的判断。另一种做法是相信 settle 窗口 —— 而上面那张表把它测成两次两错。

## D77. 只有两个名字里一个被记住的页面，等于靠运气命名

**为什么。** 证据是 2026-10-23 23:55 那次获授权实机运行，而且只有一句话：`NODE_PANEL`
点了进入之后，屏幕上是 `Super Shop` `[282,154,202,54]` 0.96（下面挂着 Enhance/Fuse/Gifts
三个页签）、`Leave` `[1622,945,150,53]` 1.0、`Sinner`/`Heal` 与一块 `SUPER OPEN`。
`src/maalimbus/vision.py` 的商店规则把标题锚在 `^Shop$`（来自
`assets/resource/en/locale.json`），于是它不匹配、这一帧掉出所有规则变成 `UNKNOWN`，
循环把**剩下的 11 次读取**全花在它上面，直到 `loop_deadline_exceeded`
（`packaged-mirror-20261023-235553`，162.3 秒、9 次点击、floors `[2]`）。

词表里其实早就有 `"super_shop": "^Super Shop$"` —— 词存在，而分类器里没人用它。页面由
节点恰好画出的那个标题命名，另一个标题的代价由运行来付。

**决定。** 商店规则在同一带内接受两个标题：

```python
if ((find(records, locale.get('shop', ...), (.10, .10, .30, .24), size, .85)
     or find(records, locale.get('super_shop', ...), (.10, .10, .30, .24), size, .85))
    and find(records, locale.get('leave', ...), (.78, .82, .97, .96), size, .85)):
    return 'SHOP'
```

`Leave` 仍然是必需的：商店计划发出的每一个输入都读自本页显示的控件，而旁边的技能检定页
不能因为一个标题就被拉进来。

**离线证明（"先回放、后实机"）。** 用真实记录的 OCR 调 `vision.classify`：

| 帧 | 运行时记录的页 | D77 之后的分类 |
| --- | --- | --- |
| `frame-0022.json`（Super Shop，节点内） | `UNKNOWN` | `SHOP` |
| `frame-0026.json`（Super Shop，节点内） | `UNKNOWN` | `SHOP` |
| `frame-0008.json`（检定结果） | `EVENT_CHECK_RESULT` | `EVENT_CHECK_RESULT` |
| `frame-0009.json`（检定可继续） | `EVENT_CHECK_READY` | `EVENT_CHECK_READY` |

`tests/test_shop_super_shop.py` 六个用例钉住标题对、`Leave` 的必要性、标题带（货架中间的
`Super Shop` 字样不算商店）以及这些录制帧；商店两侧的检定页保持各自的名字。

**同轮的实机证明**（`evidence/runtime/packaged-mirror-20261024-001120`，获授权，163.3 秒、
13 次点击、157 个事件、floors `[2]`）：页面路径是
`SHOP → SHOP_PURCHASE → GIFT_GET → SHOP → SHOP_LEAVE → MAP → NODE_PANEL → MAP →
PRE_BATTLE_TEAM → DEPLOYMENT → BATTLE_HUD`，也就是说这次运行**认出了 Super Shop、买下了
计划要的那件遗物、清掉获得提示、刷新了一次货架、走自己的离开确认离开商店、走了一个节点、
提交队伍并开始了一轮战斗**，然后在战斗中途被 `loop_deadline_exceeded` 结束。购买路径
（`shop_vision`）因此在这个变体上真的跑过，花掉的是本轮的局内货币（模块预算未动）。同一
次运行也证明 D76 生效：`map_click_result unjudged (the_map_stayed_with_the_party_in_place,
lit_icon)` 之后紧跟 `accepted (the_click_was_taken_after_the_verdict)` —— 节点点击由下一次
读取清算，而不是去喂拒绝连击。

**局限。** 多一个标题只是多一处能认出商店的地方，并不把 `super_shop` 变成一个独立页面。如果
两种商店将来需要不同的输入，那个拆分必须由一次能显示差异的运行来决定。

## D78. 被杀掉的进程写不了自己的结尾，于是由杀它的进程来写

**为什么。** `tools/selfrun_mirror.py` 在外面执行调用方给的预算——必须这样，因为调用方
没法把自己手里的表拿走——用的是 `timeout=seconds + 15`。2026-10-24 00:19 那次获授权
的 420 秒实机运行走到了**第 3 层**（本系列第一次推进楼层），却在超过预算**十五秒**时被
杀掉，正好在一个 step 中间，于是循环再没走到 step 之间的检查，也再没写
`mirror_loop_stopped`。它的日志停在一次读取上：`stop: []`。十五秒比一个 step 还短，
这个余量根本做不到它存在的目的——留存记录里量到的超时是 12.3、12.3、13.3、15.2 秒，
其中一个本就落在旧余量里面。

后果不是措辞问题。`run_metrics.ending` 看不到结尾，就把这次运行判成 `died`，
`no_progress_stop_rate` 于是把一次健康的、正在推进的运行算成「没有进展就停下」。那个
本来用来回答「循环会不会放弃」的指标，读到的其实是「harness 有没有守住自己的承诺」。

**决定。** 余量是一个有名字的常量（`MARGIN_SECONDS = 45`，比量到的每一次超时都宽），
而「杀掉」由执行杀掉的进程来写：`subprocess.run` 超时时，`attempt()` 把
`harness.json` 写进这次运行自己的目录，内容含 `killed_by_budget`、停止原因、预算、
余量、实际耗时与退出码。`run_metrics.ending(rows, directory)` 先读这个文件，回答
`budget` / `harness_budget`，于是 `ENDING_KINDS` 成了五类：停止、报错、死亡、预算结束、
以及一条事件都没有。`tools/audit_runs.py` 会打印 `killed at the budget: N`，并且不把
这类运行列进失败；`no_progress_stop_rate` 在注记里说明预算结束不计入。

**反例。** 同样的行，没有那个文件，仍然是死亡——这个桶是证据，不是从沉默里推断出来的。
`harness.json` 里没写 `killed_by_budget` 就什么都不改。`summarise(rows)` 不带目录时仍
回答 `died`，所以没有调用方能无意间拿到这个桶。

**局限。** 在这个写入者出现之前被杀的几次运行（`packaged-mirror-20261023-221109`、
`…-223237`、`…-235553`、`…-001939`）会继续读成死亡：它们结束的时候没有这个文件，事后
补写就是在事后造证据。它们的记录保持 `died`，和 2026-10-23 之前那些没有 `stop_path`
的停止保持 `unrecorded` 是同一个道理。

## D79. 风险率是平的，等待就不叫耐心

**为什么。** `window_unknown_wait` 在读到无法命名的页面时，按 step 间隔（4 秒）睡一次，
而这一组是 2026-10-24 00:19 那次 420 秒运行里的第二大成本行：**428 秒里有 88 秒，12 次，
每次 7.3 秒**。最自然的优化是「等久一点」（越久没认出来，应该越接近认出），所以先量它。

**测量（154 次留存运行，413 段未知页 episode）。** 在页面已经无法命名 *t* 秒的条件下，
**下一次**读取能命名它的概率是：12%（t = 0–4 秒）、23%（4–8）、36%（8–12）、23%
（12–20）、28%（20–40）、28%（40–300）。风险率不随时间下降，所以等待不是耐心，而是给一次
成本 2.07 秒的采样加上延迟。同一份数据还否掉了两个邻居：战斗页之后读到 UNKNOWN，再读一次
**仍是 UNKNOWN 的有 136 次、回到战斗页只有 5 次**，说明那不是抖动而是真实换页，不值得加
专门等待；而解析时间 p50 11.3 秒、p90 45.5 秒、中位数两次读取就够，长轮询只会错过。

**决定。** 无法命名的页面拥有自己的节拍：`unknown_interval`（默认 **1.5 秒**，校验
`0 < x ≤ 30`，命令行为 `--unknown-interval`）只用于 `window_unknown_wait` 的睡眠与它的
`interval_s` 字段，别处不用。它故意低于一次读取的成本（2.07 秒）：循环应当保持采样，而不是
睡觉。其余所有等待仍用 4 秒的 step 间隔。

**这轮不声称什么。** 不会用一次实机样本宣称墙钟改进。改动后那次获授权的 150 秒运行
（`evidence/runtime/packaged-mirror-20261024-003759`，167.4 秒、7 次点击、114 事件、
`stop_path=agent_loop`）确实展示了新节拍——两次未知等待都是 1.5 秒——但它的三段 episode
用了 37–40 秒才解析，那是战斗动画阶段，与语料中位数不可比。下一轮要比的是
`run_metrics.time_budget` 里 `window_unknown_wait` 这一组，且只在与同一阶段可比的运行之间比。

**局限。** 风险率是在 4 秒节拍的留存运行上量的；把暂停缩短会改变采样密度，所以「每秒」的
风险率只会更好或不变——但这份语料证明不了，只有下一份能。

## D80. 用一群没给够时间的人算通关率，量到的是预算

**为什么。** 本系列量过的每一份语料里 `clear_rate` 都是 `0.0`——155 次运行、最好到第 3
层、没有一次到第 5 层。这个数字是真的，但它说的不是循环：一次完整的镜牢是五层、领奖、
回到大厅，而留存里没有任何一次被给过超过几分钟的时间。

**量到的。** 155 次留存运行里有 **19 次**以 `loop_deadline_exceeded`（调用方的墙钟）结束，
其余是循环自己决定的结束（拒绝、看门狗、任务被拆）或者死亡。所以诚实的说法是两句话：
通关率是零；**而且**只有少数运行是被时间切断的——这些运行短，是因为它们比一次通关更早
结束，而不是因为它们全部在第五分钟被砍。

**决定。** `efficiency()` 增加 `budget_ended`（结尾原因是调用方的墙钟），`metrics()`
增加两项：

- `clear_rate` 的注记里写明有多少次运行被调用方预算结束——这个比率于是被对着那个数字读，
  而不是被当成能力结论；
- 新指标 **`floor_progress`**：在「走到过楼层」的运行上取平均楼层，basis 里写出最好楼层与
  计数。循环在走楼上变好时，动的会是这个数字；通关率在没人给够时间之前动不了。

**反例。** 以任何其他原因结束的运行 `budget_ended` 为假；一次楼层都没走到的语料报 `None` 并
写「none of N runs reached a floor」，绝不报 `0.0`；平均值只在那些走到过楼层的运行上取，
所以一群「被砍在第 0 层」的运行不会把它拉低成像是证据的东西。

**局限。** `floor_progress` 没有按难度归一：困难难度的第 1 层与普通难度的第 1 层算作同一层，
两者之间的差异这里不建模。

## D81. 无法命名的页面，不是一种行为

**为什么。** D66 把 `window_unknown_wait` 量到可归属时间的 19.9%，D79 又量出「等久一点
并不会更容易认出」——但这一组是把毫无共同点的状态平均在一起：战斗之后的载入画面、镜牢菜单
之后的过渡、过场之后的黑屏。拿整组去评判节拍或成本，评的是一团混合。

**决定。** 两个小改动，各在日志的一侧：

- 循环记住「读取器最后一次能**命名**的页面」（`state['last_named_page']`，写在地点解析处，
  且仅在该场景不是 `UNKNOWN` 时写），此后每条 `window_unknown_wait` 都带 `after=<该页>`。
  还没有命名过任何页面时写 `after=None`，而不是编一个名字。
- `time_budget` 把每次未知等待的秒数归到 `unknown_waits[after]`，`time_portfolio` 跨运行
  合并这些切分；`tools/audit_time.py` 把它们打印成「unknown-page waits, by the page that
  came before them」。

**为什么写在行里，而不是事后推断。** 事后的日志只能靠重放事件顺序、指望中间恰好命名过一次
页面才能还原前驱；而产生这次等待的那一行本来就知道。把它写在知道的地方，和 D68 的
`seconds`、D65 的 `offered` 是同一条规则。

**反例。** D81 之前写下的行没有 `after`，落进 `unrecorded` 桶，而不会混进已命名的桶——
今天的语料是 520 次等待、全部 `unrecorded`（4 601 秒），工具现在如实这样打印。没有未知等待
的语料不报桶，而不是报一个假装是零的空桶。

**局限。** `after` 是「最后一次**命名**的页面」，在连续多帧读不出来之后，它可能已经隔了好
几次转换；那是循环当下知道的最接近的事实，不是对紧邻前驱的断言。

## D82. 任务被拆掉之后，关的是输入门，不是读门

**为什么。** D72 在动作节点「不确定完成」时结束整轮，D74 把它收窄：如果页面变了，任务的判决说的是任务**自己的路线**，不是屏幕，于是循环继续走。实机运行
`evidence/runtime/packaged-mirror-20261024-010918` 说明这次收窄漏了什么：`05:13:08.972` 入口任务在 `LimbusUnknown` 上结束；`05:13:10.376` 下一次读取仍然成功（`map_observed seconds 0.74`），所以继续是对的，之后还有三次读取（`0.78`、`0.77`）。`05:13:19.200` 循环决定点一个地图节点并写下 `window_intent`；框架在同一秒回答
`controller not found [req.controller_id=]`，其中 `"controller_id":""`，而 Python 侧再没回来：那条 intent 之后日志一直空到 `05:23:20`，进展监视才写下 `mirror_loop_stopped(reason: the_run_kept_observing_without_writing_anything, stop_path: no_progress_watchdog)`。测试台早就放弃，在 `05:20:02` 就杀掉了外层进程，于是这一次运行同时有两条真实记录——而统计打印的是「被杀」，不是「自己结束」，这是下面第二半缺陷。

**统计为什么也说了假话。** `run_metrics.ending` 先看 `harness.json` 再看日志，所以这次明明写了自己结束的运行被算成 `budget`/`harness_budget`。测试台只能解释「没有写结束的运行」：原生读取阻塞时 Python 无法打断，两条记录不是二选一。

**旧守卫为什么看不见。** D71 拒绝空的 `controller.id`，但任务被拆掉之后这个句柄仍然报非空 id——这条限制在 D71 落地时就已经写下。拒绝发生在框架的原生调用里，那里既没有 Python 检查，也没有看门狗线程能跑（进程在等待时占着解释器）。

**决定。** 任务被拆掉的设备可以继续读，不可以再发输入。拆任务那条路径在设备上记下 `note_binding_lost(<原因>)`；每个输入门（`click`、`swipe`、`key`）在发出任何请求之前以该原因拒绝；循环的错误路径把这次拒绝变成有名字的结束。读门保持打开，因为实机运行证明那里读取仍然可用。

**必须通过的反例。**
- 存活的绑定照常发送：`test_a_live_binding_still_posts`。
- 拒绝不会在错的方向上黏住：只在 `note_binding_lost` 之后生效，且保留第一个原因（`test_a_lost_binding_is_named_before_the_handle_is_trusted_again`）。
- 三个门都拒绝，不只是点击（`test_every_input_door_refuses_after_the_binding_is_gone`）。
- D74 的继续路径仍然能读：`_act` 挺过一个被拆的任务之后，设备的 `binding_lost` 已设置、`ended` 未设置，日志顺序是 `node_action_unconfirmed` 之后 `the_task_ended_but_the_page_moved`（`test_a_torn_task_closes_input_and_keeps_reading`）。
- 类别表认识这个原因（`test_the_reason_is_the_one_the_ending_and_the_kind_table_use`），因此 `audit_hold_gap` 仍然保持 0 个未分类失败。

**局限。** 循环无法自己修复一个被释放的绑定：只有「拥有控制器的新任务」能做到，把它接上是另一项决定。预防是唯一可用的防御，因为阻塞发生在框架的原生调用内部。

## D83. 只会进、不会结束的任务，进不完

**为什么。** 入口任务的路是 `DRIVE → MIRROR_ENTRY → RESUME_DIALOG → MAP`，而最后那一页没有节点。实机
`packaged-mirror-20261024-010918` 把四步都放在同一个任务里：05:12:41 认出 `DRIVE`，05:12:44 认出
`MIRROR_ENTRY`，05:12:46 认出 `RESUME_DIALOG`，从 05:13:06 起这个任务的每一帧都读到 `MAP`。三次读之后
任务以 `unknown_or_bounded_transition_exhausted` 放弃，`D74` 从另一边把循环救回来
（`the_task_ended_but_the_page_moved`），随后 `D82` 因为拥有控制器的那次任务已经消失而关掉输入门——一个
缺失的节点，吃掉了那次运行的剩余时间。

类别不是「MAP 特殊」，而是：**一个把界面从 A 移到 B 的任务，也必须能说「已经在 B 了」**；而它的页面词汇
每过一段时间就会因为游戏多了一条到达路径而变旧。

**决定。** 新增 `MirrorInside`：识别 `MAP`、什么都不做、结束任务——从 `MirrorDrive`、
`MirrorResume`、`MirrorEnter`、`MirrorHard` 都能到达。**以成功结束**才是诚实的答案：调用方要的是「在里面」，
而它已经在里面了。打包管线 795 → 796 个节点；`tools/prepare_resources.py` 里带着同一个节点和同样的边，安装
树也同步了这个文件。

**反例。** `tests/test_entry_task_inside.py` 从节点表构造：删掉节点后可达场景集合里就没有 `MAP`（门会红）；在
地图上**点击**的版本被拒绝；没人指向的节点不可达——因为「存在却到不了」的节点，是同一个缺陷往前一步。

**证据。** `build/verify_inside_replay.py` 用真实 `limbus_scene` 识别与回放控制器重放那四帧：

| | 认出 | 终止 | 任务 |
| --- | --- | --- | --- |
| 改前 | `DRIVE`、`MIRROR_ENTRY`、`RESUME_DIALOG` | `unknown_or_bounded_transition_exhausted`（`last_scene: MAP`） | `succeeded: False` |
| 改后 | `DRIVE`、`MIRROR_ENTRY`、`RESUME_DIALOG`、`MAP` | 无 | `succeeded: True` |

**局限。** `MAP` 是目前唯一被观察到「入口任务在里面结束」的页面。`BATTLE_HUD`、`DUNGEON_PROGRESS` 要各自
有节点、各自有证据才算覆盖；而且任务仍然分不清「玩家在里面」与「玩家在一张他没要的地图上」——这个区分属于调用
方，因为只有调用方知道自己是从哪一页点进来的。

## D84. 任务结束了，门还归它管

**为什么。** D82 为**被拆掉**的任务（失败的节点）关上了输入门，因为框架会连控制器路由一起释放。D83 又让
入口任务可以**成功**在 `MAP` 上结束——实机 `packaged-mirror-20261024-014706` 把由此暴露的问题摆了出来：
05:49:20 任务正常结束，05:49:27 循环发出下一次点击，MaaFW 回答 `controller not found [req.controller_id=""]`，
Python 侧就在这次原生调用里卡住，一直到测试台按预算杀掉外层进程（465.3 秒、157 事件、`floors: [3]`，一次
本身没有任何错误的运行）。

所以门的判据错了。它问的是「这个节点是不是被拆掉的」，而真正要紧的事实是**「此刻有没有一个任务拥有控制器」**。
D71 早就记下：任务拆除后 `controller.id` 仍然报非空，所以 id 不能作为答案的来源。

**决定。** `MirrorRunner._input_door()` 直接问框架（`self.tasker.running`）：可以发送时返回 `None`，没有任务
拥有控制器时返回 `INPUT_NEEDS_A_TASK`。`step` 在派发 `click`/`swipe`/节点计划**之前**先问一次：被拦下的输入
记为 `input_withheld`（页面、计划理由、目标、门自己的理由），会话以该理由结束，`pages.STOP_KINDS` 把它归为
`refused_by_policy`，失败普查因此仍保持 0 个未分类。

**反例。** `tests/test_input_door_task.py`（6 个测试）：任务在运行时不拦；完全没有 tasker（`None`）时不拦，
因为没有可问的对象；`record` 计划永远不拦；以及——对一个 `id` 仍是 `'controller-1'` 的 tasker，门必须回答
「不能发」，这正是实机里那个桩的形状。

**局限。** 知道路由没了，并不能把路由要回来：得要有一个任务，而起任务是调用方的决定（测试台的
`--attempts`）。所以这条决定让结局变成**有名字、立刻发生**，而不是在框架里卡六分钟；给循环一个自己的有界
重入，是下一个单元。

**证据。** 上面那次实机就是失败案例（这条决定因它而来）；测试把两个方向都钉住；`python tools/audit_hold_gap.py`
仍报告 `still unclassified (hold) 0`，新理由已被归类。
